# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project shape

CareerPilot AI is a three-service monorepo: a **Spring Boot 4 / Java 25 backend** (`backend/`) acts as the control plane, a **Python FastAPI + LangGraph 0.2 agent service** (`agent-service/`) hosts the multi-agent workflow, and a **React 18 + Vite + TS frontend** (`frontend/`) is the UI. They share **one PostgreSQL** database (currently a **Neon serverless** instance, external to docker-compose — see `.env`) with the pgvector extension — backend persists domain data, agent-service persists LangGraph checkpoints into the same DB. Redis, Kafka, and MinIO/S3 run in `docker-compose.yml`.

The backend has grown well past its original vertical slice into ~30 role-based packages (job discovery, resume tailoring, execution/browser automation, workflow tracking, learning, autopilot, company intelligence, career-goal intelligence, etc. — see "Architecture" below for the ones with non-obvious cross-file shape). The great majority of that surface still ships **dark by default** behind independent `*.enabled` feature flags — a package existing, or even having a REST controller, is not evidence it's live in production. Several tables and beans are also intentionally provisioned-but-unwired (see "Provisioned-but-unused" below).

**This is a live production system** at https://careerpilot-ai.duckdns.org/ (backend on an Oracle Cloud VM, frontend on Vercel) — treat backend/infra changes with the caution that implies; see "Deployment" below before touching `docker-compose.yml`, the `Dockerfile`, or anything under `deployment/`.

To **launch and smoke-test the whole stack from scratch**, use the `run-careerpilot-ai` skill ([.claude/skills/run-careerpilot-ai/SKILL.md](.claude/skills/run-careerpilot-ai/SKILL.md)): `docker compose --env-file .env up -d`, then drive it with `node .claude/skills/run-careerpilot-ai/driver.mjs --e2e` — a zero-dependency HTTP harness that probes all three services and runs a real register→login→dashboard→create-job flow against the live backend + Neon.

## Commands

### Run the whole stack (preferred)
`docker-compose.yml` at the repo root is now **hardened for the Oracle Cloud VM production deploy** (`SPRING_PROFILES_ACTIVE=prod`, no host ports published for `redis`/`kafka`/`minio`/`zookeeper` — only the backend can reach them internally). Running it bare on a dev machine works but hides those services from the host and disables Swagger. For local dev, layer the local-dev overlay on top:
```bash
cp .env.example .env
# Set: JWT_SECRET (>=32 chars), GEMINI_API_KEY, and your Neon DATABASE_URL/DATABASE_URL_PY
docker compose --env-file .env -f docker-compose.yml -f docker-compose.local.yml up --build
```
[docker-compose.local.yml](docker-compose.local.yml) restores host access to redis/kafka/minio and other local-dev conveniences that were intentionally stripped from the base file for the VM deploy. **Never apply this overlay on the production VM** — the VM runs `docker-compose.yml` alone.

Frontend on http://localhost:5173, backend on http://localhost:8080 (Swagger at `/swagger-ui.html`), agent service on http://localhost:8088 (`/docs`), MinIO console on http://localhost:9001.

**Postgres lives outside docker-compose** (Neon serverless). The two `DATABASE_URL` forms in `.env` must use Neon's **direct** endpoint (no `-pooler` in hostname) — Flyway DDL and the LangGraph `PostgresSaver` both rely on prepared statements that break under Neon's transaction-mode pgBouncer pooler. Going back to a local Postgres container is documented as a comment block at the top of `.env.example`.

## Architecture — the things you need to read multiple files to see

### The LangGraph workflow is the heart of the product
[agent-service/app/graph.py](agent-service/app/graph.py) defines a single linear `StateGraph` over `CareerState` ([state.py](agent-service/app/state.py)) with these nodes in order: `resume_intelligence → job_discovery → ats_optimization → interview_prep → career_strategy → salary_intelligence → human_approval → application_tracking`. The shared `CareerState` TypedDict is the contract — each agent reads inputs from prior nodes' outputs and writes its own keys. When extending: add the node to `graph.py`, define inputs/outputs in `state.py`, place the agent under `app/agents/`.

The `human_approval` node uses `raise NodeInterrupt(...)` ([agents/human_approval.py](agent-service/app/agents/human_approval.py)) to pause the graph. The FastAPI `/runs` endpoint catches the interrupt and returns `status="interrupted"` to the backend; `/runs/resume` calls `graph.update_state(...)` + `graph.invoke(None, ...)` to continue. A conditional edge `_route_after_approval` routes `human_approval → application_tracking` on approval or `→ END` on rejection.

**Resuming a run is only valid while it's parked at `human_approval`.** [main.py](agent-service/app/main.py) checks `"human_approval" not in graph.get_state(cfg).next` and returns HTTP 409 if the run isn't currently awaiting approval; [WorkflowService.resume()](backend/src/main/java/ai/careerpilot/service/WorkflowService.java) mirrors this with its own guard (`deriveDisplayStatus(run) != "INTERRUPTED"` → `IllegalStateException` → 409) before even calling the agent. This double guard exists because resuming an already-terminal run (e.g. approving a run that was already rejected) silently corrupts its terminal state — don't remove either check independently.

State survives restarts via `PostgresSaver` (langgraph-checkpoint-postgres). `saver.setup()` in `_checkpointer()` is idempotent and creates the `checkpoints*` tables in the shared Postgres on first run — these are **not** in Flyway, they're owned by LangGraph.

### Two AI seams, no longer symmetric — read both before touching either
Each service has its own provider abstraction, and they have diverged. Do **not** assume they mirror each other.

**Java side — a multi-provider AI Gateway with health tracking and transparent failover.** [AiGatewayService.java](backend/src/main/java/ai/careerpilot/ai/AiGatewayService.java) is the single entry point for all AI in the backend; business services depend on it, never on a concrete provider. It routes each call through a configured provider order (default `deepseek,qwen,gemini`) with **automatic transparent failover**: 
- **Blocking calls** (`chat()`, `generateFeedback()`, etc.) fail over before returning if the primary provider fails.
- **Streaming calls** (`streamChat()`) fail over only *before the first token* — once tokens emit, failover is impossible (client already receiving from that provider).
- **Quota detection**: HTTP 429 errors trigger immediate failover without exhausting retries ([QuotaExceededException.java](backend/src/main/java/ai/careerpilot/ai/QuotaExceededException.java)).
- **Health tracking**: [ProviderHealthTracker.java](backend/src/main/java/ai/careerpilot/ai/ProviderHealthTracker.java) caches provider health (HEALTHY/DEGRADED/QUOTA_EXCEEDED/UNKNOWN) with 5-minute TTL to avoid repeated calls to failed providers.
- **Per-provider resilience**: Resilience4j **retry + circuit breaker** + usage metrics ([AiMetrics.java](backend/src/main/java/ai/careerpilot/ai/AiMetrics.java)).

Every provider implements [LlmProvider.java](backend/src/main/java/ai/careerpilot/ai/LlmProvider.java) (shared logic in `AbstractLlmProvider`); impls live under `ai/provider/` — `GeminiProvider`, `NvidiaDeepSeekProvider`, `NvidiaQwenProvider` (the two NVIDIA ones extend `AbstractOpenAiChatProvider` since NVIDIA's API is OpenAI-compatible). A provider only joins the chain when `isConfigured()` is true, so DeepSeek/Qwen are skipped unless `NVIDIA_API_KEY` is set. 

**Streaming provider callback**: When calling `streamChat(messages, system, providerCallback)`, pass a `Consumer<String>` to learn which provider actually served the response (useful for frontend attribution). The callback fires in the `doOnComplete()` handler, *after* the stream succeeds. This replaced ThreadLocal tracking, which didn't survive Reactor's async thread boundaries.

**Adding a provider** = one new `LlmProvider` impl + listing its key in `ai.gateway.order` — no business-logic changes.

**Python side — a single rate-limited Gemini provider.** [agent-service/app/ai_provider.py](agent-service/app/ai_provider.py) keeps the four-method contract (`generate_response`, `generate_structured_response`, `generate_json`, `estimate_cost`), but agents must obtain it via `get_ai_provider()`, which returns a `RateLimitedAIProvider` decorator wrapping `GeminiProvider`. The decorator delegates to a process-wide singleton `GeminiRateLimiter` ([rate_limiter.py](agent-service/app/rate_limiter.py)) that enforces RPM + TPM token buckets, minimum request spacing, and full-jitter retry on 429/503 — all 8 agents share one limiter. Counters are exposed at `GET /metrics`. **Never instantiate `GeminiProvider` directly in an agent** (it's intentionally retry-free) and never touch `google.generativeai` directly — go through `get_ai_provider()`.

The Python `GeminiProvider` uses `responseSchema` for structured output — every agent passes a JSON Schema and the provider calls `genai.GenerativeModel(...).generate_content(..., generation_config={"response_mime_type": "application/json", "response_schema": SCHEMA})`. Don't switch agents to free-text parsing; the schema is what keeps outputs typed.

### The Copilot is a separate, streaming AI surface (not the LangGraph workflow)
Distinct from the backend→agent-service workflow path: the backend hosts its own conversational copilot under `/api/copilot` ([CopilotController.java](backend/src/main/java/ai/careerpilot/api/CopilotController.java)), which **streams tokens over SSE** (`POST /api/copilot/stream`, `text/event-stream` via `SseEmitter`) plus `GET /conversations` and `GET /conversations/{id}/messages`. [CopilotService.java](backend/src/main/java/ai/careerpilot/service/CopilotService.java) calls `AiGatewayService.streamChat(messages, system, providerCallback)` to capture which provider served the response; the callback executes after streaming completes and stores the provider name in an `AtomicReference` that the SSE done event sends to the frontend. [AgentOrchestrator.java](backend/src/main/java/ai/careerpilot/service/AgentOrchestrator.java) builds the per-page/per-action system prompt + context block, and [ConversationMemory.java](backend/src/main/java/ai/careerpilot/service/ConversationMemory.java) persists turns via `CopilotConversationRepository`/`CopilotMessageRepository` (tables from `V2__copilot.sql`). The frontend consumes this through `lib/copilotStream.ts` + `components/copilot/CopilotPanel.tsx`. `GET /api/diagnostics/ai` and `GET /api/diagnostics/workflow` ([DiagnosticsController.java](backend/src/main/java/ai/careerpilot/api/DiagnosticsController.java)) expose gateway provider health and call/fallback metrics plus workflow engine status.

**Copilot prompts are skill-routed, not one monolithic prompt.** [CopilotSkillRouter.java](backend/src/main/java/ai/careerpilot/service/copilot/CopilotSkillRouter.java) maps each request to one of 10 `CopilotSkill` enum values — by explicit `action` if the frontend sent one, else by keyword-matching the free-text `message` (`inferSkillFromMessage`), else falling back to `GeneralAssistantHandler`. Each skill is a `CopilotSkillHandler` impl under `service/copilot/skill/` (e.g. `WorkflowExplanationHandler`, `AtsAnalysisHandler`, `ResumeAnalysisHandler`) extending `AbstractSkillHandler`, with three jobs: `assembleContext()` pulls RAG data via [CareerContextRetriever.java](backend/src/main/java/ai/careerpilot/service/CareerContextRetriever.java) into a `SkillContext`, `systemPrompt()` returns the skill-specific instructions, `contextBlock()` renders that data as the prompt's context section. Adding a new skill = new `CopilotSkill` enum value + new handler class + wiring it into `CopilotSkillRouter`'s constructor map.

### Backend → agent-service boundary
[WorkflowService.java](backend/src/main/java/ai/careerpilot/service/WorkflowService.java) is the only caller of the agent service. It owns:
- assembling the LangGraph input from a `Resume` row + `Job` rows
- calling `AgentServiceClient` (a `WebClient` wrapper, [agent/AgentServiceClient.java](backend/src/main/java/ai/careerpilot/agent/AgentServiceClient.java))
- persisting/upserting a `WorkflowRun` row keyed by the LangGraph `thread_id` on every transition
- publishing a Kafka event via `WorkflowEventProducer` on every state change
- **converting entity responses to DTOs** via `toResponse(WorkflowRun)` for proper JSON serialization

**DTO pattern for API responses**: Controller methods must return `WorkflowRunResponse` (defined in [WorkflowDtos.java](backend/src/main/java/ai/careerpilot/api/dto/WorkflowDtos.java)), not the raw `WorkflowRun` entity. The DTO uses `Map<String, Object>` for state instead of `JsonNode`, which avoids Jackson type definition errors. The service layer parses the entity's JSON state string into a Map before constructing the DTO. This pattern should be replicated for any entity with complex JSON fields.

**`deriveDisplayStatus(WorkflowRun)` is the single source of truth for lifecycle status** — it derives the per-stage agent timeline from the run's JSON `state` blob and computes the displayed status (`RUNNING`/`INTERRUPTED`/`REJECTED`/`COMPLETED`/`FAILED`) from that timeline rather than trusting the raw persisted `status` column, which can lag. Both `WorkflowController` responses and `CareerContextRetriever.getWorkflowContext()` (used by the Copilot) call this same method, so the UI and the AI assistant can never disagree about a run's state. Approval/rejection audit fields (`approved_by`/`approved_at`/`rejected_by`/`rejected_at`/`human_feedback`) are stamped into that same `state` JSON blob in `mergeResponse()` — there's no separate audit table or migration for them.

When you add a new workflow surface (e.g., re-run, branch), funnel it through this service — do not expose the agent service to the frontend.

### JWT auth carries multi-tenant context
[JwtService.java](backend/src/main/java/ai/careerpilot/security/JwtService.java) packs `userId`, `orgId`, `email`, `role` into the access token. [JwtAuthFilter.java](backend/src/main/java/ai/careerpilot/security/JwtAuthFilter.java) extracts them into an `AuthenticatedUser` record placed in the security context, and [CurrentUserResolver.java](backend/src/main/java/ai/careerpilot/security/CurrentUserResolver.java) exposes it as a controller method parameter. Multi-tenant isolation is enforced **manually** in each service via `userId.equals(entity.getUserId())` checks — there is no row-level security and no Hibernate `@Filter`. New endpoints must replicate this pattern.

`@EnableMethodSecurity` is on, but **no controller uses `@PreAuthorize`**. Anyone authenticated can hit any endpoint. Be aware when adding admin-only routes.

### Database is shared but logically partitioned
[V1__init.sql](backend/src/main/resources/db/migration/V1__init.sql) creates 9 tables owned by the backend (Flyway-managed, Hibernate runs in `validate` mode), and [V2__copilot.sql](backend/src/main/resources/db/migration/V2__copilot.sql) adds the copilot conversation/message tables. The LangGraph checkpoint tables are auto-created by `PostgresSaver.setup()` and are **not** in Flyway. If you add new tables for the backend, write the next migration (`V3__*.sql`); never modify an applied migration. `flyway.baseline-on-migrate: true` is set in `application.yml`, so Flyway will baseline against the existing Neon schema state on first boot if `flyway_schema_history` is missing — useful because V1 may have been applied manually in the Neon SQL editor.

pgvector extension is enabled and `vector(768)` columns exist on `resumes.embedding` and `jobs.embedding`, but **no code path generates embeddings**. If you wire embeddings, the `AiGatewayService` is the right seam, and you'll need an HNSW/IVFFlat index — none exist today.

### Job discovery is a global pool, layered on top of org-scoped jobs
[jobdiscovery/](backend/src/main/java/ai/careerpilot/jobdiscovery/) ingests real listings from external sources and keeps them separate from the existing org-scoped Browse/Add-job/Apply flow on the same `jobs` table — discovered rows have `org_id IS NULL` and `source`/`external_id` set; manually-added jobs have `external_id IS NULL` and are untouched by any of this. `V4__job_discovery.sql` adds the discovery columns plus `job_recommendations` and `job_fetch_audit` (applied by hand against Neon — see the migration's own header comment, same baseline-on-migrate caveat as V1).

- **Providers** (`jobdiscovery/provider/`) implement `JobProvider` (`name()`, `isConfigured()`, `fetch() -> List<RawJob>`) — same "joins the chain only if configured" convention as `LlmProvider`. `AdzunaProvider`/`JoobleProvider` are keyed (skipped without API keys); `RemoteOkProvider`/`ArbeitnowProvider` are keyless and always on. `AbstractWebJobProvider` holds the shared `WebClient` fetch/parse boilerplate.
- **`JobAggregationService.discoverAll()`** is the orchestrator: for each configured provider, fetch → `JobNormalizer.toJob()`/`.merge()` → upsert into `jobs` deduped on `(source, external_id)`, recording one `JobFetchAudit` row per provider. A provider failure is isolated (FAILED audit row, run continues) — it never throws to the caller. `JobDiscoveryScheduler` runs this daily at 06:00 (`jobs.discovery.cron`), gated by `jobs.discovery.enabled`; `JobController`'s `POST /api/jobs/discovery/run` triggers it manually and `GET /api/jobs/discovery/audit` reads the audit trail.
- **`JobMatchingService.refreshForUser()`** is a separate, rule-based (no LLM) matcher: scores the discovered pool via `JobScoring` and upserts the top 50 into `job_recommendations` so the Recommended tab is a cheap indexed read. It is **source-agnostic** — the candidate signals (skills/target role/locations/experience/preferences/excluded roles) come from **[CandidateSignalResolver.java](backend/src/main/java/ai/careerpilot/jobdiscovery/CandidateSignalResolver.java)**, which is the Phase-1 single-source-of-truth switch: when `jobs.matching.profile-source-enabled=true` and a `candidate_profiles` row exists, every signal is read from the **canonical `CandidateProfile` only**; otherwise it falls back to the legacy `WorkflowRun` state + live `candidate_preferences` path (pre-Phase-1 behavior, unchanged). Flip the flag on only **after** profiles are backfilled (`POST /api/admin/candidate-profile/backfill?dryRun=false`, admin-role + flag gated); rollback is instant (flag off). The matcher also applies a **user-defined excluded-roles hard filter** (`JobMatchingService.isRoleExcluded`, whole-word title match + non-tech family match via `JobTaxonomy`) — empty exclusions are a no-op, so it is safe always-on. Excluded roles are edited in `candidate_preferences` (`excluded_roles`, added by `V9`) and snapshotted into the profile.
- `JobController`'s `GET /api/jobs/discovered?scope=domestic|international&country=...` reads the global pool directly; `GET /api/jobs/recommended` reads the precomputed `job_recommendations`. The frontend's [Jobs.tsx](frontend/src/pages/Jobs.tsx) Domestic/International tabs call the former, separately from the existing org-scoped job list.

### Resume tailoring is a 7-stage async event pipeline, not one service
[resumetailoring/](backend/src/main/java/ai/careerpilot/resumetailoring/) implements Phase 2D: Resume Tailoring → ATS Optimization → Gap Analysis → ATS Explainability → Cover Letter → Application Package → Auto-Apply Preparation. Each stage is its own vertical slice (own sub-package, own job table, own bounded `ThreadPoolTaskExecutor`, own REST controller) chained by Spring `@TransactionalEventListener` — there is no shared orchestrator class. The chain: `RecommendationApprovedEvent → ResumeTailoringWorker → ResumeTailoredEvent → AtsOptimizationWorker → AtsOptimizedEvent → GapAnalysisWorker → GapAnalysisCompletedEvent → AtsExplainabilityWorker → AtsExplainabilityCompletedEvent → CoverLetterWorker → CoverLetterCompletedEvent → ApplicationPackageWorker → ApplicationPackageReadyEvent → AutoApplyPreparationWorker` (final stage, publishes nothing further). Events live in `resumetailoring/event/`.

**Every worker follows the identical shape** — do not deviate when adding a stage:
```java
@Async(PipelineExecutorsConfig.<STAGE>_EXECUTOR)
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT, fallbackExecution = true)
public void on<PriorEvent>(<PriorEvent> event) {
    if (!triggerEnabled || !service.isEnabled()) return;
    try {
        executor.execute(() -> service.doWork(...));
    } catch (Exception e) {
        log.warn("... worker failed ...: {}", e.toString());
    }
}
```
Two independent flags per stage (`<stage>.enabled` gates the engine itself; `<stage>.trigger....enabled` gates whether it auto-fires off the prior stage's event) — both default `false`. `PipelineExecutorsConfig` centralizes the bounded executors (one per stage, deliberately not shared, so one stage's saturated queue can't starve another's).

**Do not wrap a worker's listener body in `@Transactional(propagation = REQUIRES_NEW)`.** This was a real, previously-shipped bug (`ResumeTailoringWorker`/`AtsOptimizationWorker`): the annotation opened a second transaction around the job-row insert, and the bounded-executor thread it then handed off to could read that row back *before* the wrapping transaction committed — a silent race that stranded jobs in `QUEUED` forever with zero error logs. The `@TransactionalEventListener(phase=AFTER_COMMIT)` already guarantees the triggering transaction has committed; no worker needs its own `@Transactional`.

Each stage's job table (`resume_tailoring_jobs`, `ats_optimization_jobs`, `gap_analysis_jobs`, `ats_explainability_jobs`, `cover_letter_jobs`, `application_package_jobs`, `auto_apply_package_jobs` — migrations `V24`–`V30`) tracks `QUEUED`/`RUNNING`/`SUCCEEDED`/`FAILED` and is the only way to trace an async run; there is no synchronous fallback API for any stage. Poll a stage's status via its own `GET /api/diagnostics/<stage>` and `GET /api/diagnostics/<stage>/queue` endpoints ([DiagnosticsController.java](backend/src/main/java/ai/careerpilot/api/DiagnosticsController.java) for resume-tailoring/ATS-optimization, [PipelineDiagnosticsController.java](backend/src/main/java/ai/careerpilot/api/PipelineDiagnosticsController.java) for gap-analysis/ATS-explainability/cover-letter/application-package/auto-apply-package).

### Phase 2E — Application execution (`execution/`) plus real browser automation
[execution/](backend/src/main/java/ai/careerpilot/execution/) reuses the same `@Async` + `@TransactionalEventListener(AFTER_COMMIT)` worker pattern as resume tailoring, chained: safety validation (`execution/safety/SafetyEngine`) → mandatory human approval (`execution/approval/ApprovalService`, `POST /api/execution/approve`) → execution (`execution/execution/ApplicationExecutionService`) → retry policy (`execution/retry/RetryPolicyService`, deterministic failure-class → RETRY/PAUSE/STOP) → tracking → analytics, each its own sub-package/executor via `execution/config/ExecutionExecutorsConfig.java`.

Real browser automation lives here too: `execution/browser/GuestApplyAutomationService.java` drives Microsoft Playwright's Java API via `PlaywrightAutomationProvider`. "Guest" means unauthenticated/no-login apply forms only — eligibility is a **hardcoded allowlist** in `execution/ats/GuestApplyEligibility.java` limited to `{greenhouse, lever}` (the only ATSes with public no-login forms); every other connector under `execution/ats/connector/` is a stub. `login()` unconditionally throws — no credentials are ever stored or entered. The flow is two-phase: fill only verified real `User` fields, screenshot the unsubmitted form, queue a `FORM_SCREENSHOT` approval — only after a human approves does `finalizeSubmit()` re-navigate and actually click submit. Gated by `BROWSER_AUTOMATION_ENABLED` (default `false`); the safety/approval stage flags default to fail-closed "on" even though the execution stage itself is dark.

### Phase 3A — Workflow tracking is a second, deliberately separate tracking system
[workflow/](backend/src/main/java/ai/careerpilot/workflow/) is explicitly documented in its own code as event-driven, not a linear pipeline. `workflow/correlation/WorkflowCorrelationService` keeps one row per running Phase 3A instance, upserted on every stage transition; `WorkflowDeadLetterService` is where every worker's catch block writes instead of propagating, for audit/replay. `workflow/tracking/ApplicationLifecycleService` + `ApplicationStatusMachine` is the canonical per-(user,job) status machine — **deliberately separate from Phase 2E's execution-scoped tracking**: `application.tracking.*` (Phase 2E) and `workflow.tracking.*` (Phase 3A) are two different config namespaces tracking two different things, don't conflate them. `workflow/timeline/TimelineService` is a human-readable, confidence-scored event stream distinct from the validated status history, and `workflow/analytics/` is its own metric set, separate from Phase 2E's `execution_analytics`.

Two narrower additions in the same package family: `workflow/email/EmailIntelligenceService` is a deterministic keyword classifier that is **fully inert** — no mailbox integration exists, nothing fetches email, rows only arrive via a manual-ingest path. `workflow/interview/InterviewService` tracks interview rounds (Recruiter/Technical/System Design/Manager/HR/Final/Offer) with append-only feedback. All gated by their own `workflow.*` / `email.intelligence.*` / `interview.tracking.*` flags, default `false`.

### Phase 6 — Learning-from-outcomes exists but is deliberately disconnected from live scoring
`learning/LearningEventBridge` (same async-listener pattern) captures 2D/2E/3A domain events — application submitted/rejected/accepted, interview detected, offer received, recommendation approved — into `LearningEvent` rows. Downstream, `learning/pattern/SuccessPatternEngine` + `FailurePatternEngine` compute pattern rows, and `learning/recommendation/RecommendationWeightManager` upserts weights that `learning/recommendation/AdaptiveRecommendationEngine.getBoost(userId, dimension, key)` exposes as a read-only facade.

**Important**: that engine's own Javadoc states it is not wired into `JobScoring`/`JobMatchingService` — built end-to-end, but live job matching does not consult it. Treat it like the "Provisioned-but-unused" list below, not as an active feature. Also in this phase: `learning/resume/ResumeLearningService` (best resume version by interview/offer rate), and `learning/career/CareerLearningEngine` + `CareerStrategyEngine` — the latter is what actually populates `domain/CareerStrategy`, combining a probability engine and a trajectory analyzer into one row per user. Gated by `learning.adaptive-recommendation.enabled` / `learning.adaptive-career.enabled`, both default `false`.

### Package validation, AI review, decision memory, and retention — four more additive layers, don't conflate them
- `packageintel/ApplicationPackageIntelligenceService` (Phase 7.11) does NOT re-assemble or re-score anything: it delegates package assembly to the existing Phase 2D.6 `ApplicationPackageService`, then binds already-computed signals from other engines (autopilot decision, company research, learning boost, resume match) onto the package, runs `ApplicationPackageValidator`, and records an immutable validation history row. - `review/ApplicationReviewPipeline` (Phase 7.12) is the next gate on top of that: it REVIEWS the Phase 7.11 package (never mutates it) by running each enabled reviewer (`review/reviewer/` — resume/ATS/company-fit/learning/consistency/quality) and persists an `ApplicationReview` head + immutable history row. - `memory/CareerMemoryService` (Phase 7.15.1, "Career Decision Memory") is deliberately **not** a rebuild of `learning_event` (Phase 6, pattern-computation) or `recommendation_feedback` (Phase 2C, raw reaction log) — it normalizes both of those plus five Phase 3A workflow events (via `CareerMemoryEventBridge`) into one durable, ranked, append-only "why the candidate decided X" record the Copilot can read instead of re-asking. - `retention/RetentionService` is a pure delete-by-age maintenance job (no LLM, no events) for the append-only ledgers that grow unbounded — workflow dead-letter/correlation tables plus the recommendation/execution/resume-tailoring audit trails. Gated `retention.enabled`, default `false` (no-op with stock flags).

### Phase 9.1 — Spring AI Foundation exists but is not on any request path
`ai/springai/` adds Spring AI (`spring-ai-bom` 2.0.0, Boot-4-aligned) as a foundation layer that coexists with — and is completely inert relative to — the existing AI Gateway. `SpringAiConfig` builds `ChatModel`/`StreamingChatModel`/`EmbeddingModel` beans from a single OpenAI-protocol client (`com.openai:openai-java-client-okhttp`, added alongside the starter since it pulls no HTTP transport of its own), gated end-to-end by `ai.springai.foundation.enabled` (default `false` — the beans literally aren't constructed when off). Spring AI's own OpenAI autoconfiguration is explicitly excluded (`spring.autoconfigure.exclude` in `application.yml`) so it can never auto-activate off an incidentally-set `spring.ai.openai.*` property — `SpringAiConfig` is the only path these beans can come from. `ai/springai/adapter/` (`SpringAiChatService`, `SpringAiModelFactory`, `SpringAiProviderAdapter` implementing a standalone `ProviderAdapter` interface — deliberately not `ai.careerpilot.ai.LlmProvider`, so nothing here can be picked up by `AiGatewayService`'s provider chain) is the shape a future migration would build on. `ai/springai/mcp/` (`McpToolRegistry`, `McpToolDefinition`, `McpCapability`, `ToolExecutionContext`) is extension-point interfaces only — no implementation, no server connection; real MCP tool servers (filesystem/Postgres/GitHub) are explicitly out of scope until Phase 9.3+. As of Phase 9.1 alone, nothing outside `ai/springai/` referenced any type in this package; Phase 9.2 (below) is the first and only exception.

### Phase 9.2 — the first real Spring-AI-backed provider, wired in canary (last) position
`ai/provider/SpringAiLlmProvider.java` implements the real `ai.careerpilot.ai.LlmProvider` contract (extends `AbstractLlmProvider`, so every feature-helper prompt template is reused for free) on top of the Phase 9.1 `ChatModel`/`StreamingChatModel` beans — this is the one place the Spring AI foundation is actually load-bearing. It's registered as a plain, unconditional `@Component` (matching every other provider's shape, not `@ConditionalOnProperty`-gated) because `AiGatewayService` autowires `List<LlmProvider>`; the `ChatModel`/`StreamingChatModel` beans it needs are injected via `ObjectProvider` (never fails to construct even when Phase 9.1's flag is off) and `isConfigured()` returns `false` unless **both** `ai.springai.foundation.enabled=true` and a real api-key are set — identical in spirit to an NVIDIA provider with a blank key. Added as key `spring_ai` at the literal end of `ai.gateway.order` — the canary position, reached only after every other configured provider has failed. `ai.gateway.providers.spring_ai` in `application.yml` is diagnostics-display metadata only (model/timeout mirrored from the same `SPRING_AI_FOUNDATION_*` env vars so the two can't drift) — `SpringAiLlmProvider` does not read that block; its real config comes solely from `ai.springai.foundation.*`.

Two real bugs surfaced and were fixed during this phase, both specific to the OpenAI Java SDK's eager-validation behavior (unlike this codebase's own `AbstractOpenAiChatProvider`/WebClient-based providers, which never validate credentials at construction time): (1) `OpenAiChatModel.Builder` silently tries to build its own async client from nothing if only `openAiClient(...)` is supplied — fixed via `springAiOpenAiClient.async()`, which correctly inherits the already-configured credentials; (2) a blank api-key makes `OpenAIOkHttpClient.Builder.build()` throw immediately at bean-creation time — fixed by substituting a non-blank placeholder when the real key is blank, so construction always succeeds and `isConfigured()` (not a startup crash) is what gates real usability, matching every other provider's resilience contract.

Live-verified end-to-end (not just unit-tested): with the flag on and a real NVIDIA key, `SpringAiLlmProvider.chat()` returned a genuine `"pong"` response from NVIDIA's live API through the full Spring AI stack.

### Phase 9.3 — Gemini migrated to Spring AI (provider 1 of 6), flag-gated with legacy as default
`ai/migration/` is the provider-by-provider migration seam the enterprise migration strategy calls for: `ProviderRegistryConfig` (`@Configuration`) is the **only** place that decides, per provider key, whether the legacy or the Spring-AI-backed implementation is the one actually registered as an `LlmProvider` bean — `AiGatewayService`/the Smart Router are byte-for-byte unchanged and have no idea this class exists, since Spring's `List<LlmProvider>` autowiring naturally collects whichever bean the registry produced. `SpringAiMigrationProperties` binds `spring-ai.providers.<key>.enabled` for all 6 providers (Gemini/Groq/SambaNova/NVIDIA/Qwen/OpenRouter per the stated migration order), all defaulting `false`; only `gemini` has a real second implementation today (`GeminiSpringAiProvider`) — the other five flags exist so their config shape is stable, but flipping one currently has zero effect (no `@Bean` branch reads it yet) until that provider gets its own migration phase, following this identical pattern.

`GeminiProvider` (legacy) had `@Component` removed — its ONLY change — since it's now constructed explicitly by the registry instead of auto-scanned; no other line changed. `GeminiSpringAiProvider` (new, `ai/provider/`) targets the same Gemini Developer API (api-key auth) as the legacy provider via Spring AI's `spring-ai-google-genai` starter — deliberately not `spring-ai-vertex-ai-gemini`, which needs a GCP service account this deployment doesn't have. Both implementations read the identical config (`ai.gateway.providers.gemini.*`) — migrating is purely an engine swap, no new credentials. `displayName()` differs ("Gemini" vs "Gemini (Spring AI)"), which is the whole observability story: every existing log line/metric/diagnostics entry that already reports `displayName()` now shows which engine served a call, with zero new plumbing in `AiGatewayService`/`AiMetrics`/`ProviderHealthTracker`.

One real bug, same family as Phase 9.1/9.2: adding the `spring-ai-google-genai` starter alone (regardless of any migration flag) makes Spring Boot's own `GoogleGenAiChatAutoConfiguration` try to auto-construct an unrelated `googleGenAiClient` bean from `spring.ai.google.genai.*` properties this app never sets — crashing startup unconditionally. Fixed via the same `spring.autoconfigure.exclude` pattern used for the OpenAI starter in Phase 9.1.

Live-verified end-to-end: with `spring-ai.providers.gemini.enabled=true`, `GeminiSpringAiProvider.chat()` and `.streamChat()` both returned genuine `"pong"` responses from Gemini's live API. With the flag at its default (`false`), the registry log confirms it resolves to the legacy implementation and `gemini` reports `UP` exactly as before this phase.

### Phase 10.1 — Enterprise MCP Foundation: the platform, not a server
`ai/careerpilot/mcp/` is a dedicated Model Context Protocol platform layer, conceptually sitting between Spring AI and business services in the AI stack, built with the same "foundation only, zero wiring" discipline as Phase 9.1. **No MCP server (filesystem/Postgres/GitHub/Playwright/Redis/memory/etc.) is implemented or connected** — this phase builds the registry, capability model, health/metrics/security contracts, and plugin shape a future server integration would plug into. Every bean is gated by `mcp.enabled` / `mcp.health.enabled` (both default `false`, see `McpConfig`); with defaults, no bean in this package is constructed and nothing outside `ai.careerpilot.mcp` references it.

Core types: `McpCapability` (FILESYSTEM/DATABASE/BROWSER/GITHUB/MEMORY/SEARCH/AUTOMATION/KNOWLEDGE), `McpServerDefinition`/`McpToolDefinition` (pure metadata — registering one never opens a connection), `McpExecutionContext` (mirrors `AuthenticatedUser`'s userId/orgId multi-tenant shape), and `McpExecutor` (the tool-invocation contract — **no implementation exists**, matching the same "interface only" discipline as `learning/recommendation/AdaptiveRecommendationEngine` before it's consulted by live matching). Unlike Phase 9.1's narrower `ai.springai.mcp` placeholder (still present, unreferenced, and left as-is), `McpRegistry` here has a real default implementation — `InMemoryMcpRegistry`, a thread-safe in-memory map — because a registry with nothing to register into it can't be meaningfully built against or tested; registering a server/tool is still bookkeeping only, never I/O. `McpHealthManager`/`InMemoryMcpHealthManager` follow the same shape but nothing calls `recordHeartbeat` in this phase, so every lookup reports `UNKNOWN`. `McpMetrics`/`NoopMcpMetrics` is observability prep only — every method is a deliberate no-op, no Micrometer wiring.

`mcp.security` (`McpAuthenticationProvider`/`McpAuthorizationProvider`/`McpAuditor`) and `mcp.springai` (`SpringAiMcpBridge`/`McpToolResolver`/`ToolCallingAdapter`, built on Spring AI's real `org.springframework.ai.tool.ToolCallback` type already on the classpath since Phase 9.1's `spring-ai-bom` import) are interface-only extension points — no implementation, no bean, nothing calls them. The plugin contract: any future MCP server registers itself through `McpRegistry` via a plain `@Configuration`/`@Bean`, never hardcoded into this platform.

Verification for this phase relied on `mvn test` (1760/1760, zero regressions — same suite Phase 9.3 left at 1743) plus Spring `ApplicationContextRunner` tests (`McpConfigTest`) that load a real (if minimal) Spring context and assert bean presence/absence per flag combination — a more precise check of the exact risk (conditional bean wiring) than a full container boot. A live Docker container boot/smoke test (the verification style used in Phases 9.1–9.3) was **not** performed for this phase.

### Phase 10.2 — first real MCP tool servers, plugged into the 10.1 platform
`ai/careerpilot/mcp/tool/` adds five independently-flagged MCP servers (`mcp.filesystem.enabled` / `mcp.postgres.enabled` / `mcp.github.enabled` / `mcp.memory.enabled` / `mcp.context7.enabled`, all default `false`, all additionally requiring `mcp.enabled=true`) — each a thin read-only wrapper around an **existing** repository/service, not a new data source: filesystem wraps `ResumeRepository`, postgres wraps `JobRecommendationRepository`/`ApplicationRepository`/`CareerStrategyRepository`, memory wraps the Phase 7.15.1 `CareerMemoryService`, github is a new keyless `api.github.com` client (styled after `AbstractWebJobProvider`), and context7 is a new keyed client (dark unless `mcp.context7.api-key` is set — endpoint shape is best-effort/not live-verified, see `Context7ApiClient`'s javadoc). No new database table, no new query beyond existing finder methods, no write path added anywhere.

This phase also turns three Phase 10.1 interfaces into real implementations for the first time: `McpExecutor` → `ai/careerpilot/mcp/tool/DefaultMcpExecutor` (authorize → dispatch to the tool's `McpToolHandler` via a new `McpToolHandlerRegistry` → record metrics/health → audit, catching everything so a handler failure becomes `McpToolResult.failed(...)` rather than an exception — enforced defensively for future callers since nothing on a production path invokes it yet), `McpAuthorizationProvider`/`McpAuthenticationProvider`/`McpAuditor` → `DefaultMcpAuthorizationProvider` (any resolved `userId` is authorized, matching CLAUDE.md's documented "no `@PreAuthorize` anywhere" convention) / `DefaultMcpAuthenticationProvider` (always `true` — external-system auth is each client's own `isConfigured()` check) / `LoggingMcpAuditor` (slf4j only, deliberately does not write to the still-unused `audit_logs` table), and `SpringAiMcpBridge`/`ToolCallingAdapter` → `DefaultSpringAiMcpBridge`/`DefaultToolCallingAdapter`, which build real Spring AI `ToolCallback`s (via `org.springframework.ai.tool.function.FunctionToolCallback`, already on the classpath since Phase 9.1) that genuinely invoke `McpExecutor` when called. **Known limitation, documented in `DefaultSpringAiMcpBridge`'s javadoc**: the Phase 10.1 `toolCallbacksFor(capability)` signature takes no caller identity, so callbacks built through the bridge run with a system-scoped (`userId=null`) context — every Phase 10.2 handler already treats that as "no authenticated user" and degrades to an unavailable/empty result rather than leaking data, so this is safe but not yet useful for per-user questions.

`McpConfig`'s default `McpMetrics` implementation changed from `NoopMcpMetrics` (Phase 10.1) to the new `InMemoryMcpMetrics` — plain `AtomicLong` counters per tool name, styled after `ai.careerpilot.ai.AiMetrics` (itself hand-rolled counters, not Micrometer, despite the name) rather than a new dependency. `NoopMcpMetrics` remains in the codebase, just no longer constructed by default.

**Critically, none of this is wired into anything that runs today**: no controller, no business service, and no `ChatModel` prompt in `AiGatewayService`/the Copilot/LangGraph constructs or calls a `ToolCallback` built by this phase's bridge. The tool resolution flow described in the phase spec (Business Service → Spring AI → MCP Registry → MCP Tool → Response) exists and is genuinely functional end-to-end when invoked directly (see the `*McpServerConfigTest` classes, which call each registered handler and assert real output), but no business service invokes it — satisfying "every MCP integration must be additive" and "zero regression" simultaneously with "genuinely working, not a stub."

A Phase 10.2.1 validation sprint confirmed this gap explicitly (exhaustive grep: zero files outside `ai.careerpilot.mcp` reference any MCP type) and closed several testability gaps discovered along the way — regression tests were added for `SpringAiConfig`/`SpringAiLlmProvider`/`ProviderRegistryConfig` (previously verified only via now-deleted temporary smoke tests) and for full-context feature-flag gating of all five Phase 10.2 servers (`McpToolServersFeatureFlagTest`). Full suite after the sprint: 1816/1816.

### Phase 10.3 — Capability Engine: an orchestration layer that CAN route to MCP tool calling, still not connected to any controller
`ai/careerpilot/capability/` answers Phase 10.2.1's validation finding by building the missing piece — but, per its own explicit "ZERO REST API changes" requirement, still doesn't connect it to a controller; the gap from 10.2.1 remains open by design, one phase closer to closeable. `CapabilityAwareChatService` is a new, parallel entry point that decides per-request whether to call the existing, byte-for-byte-untouched `AiGatewayService` (the default) or route through MCP tool calling — `AiGatewayService`'s own code was not modified in any way for this phase.

The decision chain: `CapabilityResolver` (keyword matching, styled after `CopilotSkillRouter#inferSkillFromMessage`) maps free text to one of six `CapabilityType`s (`RESUME_ANALYSIS`/`JOB_RECOMMENDATION`/`GITHUB_REVIEW`/`CAREER_STRATEGY`/`INTERVIEW_PREPARATION`/`LEARNING_HELP`) → `CapabilityRegistry` (`InMemoryCapabilityRegistry`, six defaults pre-registered) supplies which `McpCapability` categories that type needs → `ToolSelectionEngine` resolves those into live, currently-registered `McpToolDefinition`s via `McpRegistry.toolsByCapability(...)` (never a hardcoded tool name) → `CapabilityEngine` (`DefaultCapabilityEngine`) combines all of the above into one `CapabilityDecision`. Any break in that chain — no keyword match, `tool.selection.enabled=false`, capability not registered, or zero tools actually resolved — produces `useToolCalling=false`, which `CapabilityAwareChatService` treats identically: call `AiGatewayService.chat(...)` unchanged.

When tool calling IS decided: `CapabilityAwareChatService` executes the selected tools via the Phase 10.2 `McpExecutor` — sequentially by default, or in parallel via `CompletableFuture.allOf(...)` when `parallel.tool.execution.enabled=true` — merges each `McpToolResult` into a text context block, then either synthesizes the final answer through the Phase 9.1 Spring AI foundation `ChatModel` (when `spring.ai.tool.calling.enabled=true` AND that bean exists) or, just like the no-tool-calling path, falls back to `AiGatewayService.chat(...)` with the merged context appended to the last user message. A capability match, a disabled Spring AI flag, and a missing `ChatModel`/`McpExecutor` bean are all handled as ordinary fallback branches, never exceptions — see `CapabilityResult.fallbackReason()`.

Four independent flags, all default `false`: `capability.engine.enabled` is the master switch — off, and none of this package's beans are constructed at all (`CapabilityConfig`, matching every other phase's dark-by-default discipline). `tool.selection.enabled`, `parallel.tool.execution.enabled`, and `spring.ai.tool.calling.enabled` are runtime toggles read via `@Value` inside the already-gated layer, not additional bean gates — flipping the master flag alone still routes every request to `AiGatewayService`. `spring.ai.tool.calling.enabled` deliberately lives under the pre-existing top-level `spring:` YAML block (not a duplicate root key) since that's the exact property path the phase spec named; safe because Spring AI's own autoconfiguration for that prefix is already excluded (Phase 9.1/9.3) and no real Spring AI property collides with it.

Verified via `mvn test` (1846/1846, zero regressions) plus unit/`ApplicationContextRunner` tests covering every branch: no-match fallback, tool-selection-disabled fallback, zero-tools-resolved fallback, sequential and parallel execution, a throwing tool degrading to `McpToolResult.failed(...)` rather than propagating, Spring-AI-present vs. Spring-AI-absent synthesis, and full-context bean-presence-per-flag-combination gating.

### Phase 10.4 — the Copilot is wired to the Capability Engine: the first real production call site
Unlike every prior Phase 9/10 sub-phase, this one **does** touch a live request path: `ai/careerpilot/service/CopilotService.java`, the backend that already serves `/api/copilot/stream`. Gated by `copilot.capability.integration.enabled` (default `false`, inline `@Value` only — no `application.yml` entry, matching its sibling `copilot.candidate-profile-context.enabled`/`copilot.career-memory-context.enabled` flags' existing convention). With the flag off, `CopilotService.streamTurn()` is byte-for-byte the pre-Phase-10.4 code: `ai.streamChat(turns, system, providerCallback)`.

With the flag on, a new private method, `routeTokens(...)`, runs a **cheap, synchronous pre-check** — `CapabilityEngine.analyze(userMessage)` — before deciding the token source: if no capability matched (general chat), it still calls `ai.streamChat(...)` unchanged, deliberately preserving real token-by-token SSE streaming for ordinary conversation (calling the synchronous `CapabilityAwareChatService.chat(...)` here instead would collapse every general-chat response into a single chunk — a user-visible regression the phase spec explicitly forbade). Only when a capability actually matched does it call `capabilityAwareChatService.chat(turns, system, mcpContext)` (Phase 10.3, itself internally re-running `analyze()` — harmless, no I/O) and wrap the single synthesized answer as a one-element `Flux`, which then flows through the exact same `.doOnNext(assistant::append).doOnComplete(persist).onErrorResume(...)` pipeline as the streaming path — so persistence, conversation history, and the SSE contract are all identical regardless of which branch produced the tokens.

**Failure handling matches the spec's three explicit fallback rules** — all three land on the same outer `try/catch` around the decision+chat call in `routeTokens()`, so a thrown exception from `CapabilityEngine.analyze()`, from `McpExecutor` tool execution inside `CapabilityAwareChatService`, or from Spring AI synthesis all fall back to `ai.streamChat(...)` identically (the "If MCP Tool fails → Continue with remaining tools" case is already handled one layer down, inside `DefaultMcpExecutor`/`CapabilityAwareChatService.executeTools` — a single tool failing never stops the others or reaches this catch block at all). One real gap found and fixed while wiring this: `CapabilityAwareChatService.chat()` (Phase 10.3) had no try/catch around its Spring AI synthesis call — a `ChatModel.call()` failure would have propagated instead of falling back to `AiGatewayService` with the already-gathered tool context; now caught and converted to the same graceful fallback the "flag off" branch already used.

Security is unchanged from Phase 10.2/10.3: `CopilotService` never touches `McpToolHandlerRegistry` or a handler directly — it only calls `CapabilityEngine.analyze()` (pure decision, no I/O) and `CapabilityAwareChatService.chat()`, which is the only caller of `McpExecutor` (authorize → dispatch → audit, unchanged).

Verified via `mvn test` (1853/1853, zero regressions — 1846 prior + 7 new, including a new `CopilotServiceTest`, the first test file this class has ever had). No REST DTO, controller, or frontend file changed.

### Phase 10.3.1 — Capability Engine's "Spring AI tool calling" was never real tool calling, until now
Live testing after Phase 10.4 shipped found `CapabilityAwareChatService` had two related bugs, both in the "real tool calling" path implied by its own name and by `spring.ai.tool.calling.enabled`: (1) `executeTools(...)` always invoked every MCP tool with `Map.of()` — an empty argument map, regardless of what the user actually asked — so any tool requiring input (GitHub's `username`, Context7's `query`) silently failed every single call (`{"reason":"missing required argument 'username'","available":false}`), registering as `success=true` in `MCP_AUDIT` because the tool's own handler returned a normal (non-exception) "can't do this" result; and (2) even where arguments didn't matter, "Spring AI synthesis" only ever *pre-executed* tools itself and pasted the merged JSON into the system prompt as text — Spring AI's `ChatModel` never actually selected or invoked a tool via its own protocol, so `FunctionToolCallback`/`ToolCallingChatOptions` (the actual Spring AI tool-calling API) were unused code paths despite the flag's name.

Fixed by wiring the real protocol: `DefaultToolCallingAdapter` (`ai.careerpilot.mcp.springai`) now calls `.inputSchema(...)` with the tool's real `McpToolDefinition.inputSchema()` (serialized via Jackson) alongside the pre-existing `.inputType(Map.class)` — previously only `.inputType(Map.class)` was set, which tells Spring AI how to *deserialize* args but exposes no real parameter schema to the model deciding what to pass. `CapabilityAwareChatService.chat()` now tries a new `synthesizeWithRealToolCalling(...)` path first when `spring.ai.tool.calling.enabled=true` and both the `ChatModel` and `ToolCallingAdapter` beans exist: it builds one real `ToolCallback` per selected tool via `toolCallingAdapter.adapt(tool, context)` — using the request's actual `McpExecutionContext`, not a system-scoped placeholder — passes them through `OpenAiChatOptions.builder().toolCallbacks(...).build()`, and calls `chatModel.call(prompt)` once, letting Spring AI's own internal loop decide whether/which tool to call, with what LLM-chosen arguments, invoke it, and feed the result back for a final answer. The pre-Phase-10.3.1 pre-execute-then-paste-as-text behavior still exists, renamed to `legacyPreExecuteAndRespond(...)` — it's the fallback whenever real tool calling isn't available (flag off, either bean missing) or throws, preserving the same never-fail-the-request discipline as every other engine in this codebase. `CapabilityConfig` injects the pre-existing Phase 10.2 `mcpToolCallingAdapter` bean (`McpConfig`, gated by its own independent `mcp.enabled`) as an `ObjectProvider<ToolCallingAdapter>` — optional, since `capability.engine.enabled` and `mcp.enabled` are independent flags.

**Live-verified the fix actually closes the argument-passing gap** (not just unit-tested): a Copilot request "Analyse my GitHub profile, username torvalds" produced `MCP_AUDIT tool=analyze_github_profile server=github ... success=true` with the LLM having genuinely extracted `username=torvalds` from free text via the now-exposed schema — previously this exact request always failed with the missing-argument error, silently, on every prior test. One separately-tracked, non-blocking observation: the NVIDIA-hosted `deepseek-ai/deepseek-v4-flash` model behind the Spring AI foundation client (see Phase 9.1's `SpringAiConfig`) sometimes echoes its own tool-call syntax as literal text in the *final* answer after a successful tool round-trip, rather than synthesizing a natural-language summary — a model output-quality quirk of that specific model's function-calling maturity, not a wiring defect; the `MCP_AUDIT` trail is the reliable signal, not the rendered text.

Verified via `mvn test` (2022/2022, zero regressions — 2020 prior + 2 new, covering real-tool-calling success and real-tool-calling-throws-falls-back-to-legacy).

### Phase 11.1 — Enterprise Intent Engine: a richer classification layer, still not wired to the Copilot
`ai/careerpilot/intent/` is the first increment of the six-part Phase 11 master plan (Phases 11.2–11.6 — Capability Planner, Multi-Capability Execution, Enterprise Memory Evolution, Proactive Career Intelligence, Autonomous Career Agent — are explicitly **not yet built**; the phase spec itself mandates incremental delivery with validation between each). Per the Phase 11 target architecture (`Copilot → Intent Engine → Capability Planner → Capability Engine → ...`), Intent Engine is a new layer sitting *above* the existing Phase 10.3 Capability Engine, not a replacement for it — `ai.careerpilot.capability` is untouched.

Pipeline: `IntentResolver` (`KeywordIntentResolver` — scores each registered `IntentDefinition` by keyword-substring matches, deliberately the ML-swap seam: a future embedding/LLM classifier implements the same interface) → `IntentClassifier` (`DefaultIntentClassifier` — ranks by score, ties broken by `IntentDefinition.priority()`, e.g. the more specific `GITHUB_ANALYSIS` beats `CAREER_STRATEGY` on an equal-score tie) → `IntentEngine` (`DefaultIntentEngine` — accepts the top candidate only above `intent.engine.min-confidence` (default 0.4), else an explicit reasoned fallback; never throws). `IntentType` is a **separate, richer taxonomy from `CapabilityType`** — 7 values including `EXECUTIVE_COACH`, which has no Phase 10.3 capability equivalent yet (anticipating a future capability the spec's own examples require). `IntentHistory` (`InMemoryIntentHistory`, bounded 50-entry-per-user ring buffer) and `IntentMetrics` (`InMemoryIntentMetrics`) exist for a future Capability Planner to consult — nothing reads them yet.

Single flag, unlike Phase 10.3's four-flag layering: `intent.engine.enabled` (default `false`, `IntentConfig` the only bean source — matches the phase spec's own single-flag requirement exactly). **Not wired into `CopilotService` or anything else** — this is deliberate scope discipline, not an oversight: Phase 11.2's Capability Planner is what will map a classified `IntentType` down to `CapabilityType`(s) and route into the existing Phase 10.3/10.4 pipeline; connecting Intent Engine directly to the Copilot now would bypass that not-yet-built planner.

Verified via `mvn test` (1885/1885, zero regressions — 1853 prior + 32 new) plus an `ApplicationContextRunner` end-to-end test (`IntentConfigTest`) that wires the real bean graph and classifies an actual message, and a dedicated test exercising every one of the phase spec's own worked examples ("I keep getting rejected" → Resume Analysis, "Can I crack Amazon?" → Interview Preparation, etc.) through the real resolver+classifier.

### Phase 11.2 — Capability Planner: bridges Intent Engine and Capability Engine, still not executing anything
`ai/careerpilot/planner/` answers the Phase 11.1 package javadoc's own promise: the first code that maps a classified `IntentType` down to one or more `CapabilityType`s (Phase 10.3, byte-for-byte unchanged). Per the Phase 11 target architecture, this is planning-only — Phase 11.3 (Multi-Capability Execution, not yet built) is what will actually execute a `CapabilityPlan`; `CapabilityPlanner` is not called by the Copilot, `CapabilityAwareChatService`, or anything else yet.

`DefaultCapabilityPlanner`'s `IntentType → List<CapabilityStep>` mapping is a static `Map` today (six of the seven Phase 11.1 intents map 1:1 onto an identically-shaped Phase 10.3 capability); `EXECUTIVE_COACH` — which still has no dedicated capability — is the one worked multi-capability example, mapping to `{CAREER_STRATEGY (HIGH), JOB_RECOMMENDATION (MEDIUM)}` with an explicit `CapabilityDependencies` edge (job recommendations should be informed by an already-computed career strategy). `DefaultPlanOptimizer` resolves steps + dependencies into a stage-by-stage `ExecutionOrder` via Kahn's-algorithm topological sort (each stage a list of capabilities safe to run in parallel — the shape a future Phase 11.3 `ParallelCapabilityExecutor` would consume) with priority-based ordering within a stage; a dependency cycle (never produced by today's static mapping, but a future dynamic one could) degrades to one combined stage rather than looping or throwing, matching the same never-fail discipline as every prior Phase 10/11 engine.

Single flag, gated the same way as Phase 11.1: `capability.planner.enabled` (default `false`, lives under the pre-existing top-level `capability:` YAML block alongside Phase 10.3's `capability.engine.enabled` — not a duplicate key). `CapabilityPlannerMetrics` (plan latency, plan size, cycle-detection count) is intentionally separate from Phase 10.3's `CapabilityMetrics` — planning and execution are different concerns measured at different layers.

Verified via `mvn test` (1901/1901, zero regressions — 1885 prior + 16 new), including an `ApplicationContextRunner` end-to-end test wiring the real bean graph and producing an actual multi-stage plan, and dedicated topological-sort tests (independent steps → one parallel stage, a real dependency → two ordered stages, an out-of-plan dependency ignored rather than blocking, a forced cycle → graceful one-stage degrade).

### Phase 11.3 — Multi-Capability Execution: actually runs a plan, still not called by anything live
`ai/careerpilot/planner/execution/` is the layer that turns a Phase 11.2 `CapabilityPlan` (planning output only) into a real, executed `MultiCapabilityResult` — multiple capabilities (resume, GitHub, memory, jobs, career strategy) genuinely running in one request. Still not wired into the Copilot or any controller — `ExecutionCoordinator` is the intended future call site for whichever phase eventually connects Intent Engine → Capability Planner → this layer → Spring AI synthesis.

`DefaultCapabilityExecutor` executes ONE capability by reusing the existing Phase 10.3 `CapabilityRegistry`/`ToolSelectionEngine` to resolve its MCP tools and the existing Phase 10.2 `McpExecutor` to run them — no duplicated tool-resolution logic, and never a tool handler called directly (same security contract as every prior phase). A step is retried (whole-step, not per-tool) up to `multi.capability.max-retries` (default 1) additional times before being recorded as a partial failure. `DefaultParallelCapabilityExecutor` runs one stage's capabilities concurrently via `CompletableFuture` — safe because Phase 11.2's `PlanOptimizer` already guarantees no dependency within a stage, mirroring the exact parallel shape Phase 10.3's `CapabilityAwareChatService.executeTools` established one layer down (over MCP tools instead of whole capabilities). `DefaultExecutionCoordinator` walks `ExecutionGraph.from(plan)` stage by stage — sequential between stages (a later stage may depend on an earlier one's results), parallel within — and a failed capability in one stage never stops later stages from attempting to run. `DefaultResultMerger` produces a genuinely structured `MergedExecutionContext` (a `Map<CapabilityType, Object>` of successful results plus a rendered text block noting failures) rather than concatenating raw strings, per the phase spec's explicit requirement.

Single flag, same pattern as 11.1/11.2: `multi.capability.enabled` (default `false`). `CapabilityRegistry`/`ToolSelectionEngine`/`McpExecutor` are all injected as `ObjectProvider`s (their own independent flags — `capability.engine.enabled`/`mcp.enabled`) — `DefaultCapabilityExecutor` degrades to an explicit failed `ExecutionResult` rather than throwing if either underlying layer is off.

Verified via `mvn test` (1925/1925, zero regressions — 1901 prior + 24 new), including a timing-based test proving three simulated 100ms tool calls complete in well under the ~300ms sequential baseline (genuine concurrency, not just API shape), a real retry-then-succeed test, a partial-failure test confirming later stages still execute after an earlier stage's failure, and a full `ApplicationContextRunner` flag-gating test.

### Phase 11.4 — Enterprise Memory Evolution: a new classification layer, additive alongside every existing memory subsystem
`ai/careerpilot/memory/enterprise/` adds the 8-category memory taxonomy from the phase spec (WORKING/LONG_TERM/CAREER/DECISION/CONVERSATION/SKILL/PREFERENCE/LEARNING) as a **new layer that does not replace anything**: `ai.careerpilot.memory.CareerMemoryService` (Phase 7.15.1, still the backing store for the Phase 10.2 Memory MCP server), `ai.careerpilot.memory.conversation` (conversation-derived decision extraction), and `ai.careerpilot.service.ConversationMemory` (Copilot chat history) are all untouched — this package is a parallel, broader classification system, not wired to read from or write into any of them.

`DefaultMemoryClassifier` (keyword rules, the same ML-swap-seam discipline as `ai.careerpilot.intent.KeywordIntentResolver`) assigns both a `MemoryType` and a `MemoryImportance` (score + CRITICAL/HIGH/MEDIUM/LOW band, same shape as `IntentConfidence`) to freshly-remembered content, landing anything unclassified in `WORKING` — the deliberately transient default. `DefaultMemoryConsolidator` is the working-memory → long-term lifecycle the spec asked for: a `WORKING` entry accessed at least `promotion-access-threshold` times gets promoted (re-classified, or generic `LONG_TERM` if still ambiguous) regardless of age; one that ages past `working-ttl-hours` without enough access is evicted outright; anything neither aged nor frequently accessed is left alone. `DefaultMemoryRetriever` marks every entry it returns as accessed, which is what actually feeds the consolidator's access-count rule — the two are deliberately coupled.

Entirely in-memory (`InMemoryMemoryStore`, an unbounded-until-capacity per-user map) — **no new Flyway migration**, matching the phase's "ZERO database breaking changes" requirement exactly; a future phase wanting durability would replace that one class only. `DefaultMemoryManager` enforces `max-entries-per-type` per user, evicting the single lowest-importance (oldest tie-break) entry of that type before a new one would exceed the cap — a bounded structure, not unbounded growth.

Single flag, same pattern as every prior Phase 11 sub-phase: `enterprise.memory.enabled` (default `false`, `EnterpriseMemoryConfig` the only bean source). Not wired into the Copilot, any controller, or any of the existing memory subsystems — `MemoryManager`/`MemoryRetriever`/`MemorySearch`/`MemoryConsolidator` are ready-to-wire but currently only reachable from tests.

Verified via `mvn test` (1962/1962, zero regressions — 1925 prior + 37 new), including a capacity-eviction test (lowest-importance entry evicted first when a type hits its cap), and dedicated consolidation tests for all four branches (frequent-access promotion, unclassifiable-content-falls-back-to-LONG_TERM, aged-and-unused eviction, fresh-and-unused left untouched).

### Phase 11.5 — Proactive Career Intelligence: read-only insight detection over existing data, still not scheduled or wired
`ai/careerpilot/career/monitor/` detects the 7 proactive-insight categories the phase spec names — new job matches, resume outdated, missing certifications, salary below market, promotion readiness, interview reminders, learning suggestions — as thin read-only wrappers around data that already existed before this phase, the same discipline as every Phase 10.2 MCP tool: `JobRecommendationRepository` (job matches), `ResumeRepository.createdAt` (resume staleness), `CareerStrategy.skillGapsJson`/`promotionReadinessJson` (learning/certification/promotion signals — presence-only, this package never parses that JSON's internal shape), `Offer.baseSalary` vs. `Offer.marketP50` (salary below market), `Interview.scheduledAt` (interview reminders). No new query beyond existing finder methods, no new table, no fabricated signal.

`CareerOpportunityDetector` covers job matches specifically; `CareerEventEngine` covers the other six — each check independently try/caught inside `DefaultCareerEventEngine`/`DefaultCareerMonitor` so one missing/absent data source (no resume, no career strategy row, no offer) simply produces no alert for that category rather than an error. `CareerTimeline` (in-memory, bounded per-user ring buffer, same shape as Phase 11.1's `InMemoryIntentHistory`) is what stops the same alert firing every run — `DefaultCareerMonitor` suppresses anything surfaced within `alert-cooldown-days` (default 7) before handing the rest to `CareerRecommendationEngine` for severity-ranked, capped prioritization.

Single flag, same pattern as every prior Phase 11 sub-phase: `career.monitor.enabled` (default `false`, merged into the pre-existing top-level `career:` YAML block rather than a duplicate root key — that block already holds `career.orchestrator.*`/`career.relevance.*`/etc. from earlier phases). Not wired into any scheduler or controller — compare to the already-shipped, already-wired `ai.careerpilot.dailydiscovery` package, which this does not replace or connect to.

One real bug caught by its own test suite: the resume-outdated and interview-reminder alerts originally built their `evidence` map with `Map.of(...)`, which throws `NullPointerException` on a null value — and entity ids are null for any not-yet-persisted row (every unit test, and potentially a real not-yet-flushed entity). Fixed with a null-tolerant `HashMap`-based helper.

Verified via `mvn test` (1994/1994, zero regressions — 1962 prior + 32 new).

### Phase 11.6 — Autonomous Career Agent: closes the Phase 11 series, task dispatch deliberately deferred
`ai/careerpilot/career/agent/` is the sixth and final sub-phase of the Phase 11 master plan. It closes the observe → plan → reflect loop: `AutonomousCareerAgent.runOnce(userId)` checks `TaskScheduler` for run eligibility (in-process cadence tracking, default 24h — not Spring's `@Scheduled`, nothing auto-triggers this), observes via Phase 11.5's `CareerMonitor` (`AgentObservation.from(CareerInsights)` — wraps its `recommendations()` directly, or an empty observation if that layer's own independent `career.monitor.enabled` flag is off or it throws), plans via `DefaultAgentPlanner` (a static `CareerAlertType → AgentTaskType` map, the same style as Phase 11.2's intent-to-capability mapping), dispatches each planned task, reflects, and remembers via `AgentMemory` (bounded per-user ring buffer, same shape as every other Phase 11 history component).

**Task dispatch is deliberately deferred, not real.** Every one of the 8 autonomous task categories the phase spec names already has a real, existing engine somewhere in this codebase — daily job discovery (`JobDiscoveryScheduler`/`DailyJobDiscoveryScheduler`), ATS resume optimization (Phase 2D.2), Phase 3A application tracking, interview planning (`InterviewService`/`StarStoryEngine`), career/learning roadmap generation, skill gap detection (`SkillGapIntelligenceService`), salary trend monitoring (`OfferAnalysisService`). Per the Phase 11 mission's explicit "DO NOT replace any existing subsystem," `DeferredAgentTaskExecutor` — the only `AgentTaskExecutor` shipped in this phase — always returns `TaskOutcome.DEFERRED` rather than calling any of them. The full loop is genuinely exercised end-to-end against real Phase 11.5 signals; only the final "actually do it" step is a documented placeholder, the same honesty discipline as `Context7ApiClient`'s "best-effort, not live-verified" caveat.

Single flag, gated the same way as every prior Phase 11 sub-phase: `career.agent.enabled` (default `false`, merged into the pre-existing top-level `career:` YAML block as a `agent:` sibling to `career.monitor.*`). Verified via `mvn test` (2020/2020, zero regressions — 1994 prior + 26 new). One flaky-test bug found and fixed during this phase: a `Duration.ZERO`-interval eligibility test raced against clock resolution (last-run and "now" landing in the same instant); fixed with a real `Thread.sleep` gap, not a production code change.

**Phase 11 is now complete**: Intent Engine (11.1) → Capability Planner (11.2) → Multi-Capability Execution (11.3) → Enterprise Memory Evolution (11.4) → Proactive Career Intelligence (11.5) → Autonomous Career Agent (11.6). Every sub-phase shipped dark-by-default, additive, and standalone-tested; none replaced an existing subsystem. Unlike Phase 10 (where 10.4 was the deliberate "connect it to production" phase), no Phase 11 sub-phase wires into the Copilot, a scheduler, or any controller — that remains open, deliberately, for a future phase.

### International Job Discovery Engine, Phase 1 — country-tier relocation program, dark by default
`ai.careerpilot.jobdiscovery.international` adds the first slice of a config-driven relocation-jobs program on top of the *existing* Domestic/International infrastructure (`JobProvider`, `JobScopeStrategy`, `JobMatchingService`/`JobScoring`) rather than rebuilding any of it — this phase is deliberately thin: seniority/title eligibility, curated country intelligence, a separate weighted ranking, and read-only endpoints/dashboard. A much larger spec (≈20 job sources, OpenSearch, Kafka events, a LangGraph/MCP surface, weekly reports, hexagonal rewrite) was scoped down after review: most of it either already exists in some form, is infeasible without scraping/ToS violations, or is genuine future-phase work — see "Out of scope" below.

**Config-driven country tiers** (`V69__international_country_tiers.sql`) — `supported_countries` (country_code, display_name, tier TIER_1/2/3, active), seeded for Germany/Netherlands (Tier 1), Ireland/Canada/Australia (Tier 2), Luxembourg (Tier 3). `SupportedCountryService` is a second, independent gate from the existing `InternationalScopeStrategy` (which answers "which countries can *this candidate* see," from their profile) — this one answers "is this country part of the Phase-1 program at all." Future countries (USA, Singapore, Japan, etc.) are a data-only row insert, never a code change. Every method on `SupportedCountryService` returns the empty/false case when `career.international.tiering.enabled` is off (default), matching this codebase's "master switch = byte-identical no-op" convention — including the read-only `/api/jobs/international/countries`/`/intelligence` endpoints.

**Seniority + title eligibility** — `SeniorityLevelClassifier` (reuses the existing `JobTaxonomy.seniorityLevel`, no new title-parsing logic) accepts SENIOR/LEAD/PRINCIPAL and rejects an explicit intern/junior/graduate/trainee/contract/part-time list; `InternationalRoleTaxonomy` holds the program's fixed 27-title allow-list (whole-word-or-role-family match, same style as `RoleExclusionFilter`). `InternationalEligibilityFilter` combines both behind two independent flags (`career.international.seniority-filter.enabled` master, `career.international.title-allowlist.enabled` the more aggressive sub-gate) and is wired as one more no-op-when-off `.filter()` stage into `JobMatchingService.refreshForUser`'s existing chain and `JobService.discovered`'s existing scope-aware post-filter pattern — zero change to either when the flag is off.

**Country Intelligence** (`V70__country_intelligence.sql`) — `country_intelligence`: nine curated 0–100 scores per country (visa probability, relocation difficulty, language requirement, cost of living, expected savings, job stability, tech market, principal-engineer growth, AI market) plus a `source_note` provenance column. **Explicitly static/curated, not live-computed** — there's no real data source for e.g. live visa-approval probability; values are placeholder-but-defensible and should be reviewed against real published indices before being relied on for a real decision.

**International ranking** (`V71__international_job_ranking.sql`) — `InternationalJobScoring` implements the program's exact weighted formula (40% skill / 15% visa probability / 10% salary / 10% career growth / 10% company stability / 5% remote flexibility / 5% principal-engineer growth / 5% AI tech stack), deliberately separate from `JobScoring.scoreV2`'s own weights (40/25/20/10/3/1/1) and written to a **new parallel table** rather than new columns on `job_recommendations` — two independently-weighted formulas for two different purposes (relocation viability vs. general job fit) stay structurally independent. `JobScoring` gained two new `public` (previously private/inline) helpers, `skillScoreOnly(...)` and `salaryScore(...)`, extracted with zero behavior change to `scoreV2` itself (verified: the full pre-existing `JobScoring`/`JobMatchingService` test suite stayed green after the extraction) — `InternationalJobScoring` reuses these rather than duplicating the logic. `InternationalJobRankingService` mirrors `JobMatchingService.refreshForUser`'s shape and rides the *same* refresh trigger points (`JobRecommendationService.rebuild()` and the page-0 implicit refresh in `recommend()`), try/catch isolated so a ranking failure never blocks the existing recommendation refresh. **Depends on two flags, not one**: `career.international.ranking.enabled` gates the write path itself, but `SupportedCountryService#byDisplayName` (used to resolve each candidate country into a Phase-1 row) also requires `career.international.tiering.enabled` — both must be on before this service writes anything, the same layered pattern as Phase 2D's `<stage>.enabled` + `<stage>.trigger.enabled`.

**Providers** — `AdzunaProvider` gained `ie` (Ireland) to its country-name/currency maps and its default country list (`gb,us,in,ie,au`); Luxembourg has no Adzuna coverage and ships thin in Phase 1 (documented gap, no fabricated endpoint). Three new dark-stub providers — `LinkedInProvider`/`IndeedProvider`/`GlassdoorProvider` — are exact structural copies of the existing `TaleoProvider` convention: `isConfigured()` is permanently `false` (none of the three has a free/ToS-compliant public search API — scraping any of them violates their ToS), with a diagnostics-only `isFlagEnabled()` mirroring the flag without ever affecting `isConfigured()`.

**New read-only API** — `InternationalJobController` (`/api/jobs/international/{countries,intelligence/{code},ranked,dashboard}`), entirely additive; `GET /api/jobs/discovered` and `GET /api/jobs/recommended` are untouched byte-for-byte. `/ranked` composes (never replaces) the existing job shape with the new ranking + country-intelligence data and returns an empty page rather than erroring when the ranking flag is off or the user has no rows yet. `/dashboard` (`InternationalDashboardService`) is plain in-memory aggregation over the current user's own `international_job_ranking` rows plus their jobs/applications — not a new analytics pipeline.

**Frontend** — `PreferencesDialog.tsx` gained a tier-grouped country picker (click-to-add into the existing free-text `preferredCountries` field) sourced from `/countries`; `JobBadges.tsx` gained `CountryTierBadge`/`SeniorityBadge`; `ExplainDialog.tsx`'s existing "why am I a match" panel now additionally renders a compact country-intelligence block when ranking data exists for that job's country (conditional, no change to the domestic-path rendering). New page `InternationalDashboard.tsx` (route `/jobs/international/dashboard`, linked from the International tab header) reuses the exact Recharts + CSS-variable-token styling already established in `Dashboard.tsx` — no new charting library, no new design tokens.

**Flags** (all new, all default `false`): `career.international.tiering.enabled`, `career.international.seniority-filter.enabled`, `career.international.title-allowlist.enabled`, `career.international.ranking.enabled`, `career.discovery.linkedin.enabled`/`indeed.enabled`/`glassdoor.enabled` (the last three diagnostics-only).

**Out of scope for Phase 1** (deferred to future, separately-requested phases): real LinkedIn/Indeed/Glassdoor integration (never planned — ToS-prohibited, stubs stay dark permanently); a generic Personio/Recruitee crawler; OpenSearch-based faceted search/heatmaps (pgvector + Postgres suffice at Phase 1 scale); new Kafka event types for discovery milestones; a LangGraph/MCP-exposed agent or tool surface for the international engine; weekly email/notification reports (would reuse `DailyCareerSummaryGenerator`'s existing pattern rather than a new pipeline); admin CRUD UI for `supported_countries`/`country_intelligence` (read-only + migration-seeded in Phase 1); a candidate-side "relocation support required" preference (Phase 1 relies solely on the existing job-side `relocation_support` boolean); expansion beyond the 6 seeded countries.

Verified via `mvn test` (2043/2043, zero regressions — 2022 prior + 21 new) and `npx tsc --noEmit` + `npx vitest run` (frontend, zero errors). Live-verified end-to-end: `docker compose build backend` initially silently failed on the recurring `docker-credential-desktop` PATH bug (same fix as documented elsewhere in this file — remove `credsStore` from `~/.docker/config.json`) and produced a stale image missing the new migrations without the compose command reporting a nonzero exit — always verify a freshly-built image actually contains new migration files (`docker run --rm --entrypoint sh <image> -c "unzip -l /app/app.jar | grep db/migration"`) before trusting a "successful" build. Once rebuilt correctly, Flyway applied V69–V71 cleanly on the live Neon database; with all flags at default `false`, `/api/jobs/international/countries` returns `[]` and `/dashboard`/`/ranked` return empty/zero — confirmed byte-identical to off; with `career.international.tiering.enabled=true`, `/countries` returned the 6 seeded countries with correct tiers and `/intelligence/de` returned real seeded scores, `/intelligence/xx` correctly 404'd.

### Frontend data flow
[lib/api.ts](frontend/src/lib/api.ts) is a single axios instance with a bearer-token request interceptor (reading from the zustand store in [lib/auth.ts](frontend/src/lib/auth.ts)) and a 401-→-logout response interceptor. Auth state persists to localStorage via zustand's `persist` middleware. Server state uses TanStack Query — refetches are explicit (`queryClient.invalidateQueries`) after mutations; there is no SSE/WebSocket, so the Workflow page only updates on user action.

## Provisioned-but-unused (do not assume these are integrated)

Knowing what is *not* wired prevents wasted debugging:
- `refresh_tokens` table — no `/api/auth/refresh` endpoint exists
- `audit_logs` table — no code writes to it
- `usage_records` table — no code writes to it; cost tracking is not aggregated
- `embedding` vector columns — no embedding generation anywhere (pgvector extension is installed, but no HNSW/IVFFlat indexes)
- Redis — `spring-boot-starter-data-redis` on the classpath, no `@Cacheable` / `RedisTemplate` usage
- `careerpilot.audit.events` topic — declared in config, neither produced nor consumed
- `security.rate-limit.*` values — read by no limiter (no Bucket4j / RedisRateLimiter)
- `@KafkaListener` — zero consumers exist; producer events go nowhere
- `refresh_tokens` table — exists but no refresh endpoint wired
- `AdaptiveRecommendationEngine.getBoost()` (`learning/recommendation/`) — computed and persisted end-to-end, but not called by `JobScoring`/`JobMatchingService`; live job matching does not use outcome-based learning today despite the pipeline existing

When in doubt, grep for the symbol — if it has no callers, it is scaffolding.

## Diagnostics and Monitoring

[DiagnosticsController.java](backend/src/main/java/ai/careerpilot/api/DiagnosticsController.java) exposes two public endpoints (no auth required) for troubleshooting:

- **`GET /api/diagnostics/ai`** — Gateway diagnostics: API keys loaded, configured models, base URLs, provider health (UP/DOWN/NOT_CONFIGURED), provider order, call stats (total calls, fallbacks, failures per provider), default temperature.
- **`GET /api/diagnostics/workflow`** — Workflow engine diagnostics: workflowEngine/jsonSerialization/agentService status, plus provider chain health. Used to validate that all three services and the provider chain are operational after deployment.

These endpoints are **not guarded by auth** (anyone can call them) to enable uptime monitoring without needing credentials.

Most later phases ship their own narrower diagnostics controller rather than extending `DiagnosticsController` — e.g. `ExecutionDiagnosticsController` (execution/recovery/operations), `PipelineDiagnosticsController` (gap-analysis/ATS-explainability/cover-letter/application-package/auto-apply-package). Before adding a new admin/ops surface, check whether it belongs on one of these existing controllers instead of a new one — `frontend/src/pages/OperationsCenter.tsx` (admin-only route) already aggregates execution/retry/recovery data this way and is the pattern to extend, not duplicate, for any future ops dashboard work.

## Conventions

- Java package root is `ai.careerpilot`. Sub-packages are role-based: `api` (controllers + DTOs), `service`, `repo`, `domain` (JPA entities), `security`, `kafka`, `storage`, `ai`, `agent`, `config`.
- Python agents live one-file-per-agent under `agent-service/app/agents/`. Each exports a single `<name>_node(state) -> dict` function; the dict is shallow-merged into `CareerState` by LangGraph.
- New backend endpoints accept `AuthenticatedUser` as a method parameter (see any existing controller) — this is how you get `userId`/`orgId`.
- Frontend pages live under `src/pages/`, one file each. Routes are registered in [App.tsx](frontend/src/App.tsx) inside the `<Private>`-guarded `<Layout>`.
