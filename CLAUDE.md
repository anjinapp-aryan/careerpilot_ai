# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project shape

CareerPilot AI is a three-service monorepo: a **Spring Boot 4 / Java 25 backend** (`backend/`) acts as the control plane, a **Python FastAPI + LangGraph 0.2 agent service** (`agent-service/`) hosts the multi-agent workflow, and a **React 18 + Vite + TS frontend** (`frontend/`) is the UI. They share **one PostgreSQL** database (currently a **Neon serverless** instance, external to docker-compose — see `.env`) with the pgvector extension — backend persists domain data, agent-service persists LangGraph checkpoints into the same DB. Redis, Kafka, and MinIO/S3 run in `docker-compose.yml`.

The backend has grown well past its original vertical slice into ~30 role-based packages (job discovery, resume tailoring, execution/browser automation, workflow tracking, learning, autopilot, company intelligence, career-goal intelligence, etc. — see "Architecture" below for the ones with non-obvious cross-file shape). The great majority of that surface still ships **dark by default** behind independent `*.enabled` feature flags — a package existing, or even having a REST controller, is not evidence it's live in production. Several tables and beans are also intentionally provisioned-but-unwired (see "Provisioned-but-unused" below).

**This is a live production system** at https://careerpilot-ai.duckdns.org/ (backend on an Oracle Cloud VM, frontend on Vercel) — treat backend/infra changes with the caution that implies; see "Deployment" below before touching `docker-compose.yml`, the `Dockerfile`, or anything under `deployment/`.

To **launch and smoke-test the whole stack from scratch**, use the `run-careerpilot-ai` skill ([.claude/skills/run-careerpilot-ai/SKILL.md](.claude/skills/run-careerpilot-ai/SKILL.md)): `docker compose --env-file .env up -d`, then drive it with `node .claude/skills/run-careerpilot-ai/driver.mjs --e2e` — a zero-dependency HTTP harness that probes all three services and runs a real register→login→dashboard→create-job flow against the live backend + Neon.

## Commands

### Run the whole stack (preferred)
`docker-compose.yml` at the repo root is now **hardened for the Oracle Cloud VM production deploy** (`SPRING_PROFILES_ACTIVE=prod`, no host ports published for `redis`/`kafka`/`minio`/`zookeeper` — only the backend can reach them internally). Running it bare on a dev machine works but hides those services from the host and disables Swagger. For local dev, layer the local-dev overlay on top:
```bash
cp .env.example .env
# Set: JWT_SECRET (>=32 chars), GEMINI_API_KEY, and your Neon DATABASE_URL/DATABASE_URL_PY
docker compose --env-file .env -f docker-compose.yml -f docker-compose.local.yml up --build
```
[docker-compose.local.yml](docker-compose.local.yml) restores host access to redis/kafka/minio and other local-dev conveniences that were intentionally stripped from the base file for the VM deploy. **Never apply this overlay on the production VM** — the VM runs `docker-compose.yml` alone.

Frontend on http://localhost:5173, backend on http://localhost:8080 (Swagger at `/swagger-ui.html`), agent service on http://localhost:8088 (`/docs`), MinIO console on http://localhost:9001.

**Postgres lives outside docker-compose** (Neon serverless). The two `DATABASE_URL` forms in `.env` must use Neon's **direct** endpoint (no `-pooler` in hostname) — Flyway DDL and the LangGraph `PostgresSaver` both rely on prepared statements that break under Neon's transaction-mode pgBouncer pooler. Going back to a local Postgres container is documented as a comment block at the top of `.env.example`.

### Production deployment
**[DEPLOYMENT_ORACLE_CLOUD.md](DEPLOYMENT_ORACLE_CLOUD.md) is the authoritative production architecture doc** (single Oracle Cloud VM, `docker-compose.yml` at the repo root, frontend on Vercel separately) — it explains *why* the VM/network/systemd pieces are shaped as they are; the day-to-day *how* (setup, redeploy, rollback, backup, health checks) is the operational runbook at [deployment/README.md](deployment/README.md). [DEPLOYMENT.md](DEPLOYMENT.md) (Render + Vercel + Neon, free-tier demo) and [DEPLOYMENT_CLOUDRUN.md](DEPLOYMENT_CLOUDRUN.md) (Cloud Run, backend-only alternative) are earlier/alternative deploy targets — not what's currently serving production traffic; don't merge their instructions with the Oracle Cloud path.

The backend `Dockerfile`'s `JAVA_OPTS` includes `-XX:MaxMetaspaceSize=320m` — a previous value of `160m` caused a real production crash-loop (Metaspace OOM under sustained uptime) on the Oracle VM. Don't lower it without checking VM RAM headroom against the other containers sharing that host.

**Measured production VM facts** (taken 2026-08-03 via `ssh opc@152.67.2.17`; the repo previously stated RAM three different ways — 5.5 GB in `backend/Dockerfile`, 4 GB here, 3 GB in a phase brief — so treat these as the authority):

| Fact | Value | Why it matters |
|---|---|---|
| Total RAM | **5.5 GiB** (2.5 GiB available) | RAM is *not* the binding constraint; earlier 3 GB sizing was too pessimistic |
| **vCPUs** | **1** | **The real constraint.** Chromium rendering/JS is CPU-bound; one core is shared with the JVM, Kafka, ZK and uvicorn |
| Architecture | **aarch64 (ARM64)** | Playwright ships no `linux-arm64` Chromium — distro Chromium via `setExecutablePath`/`setChannel` is mandatory, not optional |
| Swap | 4 GiB (554 MiB in use) | Swap *does* exist, contrary to earlier notes — but on 1 vCPU, swap thrash is effectively an outage |

Measured per-container memory: backend 621 MiB, **kafka 768 MiB**, **zookeeper 372 MiB**, minio 101 MiB, agent-service 36 MiB, redis 10 MiB, frontend 1 MiB (~1.9 GiB total; the remaining ~1.2 GiB of the 3.1 GiB used is host OS + Nginx + dockerd). **Kafka + ZooKeeper together consume 1.11 GiB — roughly 20% of the box — while this codebase has zero `@KafkaListener` consumers** (see "Provisioned-but-unused"), so every event produced goes nowhere. That remains the single largest available memory recovery.

Note the interaction with `-XX:MaxRAMPercentage=50` and the fact that **no service in `docker-compose.yml` has a `mem_limit`**: with container support seeing the whole 5.5 GiB host, the backend JVM's max heap ceiling is ~2.75 GiB even though it currently uses 621 MiB. If it ever expands toward that ceiling while a browser is running, the box goes to swap on a single core. An explicit `-Xmx` plus per-service `mem_limit`s should land before browser automation is enabled.

## Architecture — the things you need to read multiple files to see

### The LangGraph workflow is the heart of the product
[agent-service/app/graph.py](agent-service/app/graph.py) defines a single linear `StateGraph` over `CareerState` ([state.py](agent-service/app/state.py)) with these nodes in order: `resume_intelligence → job_discovery → ats_optimization → interview_prep → career_strategy → salary_intelligence → human_approval → application_tracking`. The shared `CareerState` TypedDict is the contract — each agent reads inputs from prior nodes' outputs and writes its own keys. When extending: add the node to `graph.py`, define inputs/outputs in `state.py`, place the agent under `app/agents/`.

The `human_approval` node uses `raise NodeInterrupt(...)` ([agents/human_approval.py](agent-service/app/agents/human_approval.py)) to pause the graph. The FastAPI `/runs` endpoint catches the interrupt and returns `status="interrupted"` to the backend; `/runs/resume` calls `graph.update_state(...)` + `graph.invoke(None, ...)` to continue. A conditional edge `_route_after_approval` routes `human_approval → application_tracking` on approval or `→ END` on rejection.

**Resuming a run is only valid while it's parked at `human_approval`.** [main.py](agent-service/app/main.py) checks `"human_approval" not in graph.get_state(cfg).next` and returns HTTP 409 if the run isn't currently awaiting approval; [WorkflowService.resume()](backend/src/main/java/ai/careerpilot/service/WorkflowService.java) mirrors this with its own guard (`deriveDisplayStatus(run) != "INTERRUPTED"` → `IllegalStateException` → 409) before even calling the agent. This double guard exists because resuming an already-terminal run (e.g. approving a run that was already rejected) silently corrupts its terminal state — don't remove either check independently.

State survives restarts via `PostgresSaver` (langgraph-checkpoint-postgres). `saver.setup()` in `_checkpointer()` is idempotent and creates the `checkpoints*` tables in the shared Postgres on first run — these are **not** in Flyway, they're owned by LangGraph.

### Two AI seams, no longer symmetric — read both before touching either
Each service has its own provider abstraction, and they have diverged. Do **not** assume they mirror each other.

**Java side — a multi-provider AI Gateway with health tracking and transparent failover.** [AiGatewayService.java](backend/src/main/java/ai/careerpilot/ai/AiGatewayService.java) is the single entry point for all AI in the backend; business services depend on it, never on a concrete provider. It routes each call through a configured provider order (default `deepseek,qwen,gemini`) with **automatic transparent failover**: 
- **Blocking calls** (`chat()`, `generateFeedback()`, etc.) fail over before returning if the primary provider fails.
- **Streaming calls** (`streamChat()`) fail over only *before the first token* — once tokens emit, failover is impossible (client already receiving from that provider).
- **Quota detection**: HTTP 429 errors trigger immediate failover without exhausting retries ([QuotaExceededException.java](backend/src/main/java/ai/careerpilot/ai/QuotaExceededException.java)).
- **Health tracking**: [ProviderHealthTracker.java](backend/src/main/java/ai/careerpilot/ai/ProviderHealthTracker.java) caches provider health (HEALTHY/DEGRADED/QUOTA_EXCEEDED/UNKNOWN) with 5-minute TTL to avoid repeated calls to failed providers.
- **Per-provider resilience**: Resilience4j **retry + circuit breaker** + usage metrics ([AiMetrics.java](backend/src/main/java/ai/careerpilot/ai/AiMetrics.java)).

Every provider implements [LlmProvider.java](backend/src/main/java/ai/careerpilot/ai/LlmProvider.java) (shared logic in `AbstractLlmProvider`); impls live under `ai/provider/` — `GeminiProvider`, `NvidiaDeepSeekProvider`, `NvidiaQwenProvider` (the two NVIDIA ones extend `AbstractOpenAiChatProvider` since NVIDIA's API is OpenAI-compatible). A provider only joins the chain when `isConfigured()` is true, so DeepSeek/Qwen are skipped unless `NVIDIA_API_KEY` is set. 

**Streaming provider callback**: When calling `streamChat(messages, system, providerCallback)`, pass a `Consumer<String>` to learn which provider actually served the response (useful for frontend attribution). The callback fires in the `doOnComplete()` handler, *after* the stream succeeds. This replaced ThreadLocal tracking, which didn't survive Reactor's async thread boundaries.

**Adding a provider** = one new `LlmProvider` impl + listing its key in `ai.gateway.order` — no business-logic changes.

**Python side — a single rate-limited Gemini provider.** [agent-service/app/ai_provider.py](agent-service/app/ai_provider.py) keeps the four-method contract (`generate_response`, `generate_structured_response`, `generate_json`, `estimate_cost`), but agents must obtain it via `get_ai_provider()`, which returns a `RateLimitedAIProvider` decorator wrapping `GeminiProvider`. The decorator delegates to a process-wide singleton `GeminiRateLimiter` ([rate_limiter.py](agent-service/app/rate_limiter.py)) that enforces RPM + TPM token buckets, minimum request spacing, and full-jitter retry on 429/503 — all 8 agents share one limiter. Counters are exposed at `GET /metrics`. **Never instantiate `GeminiProvider` directly in an agent** (it's intentionally retry-free) and never touch `google.generativeai` directly — go through `get_ai_provider()`.

The Python `GeminiProvider` uses `responseSchema` for structured output — every agent passes a JSON Schema and the provider calls `genai.GenerativeModel(...).generate_content(..., generation_config={"response_mime_type": "application/json", "response_schema": SCHEMA})`. Don't switch agents to free-text parsing; the schema is what keeps outputs typed.

### The Copilot is a separate, streaming AI surface (not the LangGraph workflow)
Distinct from the backend→agent-service workflow path: the backend hosts its own conversational copilot under `/api/copilot` ([CopilotController.java](backend/src/main/java/ai/careerpilot/api/CopilotController.java)), which **streams tokens over SSE** (`POST /api/copilot/stream`, `text/event-stream` via `SseEmitter`) plus `GET /conversations` and `GET /conversations/{id}/messages`. [CopilotService.java](backend/src/main/java/ai/careerpilot/service/CopilotService.java) calls `AiGatewayService.streamChat(messages, system, providerCallback)` to capture which provider served the response; the callback executes after streaming completes and stores the provider name in an `AtomicReference` that the SSE done event sends to the frontend. [AgentOrchestrator.java](backend/src/main/java/ai/careerpilot/service/AgentOrchestrator.java) builds the per-page/per-action system prompt + context block, and [ConversationMemory.java](backend/src/main/java/ai/careerpilot/service/ConversationMemory.java) persists turns via `CopilotConversationRepository`/`CopilotMessageRepository` (tables from `V2__copilot.sql`). The frontend consumes this through `lib/copilotStream.ts` + `components/copilot/CopilotPanel.tsx`. `GET /api/diagnostics/ai` and `GET /api/diagnostics/workflow` ([DiagnosticsController.java](backend/src/main/java/ai/careerpilot/api/DiagnosticsController.java)) expose gateway provider health and call/fallback metrics plus workflow engine status.

**Copilot prompts are skill-routed, not one monolithic prompt.** [CopilotSkillRouter.java](backend/src/main/java/ai/careerpilot/service/copilot/CopilotSkillRouter.java) maps each request to one of 10 `CopilotSkill` enum values — by explicit `action` if the frontend sent one, else by keyword-matching the free-text `message` (`inferSkillFromMessage`), else falling back to `GeneralAssistantHandler`. Each skill is a `CopilotSkillHandler` impl under `service/copilot/skill/` (e.g. `WorkflowExplanationHandler`, `AtsAnalysisHandler`, `ResumeAnalysisHandler`) extending `AbstractSkillHandler`, with three jobs: `assembleContext()` pulls RAG data via [CareerContextRetriever.java](backend/src/main/java/ai/careerpilot/service/CareerContextRetriever.java) into a `SkillContext`, `systemPrompt()` returns the skill-specific instructions, `contextBlock()` renders that data as the prompt's context section. Adding a new skill = new `CopilotSkill` enum value + new handler class + wiring it into `CopilotSkillRouter`'s constructor map.

### Phase 11A — Copilot Context Expansion: cross-subsystem awareness, still additive
Before this phase, an audit (grep-confirmed) found the Copilot's per-skill RAG context — [CareerContextRetriever.java](backend/src/main/java/ai/careerpilot/service/CareerContextRetriever.java) plus the 27 skill handlers — never touched `CareerMission`/`MissionOrchestratorService` (Mission Engine), `CareerTimelineService` (Phase 10H), `InterviewRepository`/`InterviewService`, `ApplicationTimelineRepository`, or any analytics service; only Candidate Profile and top-N Career Decision Memory were wired centrally, and only Company Intelligence had per-skill handlers. [CareerContextService.java](backend/src/main/java/ai/careerpilot/service/CareerContextService.java) closes that gap the same way those two precedents were built: **one new additive read-side aggregator**, not a rewrite of `CareerContextRetriever` and not a new API — it composes exclusively from already-existing repositories/services (`CareerMissionRepository`+`MissionOrchestratorService`, `CareerTimelineService`, `WorkflowRunRepository`+`WorkflowService.deriveDisplayStatus`, `ApplicationRepository`+`ApplicationSubmissionSessionService` for the Phase 2E `WAITING_MANUAL_SUBMISSION` state, `InterviewRepository`+`InterviewService`, `CompanyKnowledgeRepository`+`CompanyKnowledgeService`), never a new query, new table, or new AI call.

Every one of the 7 sections (`mission`, `recentTimeline`, `workflow`, `applications`, `interviews`, `topCompanies`, `analyticsNote`) is independently try/catch isolated (`safely(...)`, mirroring `CareerTimelineService`'s own per-source isolation) so one missing/misconfigured subsystem degrades only that section to `null`/empty, never the whole turn. Subsystems with their own dark-by-default flag are consulted through that subsystem's own `isEnabled()`/flag-checked read path (`CareerTimelineService.isEnabled()`, `InterviewService.isEnabled()`, `CompanyKnowledgeService.isEnabled()`, `ApplicationSubmissionSessionService.isEnabled()`) — `CareerContextService` never bypasses those flags itself. `ApplicationAnalytics`/`CareerIntelligence` are append-only numeric snapshot series with no discrete "score improved" event anywhere in this codebase (same finding CLAUDE.md's Career Timeline section already documents) — `analyticsNote()` never synthesizes a trend narrative, only a real snapshot count or an explicit "No verified historical trend available."

Wired into [CopilotService.java](backend/src/main/java/ai/careerpilot/service/CopilotService.java) with the exact same centralized pattern as candidate-profile/career-memory context: gated by its own flag (`copilot.career-context.enabled`, default `false`, inline `@Value`, no `application.yml` entry), populated once per turn regardless of which skill handled it, rendered via a new `SkillContext.careerContextBlock()` and appended to every handler's `contextBlock()` output — no individual skill handler was touched. With the flag off, byte-for-byte unchanged from pre-Phase-11A behavior.

Verified via `mvn test` (2290/2290 — 2260 prior + 30 new, including `CareerContextServiceTest`'s per-source isolation tests: each section independently absent/disabled/throwing without affecting the others).

### Phase 11B — Copilot Intelligent Actions: a deterministic priority engine, one new cross-system skill
Phase 11A gave every skill access to cross-subsystem data; Phase 11B turns that data into ranked, actionable next steps without ever letting the LLM invent the ranking. [RecommendedActionEngine.java](backend/src/main/java/ai/careerpilot/service/RecommendedActionEngine.java) is a pure, stateless, deterministic (no LLM, no repository access) rule ladder — same discipline as `MissionOrchestratorService.decide`/`CountryMatchingCapability`/`StrategyEvaluationService` — over an **already-built** `CareerContextService.CareerContext`: manual-submission-waiting (priority 1) → upcoming interview (2) → workflow awaiting approval (3) → mission-orchestrator recommendations (4) → failed workflow runs (5) → rejected applications (6). A signal this engine has no real data source for (e.g. resume staleness) is simply absent as a rule rather than approximated — same "don't invent a rule for missing data" discipline as everything else in this codebase.

`CareerContextService.getCareerContext` now derives `recommendedActions` from the sections it already fetched in the same call — **zero additional queries**, confirmed by `CareerContextServiceTest`'s `recommendedActions_derivedFromSameAggregationCallNoExtraQueries` test asserting each underlying repository call happens exactly once. `SkillContext.careerContextBlock()` renders the ranked list under a new "RECOMMENDED ACTIONS" section with an explicit instruction not to reorder or invent additional actions — this section is appended to **every** skill's prompt (not just the new one) whenever `copilot.career-context.enabled` is on, so any existing skill's answer can now reference verified priorities for free.

One new flagship skill, `DAILY_PRIORITY_BRIEFING` (`CopilotSkill`/`DailyPriorityBriefingHandler`), answers the phase's own worked example — "what should I do today", "what's blocking my mission", "top priority", "daily briefing" — routed via 6 new keyword rules checked first in `CopilotSkillRouter.inferSkillFromMessage` (specific enough not to collide with any existing skill's keywords; a `CopilotSkillRouterTest` — the first for this router — pins both the new routes and 5 existing routes as regression coverage). Unlike other handlers, `DailyPriorityBriefingHandler.contextBlock()` is deliberately thin — it points at the same `careerContextBlock()` every other skill already renders — and its `assembleContext()` calls `CareerContextService` directly so the briefing works even with the global `copilot.career-context.enabled` flag off (a bounded, harmless double-fetch if the flag is also on). Its system prompt hard-requires the literal fallback string `"I don't currently have verified information to build a priority briefing."` when the context is empty — never a guess.

No new endpoint, DTO, table, or migration. `CareerContext`'s new `recommendedActions` field is additive to the record (existing 7 fields unchanged in order and meaning); all 29 pre-existing skill handlers, `CopilotSkillRouter`'s existing routing, and `CareerContextService`'s Phase 11A behavior are untouched. Verified via `mvn test` (2314/2314 — 2290 prior + 24 new: `RecommendedActionEngineTest`'s priority-ladder tests, the extended `CareerContextServiceTest`, `DailyPriorityBriefingHandlerTest`, and `CopilotSkillRouterTest`).

### Backend → agent-service boundary
[WorkflowService.java](backend/src/main/java/ai/careerpilot/service/WorkflowService.java) is the only caller of the agent service. It owns:
- assembling the LangGraph input from a `Resume` row + `Job` rows
- calling `AgentServiceClient` (a `WebClient` wrapper, [agent/AgentServiceClient.java](backend/src/main/java/ai/careerpilot/agent/AgentServiceClient.java))
- persisting/upserting a `WorkflowRun` row keyed by the LangGraph `thread_id` on every transition
- publishing a Kafka event via `WorkflowEventProducer` on every state change
- **converting entity responses to DTOs** via `toResponse(WorkflowRun)` for proper JSON serialization

**DTO pattern for API responses**: Controller methods must return `WorkflowRunResponse` (defined in [WorkflowDtos.java](backend/src/main/java/ai/careerpilot/api/dto/WorkflowDtos.java)), not the raw `WorkflowRun` entity. The DTO uses `Map<String, Object>` for state instead of `JsonNode`, which avoids Jackson type definition errors. The service layer parses the entity's JSON state string into a Map before constructing the DTO. This pattern should be replicated for any entity with complex JSON fields.

**`deriveDisplayStatus(WorkflowRun)` is the single source of truth for lifecycle status** — it derives the per-stage agent timeline from the run's JSON `state` blob and computes the displayed status (`RUNNING`/`INTERRUPTED`/`REJECTED`/`COMPLETED`/`FAILED`) from that timeline rather than trusting the raw persisted `status` column, which can lag. Both `WorkflowController` responses and `CareerContextRetriever.getWorkflowContext()` (used by the Copilot) call this same method, so the UI and the AI assistant can never disagree about a run's state. Approval/rejection audit fields (`approved_by`/`approved_at`/`rejected_by`/`rejected_at`/`human_feedback`) are stamped into that same `state` JSON blob in `mergeResponse()` — there's no separate audit table or migration for them.

When you add a new workflow surface (e.g., re-run, branch), funnel it through this service — do not expose the agent service to the frontend.

### JWT auth carries multi-tenant context
[JwtService.java](backend/src/main/java/ai/careerpilot/security/JwtService.java) packs `userId`, `orgId`, `email`, `role` into the access token. [JwtAuthFilter.java](backend/src/main/java/ai/careerpilot/security/JwtAuthFilter.java) extracts them into an `AuthenticatedUser` record placed in the security context, and [CurrentUserResolver.java](backend/src/main/java/ai/careerpilot/security/CurrentUserResolver.java) exposes it as a controller method parameter. Multi-tenant isolation is enforced **manually** in each service via `userId.equals(entity.getUserId())` checks — there is no row-level security and no Hibernate `@Filter`. New endpoints must replicate this pattern.

`@EnableMethodSecurity` is on, but **no controller uses `@PreAuthorize`**. Anyone authenticated can hit any endpoint. Be aware when adding admin-only routes.

### Database is shared but logically partitioned
[V1__init.sql](backend/src/main/resources/db/migration/V1__init.sql) creates 9 tables owned by the backend (Flyway-managed, Hibernate runs in `validate` mode), and [V2__copilot.sql](backend/src/main/resources/db/migration/V2__copilot.sql) adds the copilot conversation/message tables. The LangGraph checkpoint tables are auto-created by `PostgresSaver.setup()` and are **not** in Flyway. If you add new tables for the backend, write the next migration (`V3__*.sql`); never modify an applied migration. `flyway.baseline-on-migrate: true` is set in `application.yml`, so Flyway will baseline against the existing Neon schema state on first boot if `flyway_schema_history` is missing — useful because V1 may have been applied manually in the Neon SQL editor.

pgvector extension is enabled and `vector(768)` columns exist on `resumes.embedding` and `jobs.embedding`, but **no code path generates embeddings**. If you wire embeddings, the `AiGatewayService` is the right seam, and you'll need an HNSW/IVFFlat index — none exist today.

### Job discovery is a global pool, layered on top of org-scoped jobs
[jobdiscovery/](backend/src/main/java/ai/careerpilot/jobdiscovery/) ingests real listings from external sources and keeps them separate from the existing org-scoped Browse/Add-job/Apply flow on the same `jobs` table — discovered rows have `org_id IS NULL` and `source`/`external_id` set; manually-added jobs have `external_id IS NULL` and are untouched by any of this. `V4__job_discovery.sql` adds the discovery columns plus `job_recommendations` and `job_fetch_audit` (applied by hand against Neon — see the migration's own header comment, same baseline-on-migrate caveat as V1).

- **Providers** (`jobdiscovery/provider/`) implement `JobProvider` (`name()`, `isConfigured()`, `fetch() -> List<RawJob>`) — same "joins the chain only if configured" convention as `LlmProvider`. `AdzunaProvider`/`JoobleProvider` are keyed (skipped without API keys); `RemoteOkProvider`/`ArbeitnowProvider` are keyless and always on. `AbstractWebJobProvider` holds the shared `WebClient` fetch/parse boilerplate.
- **`JobAggregationService.discoverAll()`** is the orchestrator: for each configured provider, fetch → `JobNormalizer.toJob()`/`.merge()` → upsert into `jobs` deduped on `(source, external_id)`, recording one `JobFetchAudit` row per provider. A provider failure is isolated (FAILED audit row, run continues) — it never throws to the caller. `JobDiscoveryScheduler` runs this daily at 06:00 (`jobs.discovery.cron`), gated by `jobs.discovery.enabled`; `JobController`'s `POST /api/jobs/discovery/run` triggers it manually and `GET /api/jobs/discovery/audit` reads the audit trail.
- **`JobMatchingService.refreshForUser()`** is a separate, rule-based (no LLM) matcher: scores the discovered pool via `JobScoring` and upserts the top 50 into `job_recommendations` so the Recommended tab is a cheap indexed read. It is **source-agnostic** — the candidate signals (skills/target role/locations/experience/preferences/excluded roles) come from **[CandidateSignalResolver.java](backend/src/main/java/ai/careerpilot/jobdiscovery/CandidateSignalResolver.java)**, which is the Phase-1 single-source-of-truth switch: when `jobs.matching.profile-source-enabled=true` and a `candidate_profiles` row exists, every signal is read from the **canonical `CandidateProfile` only**; otherwise it falls back to the legacy `WorkflowRun` state + live `candidate_preferences` path (pre-Phase-1 behavior, unchanged). Flip the flag on only **after** profiles are backfilled (`POST /api/admin/candidate-profile/backfill?dryRun=false`, admin-role + flag gated); rollback is instant (flag off). The matcher also applies a **user-defined excluded-roles hard filter** (`JobMatchingService.isRoleExcluded`, whole-word title match + non-tech family match via `JobTaxonomy`) — empty exclusions are a no-op, so it is safe always-on. Excluded roles are edited in `candidate_preferences` (`excluded_roles`, added by `V9`) and snapshotted into the profile.
- `JobController`'s `GET /api/jobs/discovered?scope=domestic|international&country=...` reads the global pool directly; `GET /api/jobs/recommended` reads the precomputed `job_recommendations`. The frontend's [Jobs.tsx](frontend/src/pages/Jobs.tsx) Domestic/International tabs call the former, separately from the existing org-scoped job list.

### Resume tailoring is a 7-stage async event pipeline, not one service
[resumetailoring/](backend/src/main/java/ai/careerpilot/resumetailoring/) implements Phase 2D: Resume Tailoring → ATS Optimization → Gap Analysis → ATS Explainability → Cover Letter → Application Package → Auto-Apply Preparation. Each stage is its own vertical slice (own sub-package, own job table, own bounded `ThreadPoolTaskExecutor`, own REST controller) chained by Spring `@TransactionalEventListener` — there is no shared orchestrator class. The chain: `RecommendationApprovedEvent → ResumeTailoringWorker → ResumeTailoredEvent → AtsOptimizationWorker → AtsOptimizedEvent → GapAnalysisWorker → GapAnalysisCompletedEvent → AtsExplainabilityWorker → AtsExplainabilityCompletedEvent → CoverLetterWorker → CoverLetterCompletedEvent → ApplicationPackageWorker → ApplicationPackageReadyEvent → AutoApplyPreparationWorker` (final stage, publishes nothing further). Events live in `resumetailoring/event/`.

**Every worker follows the identical shape** — do not deviate when adding a stage:
```java
@Async(PipelineExecutorsConfig.<STAGE>_EXECUTOR)
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT, fallbackExecution = true)
public void on<PriorEvent>(<PriorEvent> event) {
    if (!triggerEnabled || !service.isEnabled()) return;
    try {
        executor.execute(() -> service.doWork(...));
    } catch (Exception e) {
        log.warn("... worker failed ...: {}", e.toString());
    }
}
```
Two independent flags per stage (`<stage>.enabled` gates the engine itself; `<stage>.trigger....enabled` gates whether it auto-fires off the prior stage's event) — both default `false`. `PipelineExecutorsConfig` centralizes the bounded executors (one per stage, deliberately not shared, so one stage's saturated queue can't starve another's).

**Do not wrap a worker's listener body in `@Transactional(propagation = REQUIRES_NEW)`.** This was a real, previously-shipped bug (`ResumeTailoringWorker`/`AtsOptimizationWorker`): the annotation opened a second transaction around the job-row insert, and the bounded-executor thread it then handed off to could read that row back *before* the wrapping transaction committed — a silent race that stranded jobs in `QUEUED` forever with zero error logs. The `@TransactionalEventListener(phase=AFTER_COMMIT)` already guarantees the triggering transaction has committed; no worker needs its own `@Transactional`.

Each stage's job table (`resume_tailoring_jobs`, `ats_optimization_jobs`, `gap_analysis_jobs`, `ats_explainability_jobs`, `cover_letter_jobs`, `application_package_jobs`, `auto_apply_package_jobs` — migrations `V24`–`V30`) tracks `QUEUED`/`RUNNING`/`SUCCEEDED`/`FAILED` and is the only way to trace an async run; there is no synchronous fallback API for any stage. Poll a stage's status via its own `GET /api/diagnostics/<stage>` and `GET /api/diagnostics/<stage>/queue` endpoints ([DiagnosticsController.java](backend/src/main/java/ai/careerpilot/api/DiagnosticsController.java) for resume-tailoring/ATS-optimization, [PipelineDiagnosticsController.java](backend/src/main/java/ai/careerpilot/api/PipelineDiagnosticsController.java) for gap-analysis/ATS-explainability/cover-letter/application-package/auto-apply-package).

### Phase 2E — Application execution (`execution/`) plus real browser automation
[execution/](backend/src/main/java/ai/careerpilot/execution/) reuses the same `@Async` + `@TransactionalEventListener(AFTER_COMMIT)` worker pattern as resume tailoring, chained: safety validation (`execution/safety/SafetyEngine`) → mandatory human approval (`execution/approval/ApprovalService`, `POST /api/execution/approve`) → execution (`execution/execution/ApplicationExecutionService`) → retry policy (`execution/retry/RetryPolicyService`, deterministic failure-class → RETRY/PAUSE/STOP) → tracking → analytics, each its own sub-package/executor via `execution/config/ExecutionExecutorsConfig.java`.

Real browser automation lives here too: `execution/browser/GuestApplyAutomationService.java` drives Microsoft Playwright's Java API via `PlaywrightAutomationProvider`. "Guest" means unauthenticated/no-login apply forms only — eligibility is a **hardcoded allowlist** in `execution/ats/GuestApplyEligibility.java` limited to `{greenhouse, lever}` (the only ATSes with public no-login forms); every other connector under `execution/ats/connector/` is a stub. `login()` unconditionally throws — no credentials are ever stored or entered. The flow is two-phase: fill only verified real `User` fields, screenshot the unsubmitted form, queue a `FORM_SCREENSHOT` approval — only after a human approves does `finalizeSubmit()` re-navigate and actually click submit. Gated by `BROWSER_AUTOMATION_ENABLED` (default `false`); the safety/approval stage flags default to fail-closed "on" even though the execution stage itself is dark.

**Browser Automation Platform, Phase 1 — the memory bound (`execution/browser/pool/`).** An audit found that the concurrency limit everyone assumed existed **did not**: `browser.automation.executor.max-pool-size=2` bounds a *thread pool*, but `ApplicationExecutionService.execute()` (which opens a Chromium context) is reachable from four independent pools — `applicationSubmissionExecutor` (max 4), **Tomcat HTTP request threads** via `ExecutionController`'s manual retry, `RecoveryScheduler`, and `browserAutomationExecutor` — and `BrowserSessionManager.newContext()` had no gate at all. At ~250–600 MB per context+page, enabling the flag on the 3 GB VM was an OOM waiting to happen. `BrowserLeasePool` is now that gate: a fair `Semaphore` (default **1** lease, `browser.automation.pool.max-leases`) plus a registry of outstanding `ContextLease`s.

**Permits are pooled; contexts are not.** A `BrowserContext` carries cookies/localStorage/cache, so reusing one across users would leak one applicant's session into another's application — the semaphore is what bounds memory, and the always-fresh-context rule is what preserves the manual multi-tenant isolation used everywhere else in this codebase. This is why there is no `BrowserContextPool`/`PagePool` despite those being the conventional names. A forgotten lease cannot permanently consume capacity: `reclaimExpired()` (run opportunistically on every acquire, so no extra scheduler thread) destroys anything past `lease-ttl-seconds` and returns its permit, with `ConcurrentHashMap#remove` as the atomic arbiter between a reclaiming sweep and a late `close()` so a permit is released exactly once. Capacity exhaustion surfaces as a typed `BrowserCapacityUnavailableException` that maps onto the existing `RetryPolicyService` classes, never an unbounded queue.

Three further defects fixed: (1) `PlaywrightAutomationProvider.navigate()` used to overwrite its `ThreadLocal` context holder unconditionally, so a caller that threw before `logout()` orphaned a live context on a pooled thread *and* skipped `contextClosed()` — it now detects and releases a stale lease first (test: `navigateReleasesAnUnclosedPriorLeaseInsteadOfOrphaningIt`); (2) `@PreDestroy` closed the browser mid-job — `drainAndShutdown()` now waits `drain-timeout-seconds` for in-flight leases before force-destroying; (3) the pool notifies `sessionManager.contextClosed()` on every teardown path, so the open-context counter can no longer drift upward and permanently false-positive zombie detection.

`BrowserLaunchOptionsFactory` replaces the previous `new LaunchOptions().setHeadless(true)` — which **could not start Chromium on the actual deployment target at all**. It adds `--disable-dev-shm-usage` (Docker's default `/dev/shm` is 64 MB and no `shm_size` is set in `docker-compose.yml`), `--no-sandbox`/`--disable-setuid-sandbox` (the container has no user namespace; a documented security trade-off, disableable via `browser.automation.launch.no-sandbox=false`), a `--js-flags=--max-old-space-size` renderer heap cap, and `setExecutablePath`/`setChannel` support — **required on ARM, where Playwright publishes no `linux-arm64` Chromium build**. `--single-process` is deliberately excluded: it saves ~40–60 MB but makes one renderer crash kill every concurrent job. `BrowserPoolMetrics` is kept separate from `BrowserAutomationMetrics` (capacity vs. submission outcomes); `poolAcquireTimeouts` is the demand-exceeds-budget signal and `poolLeasesExpired` is the release-leak signal, both previously unobservable. All of it is surfaced on the existing `GET /api/diagnostics/browser` rather than a new controller.

New flags, all with safe defaults: `browser.automation.pool.max-leases:1`, `.lease-ttl-seconds:180`, `.acquire-timeout-seconds:30`, `.page-timeout-seconds:30`, `.drain-timeout-seconds:20`, `browser.automation.launch.{no-sandbox:true,disable-dev-shm:true,max-old-space-mb:256,executable-path:,channel:,timeout-ms:60000}`. Verified via `mvn test` (2375/2375 — 2347 prior + 28 new), including a 12-thread concurrency test asserting peak concurrent leases never exceeds the cap and every permit is returned. **Still unfixed and out of scope: the production image cannot run Chromium** — the launch flags are now correct, but the Alpine/musl base image and missing browser binaries remain (see the Phase 0 note below). **Phase 12A closed exactly that gap** — see below.

### Phase 12A — Production Infrastructure Hardening: the image can now actually run Chromium
Infrastructure only; **no Java, Python, SQL, migration, endpoint, DTO, or feature flag changed**. Three files: `backend/Dockerfile`, `docker-compose.yml`, `careerpilot.env.example`.

The runtime base moved from `eclipse-temurin:25-jre-alpine` to `debian:bookworm-slim` carrying a copied Temurin JRE, because the Alpine image could not run browser automation for three independently fatal reasons (all verified on the live VM): musl vs glibc (Playwright's Chromium and Node driver are glibc builds), no browser installed and no `~/.cache/ms-playwright`, and ARM — Playwright publishes no `linux-arm64` Chromium, so its download-on-first-use path cannot succeed regardless of libc. The image now installs distro `chromium` (verified `151.0.7922.71` on this exact hardware) plus `fonts-liberation` (without a font, headless Chromium renders blank text — which would silently corrupt the very screenshots the human `FORM_SCREENSHOT` approval gate depends on), `tini` as PID 1 (Chromium spawns children; without a reaper, crashed renderers accumulate as zombies), and `wget` (the compose healthcheck relied on BusyBox's `wget` from Alpine — a latent break caught during this phase). It runs as non-root `careerpilot`, which matters specifically because `--no-sandbox` is mandatory here.

**The `mem_limit`/`-Xmx` pairing is load-bearing and must not be split.** `MaxRAMPercentage=50` sizes the heap from whatever bound it sees, so adding `mem_limit: 2048m` *alone* would grant a 1024m heap; add non-heap (~450m) and a Chromium child process (~600m peak, launched **inside this container** by Playwright) and the container is OOM-killed. An explicit `-Xmx768m` replaces the percentage. `MaxMetaspaceSize=320m` is retained (160m caused a real production crash-loop) and SerialGC is retained and now clearly correct on 1 vCPU. Per-service `mem_limit`s are sized from measured usage; `KAFKA_HEAP_OPTS`/ZooKeeper heaps are capped (they consume ~20% of the box with zero consumers — see "Provisioned-but-unused"). **No `cpus:` caps** — on one core, hard fractional caps worsen contention rather than isolating it.

Verified empirically on the production VM rather than reasoned: Chromium installs on bookworm arm64, Temurin 25.0.3 runs on glibc 2.36, headless launch with the exact production flags renders DOM and exits 0 as the non-root user with `shm_size: 256m`. Production containers were untouched throughout. `mvn test` 2375/2375.

### Phase 12B — Safe Rollout, Canary Deployment, Browser Health & Diagnostics
Phase 12A made the image capable of running Chromium; 12B makes turning it on a controlled, observable, reversible act. Additive only — no API change, no migration, no schema change, and with every new flag at its default the build is byte-identical to Phase 12A.

**Flag audit finding, stated plainly: `playwright.enabled`, `browser.enabled`, and `browser.max-leases` do not exist and were not created.** The real names are `browser.automation.enabled`, `browser.automation.pool.max-leases`, etc. Adding aliases would have *introduced* the hidden coupling the audit was meant to rule out. `browser.automation.guest-apply-only` remains diagnostics-visibility only — real enforcement is the hardcoded `GuestApplyEligibility` allow-list. There is deliberately **no flag to disable verification**: a switch that turns off the truthfulness gate is not a feature.

**`BrowserRolloutGate`** (`execution/browser/rollout/`) is a second, independent gate on top of `browser.automation.enabled` — the master flag decides whether Chromium may exist, this decides per user whether an otherwise-eligible execution may drive it. Both must agree. Bucketing is a stable hash of the user's `UUID` bits (not `toString().hashCode()`), giving two properties asserted directly rather than inferred: **deterministic** (a user never oscillates between requests) and **monotonic** (anyone admitted at 5% is still admitted at 25% — raising the percentage only ever adds, so a stage advance can't silently drop the very users whose successful runs justified it). `Math.floorMod` guards the sign. An allow-list checked before the percentage is what makes Stage 1 (internal testers, 0% everyone else) expressible. A null user id is never admitted — an unattributable execution is exactly the one that must not reach a live employer form. A malformed allow-list uuid is dropped with a warning, never a startup failure; `snapshot()` emits the allow-list *size*, never the ids. Wired at exactly one place — `ApplicationExecutionService`'s guest-apply branch — where a non-admitted user falls through to the **pre-existing** `ABORTED` path, so the dark build is unchanged. **Default 0% means enabling the master flag alone still exposes nobody**, making Stage 0 a real observable state rather than a promise. `finalizeGuestApplySubmit` is deliberately *not* gated: the fill already happened and a human already approved that screenshot, so stranding it helps nobody and invites a duplicate manual application — hard-stopping in-flight work is the master flag's job.

**`BrowserHealthService`** aggregates the full Part-2 report into the existing `GET /api/diagnostics/browser` (no new endpoint), preserving every pre-12B key at its exact path and adding `rollout`/`runtime`/`installation`/`session`/`lifecycle`. It never triggers a lazy launch — an operator checking health on a dark deployment must not be the thing that starts Chromium. Honesty rules it enforces: Chromium version is reported only when genuinely launched (no `chromium --version` subprocess — this endpoint is unauthenticated); `browserInstalled` is a real filesystem check, reporting `null`/"unknown" rather than `false` when no explicit path is configured, since Playwright's bundled-browser location is internal and guessing would fabricate a fact; `openPages` equals `activeLeases` **and says so**, because one page per lease is structural and two counters that can disagree is how a metric stops being trusted; ARM compatibility is genuinely derived (`aarch64` + no executable-path/channel ⇒ incompatible) so the most likely first-time failure is visible *before* anyone flips the flag. The composite `health` verdict deliberately overwrites `stage()`'s queue-depth-only one, which reported `UP` for a browser that could not launch at all. Every section is independently try/caught, including the verdict itself.

**`BrowserLifecycleMetrics`** is a third metrics class, not a merge, following this package's existing separation by question: `BrowserAutomationMetrics` = submission outcomes, `BrowserPoolMetrics` = capacity, this = process health (launch attempts/successes/failures, launch-time avg/max, restarts, crashes, `lastLaunchError`, `lastCrashAt`). Launch was previously *entirely* unobservable — a Chromium that failed to start produced a stack trace and nothing else. `launchSuccessRate` returns 100% when nothing was attempted; reporting 0% would make every dark deployment read as broken. Errors are truncated so the unauthenticated endpoint can't leak page content. `BrowserAutomationMetrics` also gained screenshot capture/failure counts, `lastScreenshotAt`/`lastConfirmationAt` (a screenshot that quietly stopped working is how a silent rendering failure first shows up — the approval gate would be reviewing blank images), and submit duration tracked separately from attempt latency (averaging fills and submits together hides a slow submit behind fast fills).

**Two real recovery defects fixed.** (1) `reclaimExpired()` ran *only* inside `acquire()` — correct while traffic flows, but with the production default of `max-leases=1` one leaked lease consumes the entire budget, so there is no next acquire to trigger the reclaim: **the pool deadlocks itself until a restart**. `BrowserMaintenanceScheduler` (gated `browser.automation.maintenance.enabled`, default `false`, *and* the master flag) is the periodic sweep that makes reclaim reachable on an idle system; it adds a trigger, not a policy, calling the two existing methods and nothing else, each independently try/caught so one broken half can't disable the other's recovery. (2) `restartIfZombie()` closed the shared `Browser` unconditionally, destroying the context of every **healthy** in-flight job as collateral — and since the zombie heuristic fires on "5+ contexts open", the exact trigger condition is the one most likely to contain live work. It now defers while any lease is outstanding (resolved via `ObjectProvider` to avoid the `BrowserLeasePool` → `BrowserSessionManager` construction cycle); the pool's own TTL reclaim frees those leases shortly, after which the next check proceeds. Launch failure also now tears down partial Playwright state, which previously left an orphan driver process alive that nothing would ever close.

Operational documentation: [docs/operations/browser-automation-runbook.md](docs/operations/browser-automation-runbook.md) — deployment/rollback/monitoring checklists, the 6-stage rollout table with exit criteria, a per-failure-mode behaviour table (every mode fails safe; none can produce a false `SUBMITTED`), incident-response procedures, and a troubleshooting reference.

New flags, all safe by default: `browser.automation.rollout.{percentage:0,allowed-user-ids:,stage-label:STAGE_0_OFF}`, `browser.automation.maintenance.{enabled:false,interval-ms:60000,zombie-restart-enabled:true}`. Verified via `mvn test` (2416/2416 — 2375 prior + 41 new) plus frontend `npx tsc --noEmit`, `vitest run` and `npm run build`, all clean. **Not deployed** — the residual unknown remains Playwright's protocol handshake against a distro Chromium rather than a Playwright-pinned build, which is precisely what rollout Stage 1 exists to discover.

**Browser Automation Platform, Phase 0 — the truthfulness gate (evidence adjudication).** `execution/verification/evidence/` closes a real correctness defect found by audit: `ApplicationExecutionService.finalizeGuestApplySubmit` used to call verification inside a try/catch and then transition to terminal `STATUS_SUBMITTED` **regardless of the verdict**, while the only actual check (`GreenhouseConnector`/`LeverConnector.verifySubmission`) was *"is the post-submit page longer than 50 characters"* — so a rendered error page certified a failed submission as successful, and the submission session then trusted that status. `VerificationAdjudicator` (pure, deterministic, no I/O — same discipline as `RetryPolicyService.decide`) maps an `EvidenceBundle` of `VerificationSignal`s onto a four-level `ConfidenceLevel` ladder (`CONFIRMED`/`STRONG`/`WEAK`/`NONE`), and **only `CONFIRMED` or `STRONG` may reach `SUBMITTED`** (`ConfidenceLevel.permitsSubmittedStatus()`). `ConfirmationPageAnalyzer` extracts the signals that the already-captured post-submit page can genuinely support — a labelled application reference (`DECISIVE`), a confirmation phrase (`STRONG`), and failure indicators (`ERROR_STATE`, which forces `NONE` regardless of any positive signal); `SignalType.URL_TRANSITION`/`NETWORK_RESPONSE`/`EMAIL_CONFIRMATION` are declared but deliberately have no producer yet (they need the adapter layer, and `EmailIntelligenceService` is still inert) — an unproducible signal simply never appears rather than being synthesised to pad confidence. Screenshots are `CORROBORATING` only and can never raise a level on their own.

Two new statuses carry the honest middle ground, both named `SUBMIT_UNVERIFIED` (17 chars — fits the existing `execution_status VARCHAR(20)` and `status VARCHAR(32)` columns, so **this phase needs no migration**): `ApplicationExecution.STATUS_SUBMIT_UNVERIFIED` and `ApplicationSubmissionSession.STATUS_SUBMIT_UNVERIFIED`. It means the submit click genuinely happened but delivery couldn't be certified. It is deliberately *not* routed to `WAITING_MANUAL_SUBMISSION` — telling a user to manually re-apply to a job they may already have applied to is how duplicate applications reach an employer — so `SubmissionStateMachine` gains `SUBMITTING → SUBMIT_UNVERIFIED → TRACKING` and the session still gets its kanban card and lifecycle transition via a `trackAndComplete(...)` helper extracted verbatim from steps 12-13. It is never auto-retried; `RetryPolicyService` already classifies this as `CONFIRMATION_MISSING` → `PAUSE`. `WAITING_MANUAL_SUBMISSION` remains a dead end — a separate known defect, deliberately out of Phase 0's scope and pinned by a test so a later phase closes it intentionally rather than by accident.

Verified via `mvn test` (2347/2347 — 2314 prior + 33 new/updated). **Three pre-existing tests asserted the old behavior and were deliberately inverted**, which is the clearest statement of what changed: `GreenhouseConnectorTest`/`LeverConnectorTest`'s `substantialCapturedContentIsVerified` (`"x".repeat(200)` ⇒ VERIFIED) now assert `UNABLE_TO_VERIFY`, and `ApplicationExecutionServiceTest.finalizeGuestApplySubmit_verificationExceptionNeverBlocksSubmittedOutcome` is now `...verificationExceptionFailsClosedToSubmitUnverified`. **Note the audit's other standing finding, unfixed and out of scope here: the production Docker image cannot actually run Chromium** (Alpine/musl JRE, ARM with no Playwright `linux-arm64` Chromium build, no browser binaries installed, 64 MB `/dev/shm`, and `BrowserSessionManager` launching with `setHeadless(true)` and no other options) — enabling `BROWSER_AUTOMATION_ENABLED=true` on the current image would throw at `Playwright.create()`, not degrade.

### Phase 3A — Workflow tracking is a second, deliberately separate tracking system
[workflow/](backend/src/main/java/ai/careerpilot/workflow/) is explicitly documented in its own code as event-driven, not a linear pipeline. `workflow/correlation/WorkflowCorrelationService` keeps one row per running Phase 3A instance, upserted on every stage transition; `WorkflowDeadLetterService` is where every worker's catch block writes instead of propagating, for audit/replay. `workflow/tracking/ApplicationLifecycleService` + `ApplicationStatusMachine` is the canonical per-(user,job) status machine — **deliberately separate from Phase 2E's execution-scoped tracking**: `application.tracking.*` (Phase 2E) and `workflow.tracking.*` (Phase 3A) are two different config namespaces tracking two different things, don't conflate them. `workflow/timeline/TimelineService` is a human-readable, confidence-scored event stream distinct from the validated status history, and `workflow/analytics/` is its own metric set, separate from Phase 2E's `execution_analytics`.

Two narrower additions in the same package family: `workflow/email/EmailIntelligenceService` is a deterministic keyword classifier that is **fully inert** — no mailbox integration exists, nothing fetches email, rows only arrive via a manual-ingest path. `workflow/interview/InterviewService` tracks interview rounds (Recruiter/Technical/System Design/Manager/HR/Final/Offer) with append-only feedback. All gated by their own `workflow.*` / `email.intelligence.*` / `interview.tracking.*` flags, default `false`.

### Phase 6 — Learning-from-outcomes exists but is deliberately disconnected from live scoring
`learning/LearningEventBridge` (same async-listener pattern) captures 2D/2E/3A domain events — application submitted/rejected/accepted, interview detected, offer received, recommendation approved — into `LearningEvent` rows. Downstream, `learning/pattern/SuccessPatternEngine` + `FailurePatternEngine` compute pattern rows, and `learning/recommendation/RecommendationWeightManager` upserts weights that `learning/recommendation/AdaptiveRecommendationEngine.getBoost(userId, dimension, key)` exposes as a read-only facade.

Treat it like the "Provisioned-but-unused" list below, not as an active feature. Also in this phase: `learning/resume/ResumeLearningService` (best resume version by interview/offer rate), and `learning/career/CareerLearningEngine` + `CareerStrategyEngine` — the latter is what actually populates `domain/CareerStrategy`, combining a probability engine and a trajectory analyzer into one row per user. Gated by `learning.adaptive-recommendation.enabled` / `learning.adaptive-career.enabled`, both default `false`.

### Phase 7 — Autopilot, submission orchestration, and the Application Command Center are three different patterns
- [autopilot/](backend/src/main/java/ai/careerpilot/autopilot/) (`ApplicationDecisionEngine`, `AutoApplyEngine`, an `ApplicationProvider` SPI for Ashby/Greenhouse/Lever/LinkedIn/SmartRecruiters/Taleo/Workday/CompanyPortal) is scheduler/orchestrator style (`AutopilotScheduler`, `CareerOrchestrator`), not an event chain. Gated by `application.decision.enabled` / `application.auto.enabled`.
- [submission/](backend/src/main/java/ai/careerpilot/submission/) (`ApplicationSubmissionSessionService`, `SubmissionStateMachine`) is a single orchestrator that **links by id** — never copies — into existing dormant rows from earlier stages (execution, packageintel, review, companyintel, story), spanning validation → field-mapping → question-detection → strategy → optional-approval → execution → verification → tracking → learning, publishing its own session-progress events rather than running N independent stage workers. Gated by `application.submission.*`, default `false`.
- [applications/](backend/src/main/java/ai/careerpilot/applications/) — the Application Command Center (`ApplicationCardService`, `ApplicationHealthService`, `ApplicationNextActionService`, `ApplicationRecommendationService`) — has **no flag, no worker, no event**. It's a plain synchronous, always-on read/aggregation `@Service` layer over existing `applications` data (adds `favorite`/`priority`/`archived` columns). This is the one subsystem in this whole section that is live by default, not dark-shipped.

### Company intelligence, offer intelligence, and career roadmap persistence

### Package validation, AI review, decision memory, and retention — four more additive layers, don't conflate them
- `packageintel/ApplicationPackageIntelligenceService` (Phase 7.11) does NOT re-assemble or re-score anything: it delegates package assembly to the existing Phase 2D.6 `ApplicationPackageService`, then binds already-computed signals from other engines (autopilot decision, company research, learning boost, resume match) onto the package, runs `ApplicationPackageValidator`, and records an immutable validation history row. Gated `application.package.validation.enabled`; fail-safe by construction — a failure records a BLOCKED validation, never a fabricated READY.
- `review/ApplicationReviewPipeline` (Phase 7.12) is the next gate on top of that: it REVIEWS the Phase 7.11 package (never mutates it) by running each enabled reviewer (`review/reviewer/` — resume/ATS/company-fit/learning/consistency/quality) and persists an `ApplicationReview` head + immutable history row. Gated `application.review.enabled`; same BLOCKED-not-fabricated fail-safety.
- `memory/CareerMemoryService` (Phase 7.15.1, "Career Decision Memory") is deliberately **not** a rebuild of `learning_event` (Phase 6, pattern-computation) or `recommendation_feedback` (Phase 2C, raw reaction log) — it normalizes both of those plus five Phase 3A workflow events (via `CareerMemoryEventBridge`) into one durable, ranked, append-only "why the candidate decided X" record the Copilot can read instead of re-asking. Gated `career.memory.enabled`. Copilot-conversation extraction is deliberately NOT wired (would need LLM-based parsing with no existing infra, and a bad extraction silently poisoning future recommendations is a correctness risk left for its own review).
- `retention/RetentionService` is a pure delete-by-age maintenance job (no LLM, no events) for the append-only ledgers that grow unbounded — workflow dead-letter/correlation tables plus the recommendation/execution/resume-tailoring audit trails. Each target has its own configurable retention window and its own `REQUIRES_NEW` transaction, so one target failing never aborts the others. Gated `retention.enabled`, default `false` (no-op with stock flags).

### Career Goal Intelligence and the Executive Decision Engine both upsert into the SAME `CareerStrategy` row

### Phase 9.1 — Spring AI Foundation exists but is not on any request path
`ai/springai/` adds Spring AI (`spring-ai-bom` 2.0.0, Boot-4-aligned) as a foundation layer that coexists with — and is completely inert relative to — the existing AI Gateway. `SpringAiConfig` builds `ChatModel`/`StreamingChatModel`/`EmbeddingModel` beans from a single OpenAI-protocol client (`com.openai:openai-java-client-okhttp`, added alongside the starter since it pulls no HTTP transport of its own), gated end-to-end by `ai.springai.foundation.enabled` (default `false` — the beans literally aren't constructed when off). Spring AI's own OpenAI autoconfiguration is explicitly excluded (`spring.autoconfigure.exclude` in `application.yml`) so it can never auto-activate off an incidentally-set `spring.ai.openai.*` property — `SpringAiConfig` is the only path these beans can come from. `ai/springai/adapter/` (`SpringAiChatService`, `SpringAiModelFactory`, `SpringAiProviderAdapter` implementing a standalone `ProviderAdapter` interface — deliberately not `ai.careerpilot.ai.LlmProvider`, so nothing here can be picked up by `AiGatewayService`'s provider chain) is the shape a future migration would build on. `ai/springai/mcp/` (`McpToolRegistry`, `McpToolDefinition`, `McpCapability`, `ToolExecutionContext`) is extension-point interfaces only — no implementation, no server connection; real MCP tool servers (filesystem/Postgres/GitHub) are explicitly out of scope until Phase 9.3+. As of Phase 9.1 alone, nothing outside `ai/springai/` referenced any type in this package; Phase 9.2 (below) is the first and only exception.

### Phase 9.2 — the first real Spring-AI-backed provider, wired in canary (last) position
`ai/provider/SpringAiLlmProvider.java` implements the real `ai.careerpilot.ai.LlmProvider` contract (extends `AbstractLlmProvider`, so every feature-helper prompt template is reused for free) on top of the Phase 9.1 `ChatModel`/`StreamingChatModel` beans — this is the one place the Spring AI foundation is actually load-bearing. It's registered as a plain, unconditional `@Component` (matching every other provider's shape, not `@ConditionalOnProperty`-gated) because `AiGatewayService` autowires `List<LlmProvider>`; the `ChatModel`/`StreamingChatModel` beans it needs are injected via `ObjectProvider` (never fails to construct even when Phase 9.1's flag is off) and `isConfigured()` returns `false` unless **both** `ai.springai.foundation.enabled=true` and a real api-key are set — identical in spirit to an NVIDIA provider with a blank key. Added as key `spring_ai` at the literal end of `ai.gateway.order` — the canary position, reached only after every other configured provider has failed. `ai.gateway.providers.spring_ai` in `application.yml` is diagnostics-display metadata only (model/timeout mirrored from the same `SPRING_AI_FOUNDATION_*` env vars so the two can't drift) — `SpringAiLlmProvider` does not read that block; its real config comes solely from `ai.springai.foundation.*`.

Two real bugs surfaced and were fixed during this phase, both specific to the OpenAI Java SDK's eager-validation behavior (unlike this codebase's own `AbstractOpenAiChatProvider`/WebClient-based providers, which never validate credentials at construction time): (1) `OpenAiChatModel.Builder` silently tries to build its own async client from nothing if only `openAiClient(...)` is supplied — fixed via `springAiOpenAiClient.async()`, which correctly inherits the already-configured credentials; (2) a blank api-key makes `OpenAIOkHttpClient.Builder.build()` throw immediately at bean-creation time — fixed by substituting a non-blank placeholder when the real key is blank, so construction always succeeds and `isConfigured()` (not a startup crash) is what gates real usability, matching every other provider's resilience contract.

Live-verified end-to-end (not just unit-tested): with the flag on and a real NVIDIA key, `SpringAiLlmProvider.chat()` returned a genuine `"pong"` response from NVIDIA's live API through the full Spring AI stack.

### Phase 9.3 — Gemini migrated to Spring AI (provider 1 of 6), flag-gated with legacy as default
`ai/migration/` is the provider-by-provider migration seam the enterprise migration strategy calls for: `ProviderRegistryConfig` (`@Configuration`) is the **only** place that decides, per provider key, whether the legacy or the Spring-AI-backed implementation is the one actually registered as an `LlmProvider` bean — `AiGatewayService`/the Smart Router are byte-for-byte unchanged and have no idea this class exists, since Spring's `List<LlmProvider>` autowiring naturally collects whichever bean the registry produced. `SpringAiMigrationProperties` binds `spring-ai.providers.<key>.enabled` for all 6 providers (Gemini/Groq/SambaNova/NVIDIA/Qwen/OpenRouter per the stated migration order), all defaulting `false`; only `gemini` has a real second implementation today (`GeminiSpringAiProvider`) — the other five flags exist so their config shape is stable, but flipping one currently has zero effect (no `@Bean` branch reads it yet) until that provider gets its own migration phase, following this identical pattern.

`GeminiProvider` (legacy) had `@Component` removed — its ONLY change — since it's now constructed explicitly by the registry instead of auto-scanned; no other line changed. `GeminiSpringAiProvider` (new, `ai/provider/`) targets the same Gemini Developer API (api-key auth) as the legacy provider via Spring AI's `spring-ai-google-genai` starter — deliberately not `spring-ai-vertex-ai-gemini`, which needs a GCP service account this deployment doesn't have. Both implementations read the identical config (`ai.gateway.providers.gemini.*`) — migrating is purely an engine swap, no new credentials. `displayName()` differs ("Gemini" vs "Gemini (Spring AI)"), which is the whole observability story: every existing log line/metric/diagnostics entry that already reports `displayName()` now shows which engine served a call, with zero new plumbing in `AiGatewayService`/`AiMetrics`/`ProviderHealthTracker`.

One real bug, same family as Phase 9.1/9.2: adding the `spring-ai-google-genai` starter alone (regardless of any migration flag) makes Spring Boot's own `GoogleGenAiChatAutoConfiguration` try to auto-construct an unrelated `googleGenAiClient` bean from `spring.ai.google.genai.*` properties this app never sets — crashing startup unconditionally. Fixed via the same `spring.autoconfigure.exclude` pattern used for the OpenAI starter in Phase 9.1.

Live-verified end-to-end: with `spring-ai.providers.gemini.enabled=true`, `GeminiSpringAiProvider.chat()` and `.streamChat()` both returned genuine `"pong"` responses from Gemini's live API. With the flag at its default (`false`), the registry log confirms it resolves to the legacy implementation and `gemini` reports `UP` exactly as before this phase.

### Phase 10.1 — Enterprise MCP Foundation: the platform, not a server
`ai/careerpilot/mcp/` is a dedicated Model Context Protocol platform layer, conceptually sitting between Spring AI and business services in the AI stack, built with the same "foundation only, zero wiring" discipline as Phase 9.1. **No MCP server (filesystem/Postgres/GitHub/Playwright/Redis/memory/etc.) is implemented or connected** — this phase builds the registry, capability model, health/metrics/security contracts, and plugin shape a future server integration would plug into. Every bean is gated by `mcp.enabled` / `mcp.health.enabled` (both default `false`, see `McpConfig`); with defaults, no bean in this package is constructed and nothing outside `ai.careerpilot.mcp` references it.

Core types: `McpCapability` (FILESYSTEM/DATABASE/BROWSER/GITHUB/MEMORY/SEARCH/AUTOMATION/KNOWLEDGE), `McpServerDefinition`/`McpToolDefinition` (pure metadata — registering one never opens a connection), `McpExecutionContext` (mirrors `AuthenticatedUser`'s userId/orgId multi-tenant shape), and `McpExecutor` (the tool-invocation contract — **no implementation exists**, matching the same "interface only" discipline as `learning/recommendation/AdaptiveRecommendationEngine` before it's consulted by live matching). Unlike Phase 9.1's narrower `ai.springai.mcp` placeholder (still present, unreferenced, and left as-is), `McpRegistry` here has a real default implementation — `InMemoryMcpRegistry`, a thread-safe in-memory map — because a registry with nothing to register into it can't be meaningfully built against or tested; registering a server/tool is still bookkeeping only, never I/O. `McpHealthManager`/`InMemoryMcpHealthManager` follow the same shape but nothing calls `recordHeartbeat` in this phase, so every lookup reports `UNKNOWN`. `McpMetrics`/`NoopMcpMetrics` is observability prep only — every method is a deliberate no-op, no Micrometer wiring.

`mcp.security` (`McpAuthenticationProvider`/`McpAuthorizationProvider`/`McpAuditor`) and `mcp.springai` (`SpringAiMcpBridge`/`McpToolResolver`/`ToolCallingAdapter`, built on Spring AI's real `org.springframework.ai.tool.ToolCallback` type already on the classpath since Phase 9.1's `spring-ai-bom` import) are interface-only extension points — no implementation, no bean, nothing calls them. The plugin contract: any future MCP server registers itself through `McpRegistry` via a plain `@Configuration`/`@Bean`, never hardcoded into this platform.

Verification for this phase relied on `mvn test` (1760/1760, zero regressions — same suite Phase 9.3 left at 1743) plus Spring `ApplicationContextRunner` tests (`McpConfigTest`) that load a real (if minimal) Spring context and assert bean presence/absence per flag combination — a more precise check of the exact risk (conditional bean wiring) than a full container boot. A live Docker container boot/smoke test (the verification style used in Phases 9.1–9.3) was **not** performed for this phase.

### Phase 10.2 — first real MCP tool servers, plugged into the 10.1 platform
`ai/careerpilot/mcp/tool/` adds five independently-flagged MCP servers (`mcp.filesystem.enabled` / `mcp.postgres.enabled` / `mcp.github.enabled` / `mcp.memory.enabled` / `mcp.context7.enabled`, all default `false`, all additionally requiring `mcp.enabled=true`) — each a thin read-only wrapper around an **existing** repository/service, not a new data source: filesystem wraps `ResumeRepository`, postgres wraps `JobRecommendationRepository`/`ApplicationRepository`/`CareerStrategyRepository`, memory wraps the Phase 7.15.1 `CareerMemoryService`, github is a new keyless `api.github.com` client (styled after `AbstractWebJobProvider`), and context7 is a new keyed client (dark unless `mcp.context7.api-key` is set — endpoint shape is best-effort/not live-verified, see `Context7ApiClient`'s javadoc). No new database table, no new query beyond existing finder methods, no write path added anywhere.

This phase also turns three Phase 10.1 interfaces into real implementations for the first time: `McpExecutor` → `ai/careerpilot/mcp/tool/DefaultMcpExecutor` (authorize → dispatch to the tool's `McpToolHandler` via a new `McpToolHandlerRegistry` → record metrics/health → audit, catching everything so a handler failure becomes `McpToolResult.failed(...)` rather than an exception — enforced defensively for future callers since nothing on a production path invokes it yet), `McpAuthorizationProvider`/`McpAuthenticationProvider`/`McpAuditor` → `DefaultMcpAuthorizationProvider` (any resolved `userId` is authorized, matching CLAUDE.md's documented "no `@PreAuthorize` anywhere" convention) / `DefaultMcpAuthenticationProvider` (always `true` — external-system auth is each client's own `isConfigured()` check) / `LoggingMcpAuditor` (slf4j only, deliberately does not write to the still-unused `audit_logs` table), and `SpringAiMcpBridge`/`ToolCallingAdapter` → `DefaultSpringAiMcpBridge`/`DefaultToolCallingAdapter`, which build real Spring AI `ToolCallback`s (via `org.springframework.ai.tool.function.FunctionToolCallback`, already on the classpath since Phase 9.1) that genuinely invoke `McpExecutor` when called. **Known limitation, documented in `DefaultSpringAiMcpBridge`'s javadoc**: the Phase 10.1 `toolCallbacksFor(capability)` signature takes no caller identity, so callbacks built through the bridge run with a system-scoped (`userId=null`) context — every Phase 10.2 handler already treats that as "no authenticated user" and degrades to an unavailable/empty result rather than leaking data, so this is safe but not yet useful for per-user questions.

`McpConfig`'s default `McpMetrics` implementation changed from `NoopMcpMetrics` (Phase 10.1) to the new `InMemoryMcpMetrics` — plain `AtomicLong` counters per tool name, styled after `ai.careerpilot.ai.AiMetrics` (itself hand-rolled counters, not Micrometer, despite the name) rather than a new dependency. `NoopMcpMetrics` remains in the codebase, just no longer constructed by default.

**Critically, none of this is wired into anything that runs today**: no controller, no business service, and no `ChatModel` prompt in `AiGatewayService`/the Copilot/LangGraph constructs or calls a `ToolCallback` built by this phase's bridge. The tool resolution flow described in the phase spec (Business Service → Spring AI → MCP Registry → MCP Tool → Response) exists and is genuinely functional end-to-end when invoked directly (see the `*McpServerConfigTest` classes, which call each registered handler and assert real output), but no business service invokes it — satisfying "every MCP integration must be additive" and "zero regression" simultaneously with "genuinely working, not a stub."

A Phase 10.2.1 validation sprint confirmed this gap explicitly (exhaustive grep: zero files outside `ai.careerpilot.mcp` reference any MCP type) and closed several testability gaps discovered along the way — regression tests were added for `SpringAiConfig`/`SpringAiLlmProvider`/`ProviderRegistryConfig` (previously verified only via now-deleted temporary smoke tests) and for full-context feature-flag gating of all five Phase 10.2 servers (`McpToolServersFeatureFlagTest`). Full suite after the sprint: 1816/1816.

### Phase 10.3 — Capability Engine: an orchestration layer that CAN route to MCP tool calling, still not connected to any controller
`ai/careerpilot/capability/` answers Phase 10.2.1's validation finding by building the missing piece — but, per its own explicit "ZERO REST API changes" requirement, still doesn't connect it to a controller; the gap from 10.2.1 remains open by design, one phase closer to closeable. `CapabilityAwareChatService` is a new, parallel entry point that decides per-request whether to call the existing, byte-for-byte-untouched `AiGatewayService` (the default) or route through MCP tool calling — `AiGatewayService`'s own code was not modified in any way for this phase.

The decision chain: `CapabilityResolver` (keyword matching, styled after `CopilotSkillRouter#inferSkillFromMessage`) maps free text to one of six `CapabilityType`s (`RESUME_ANALYSIS`/`JOB_RECOMMENDATION`/`GITHUB_REVIEW`/`CAREER_STRATEGY`/`INTERVIEW_PREPARATION`/`LEARNING_HELP`) → `CapabilityRegistry` (`InMemoryCapabilityRegistry`, six defaults pre-registered) supplies which `McpCapability` categories that type needs → `ToolSelectionEngine` resolves those into live, currently-registered `McpToolDefinition`s via `McpRegistry.toolsByCapability(...)` (never a hardcoded tool name) → `CapabilityEngine` (`DefaultCapabilityEngine`) combines all of the above into one `CapabilityDecision`. Any break in that chain — no keyword match, `tool.selection.enabled=false`, capability not registered, or zero tools actually resolved — produces `useToolCalling=false`, which `CapabilityAwareChatService` treats identically: call `AiGatewayService.chat(...)` unchanged.

When tool calling IS decided: `CapabilityAwareChatService` executes the selected tools via the Phase 10.2 `McpExecutor` — sequentially by default, or in parallel via `CompletableFuture.allOf(...)` when `parallel.tool.execution.enabled=true` — merges each `McpToolResult` into a text context block, then either synthesizes the final answer through the Phase 9.1 Spring AI foundation `ChatModel` (when `spring.ai.tool.calling.enabled=true` AND that bean exists) or, just like the no-tool-calling path, falls back to `AiGatewayService.chat(...)` with the merged context appended to the last user message. A capability match, a disabled Spring AI flag, and a missing `ChatModel`/`McpExecutor` bean are all handled as ordinary fallback branches, never exceptions — see `CapabilityResult.fallbackReason()`.

Four independent flags, all default `false`: `capability.engine.enabled` is the master switch — off, and none of this package's beans are constructed at all (`CapabilityConfig`, matching every other phase's dark-by-default discipline). `tool.selection.enabled`, `parallel.tool.execution.enabled`, and `spring.ai.tool.calling.enabled` are runtime toggles read via `@Value` inside the already-gated layer, not additional bean gates — flipping the master flag alone still routes every request to `AiGatewayService`. `spring.ai.tool.calling.enabled` deliberately lives under the pre-existing top-level `spring:` YAML block (not a duplicate root key) since that's the exact property path the phase spec named; safe because Spring AI's own autoconfiguration for that prefix is already excluded (Phase 9.1/9.3) and no real Spring AI property collides with it.

Verified via `mvn test` (1846/1846, zero regressions) plus unit/`ApplicationContextRunner` tests covering every branch: no-match fallback, tool-selection-disabled fallback, zero-tools-resolved fallback, sequential and parallel execution, a throwing tool degrading to `McpToolResult.failed(...)` rather than propagating, Spring-AI-present vs. Spring-AI-absent synthesis, and full-context bean-presence-per-flag-combination gating.

### Phase 10.4 — the Copilot is wired to the Capability Engine: the first real production call site
Unlike every prior Phase 9/10 sub-phase, this one **does** touch a live request path: `ai/careerpilot/service/CopilotService.java`, the backend that already serves `/api/copilot/stream`. Gated by `copilot.capability.integration.enabled` (default `false`, inline `@Value` only — no `application.yml` entry, matching its sibling `copilot.candidate-profile-context.enabled`/`copilot.career-memory-context.enabled` flags' existing convention). With the flag off, `CopilotService.streamTurn()` is byte-for-byte the pre-Phase-10.4 code: `ai.streamChat(turns, system, providerCallback)`.

With the flag on, a new private method, `routeTokens(...)`, runs a **cheap, synchronous pre-check** — `CapabilityEngine.analyze(userMessage)` — before deciding the token source: if no capability matched (general chat), it still calls `ai.streamChat(...)` unchanged, deliberately preserving real token-by-token SSE streaming for ordinary conversation (calling the synchronous `CapabilityAwareChatService.chat(...)` here instead would collapse every general-chat response into a single chunk — a user-visible regression the phase spec explicitly forbade). Only when a capability actually matched does it call `capabilityAwareChatService.chat(turns, system, mcpContext)` (Phase 10.3, itself internally re-running `analyze()` — harmless, no I/O) and wrap the single synthesized answer as a one-element `Flux`, which then flows through the exact same `.doOnNext(assistant::append).doOnComplete(persist).onErrorResume(...)` pipeline as the streaming path — so persistence, conversation history, and the SSE contract are all identical regardless of which branch produced the tokens.

**Failure handling matches the spec's three explicit fallback rules** — all three land on the same outer `try/catch` around the decision+chat call in `routeTokens()`, so a thrown exception from `CapabilityEngine.analyze()`, from `McpExecutor` tool execution inside `CapabilityAwareChatService`, or from Spring AI synthesis all fall back to `ai.streamChat(...)` identically (the "If MCP Tool fails → Continue with remaining tools" case is already handled one layer down, inside `DefaultMcpExecutor`/`CapabilityAwareChatService.executeTools` — a single tool failing never stops the others or reaches this catch block at all). One real gap found and fixed while wiring this: `CapabilityAwareChatService.chat()` (Phase 10.3) had no try/catch around its Spring AI synthesis call — a `ChatModel.call()` failure would have propagated instead of falling back to `AiGatewayService` with the already-gathered tool context; now caught and converted to the same graceful fallback the "flag off" branch already used.

Security is unchanged from Phase 10.2/10.3: `CopilotService` never touches `McpToolHandlerRegistry` or a handler directly — it only calls `CapabilityEngine.analyze()` (pure decision, no I/O) and `CapabilityAwareChatService.chat()`, which is the only caller of `McpExecutor` (authorize → dispatch → audit, unchanged).

Verified via `mvn test` (1853/1853, zero regressions — 1846 prior + 7 new, including a new `CopilotServiceTest`, the first test file this class has ever had). No REST DTO, controller, or frontend file changed.

### Phase 10.3.1 — Capability Engine's "Spring AI tool calling" was never real tool calling, until now
Live testing after Phase 10.4 shipped found `CapabilityAwareChatService` had two related bugs, both in the "real tool calling" path implied by its own name and by `spring.ai.tool.calling.enabled`: (1) `executeTools(...)` always invoked every MCP tool with `Map.of()` — an empty argument map, regardless of what the user actually asked — so any tool requiring input (GitHub's `username`, Context7's `query`) silently failed every single call (`{"reason":"missing required argument 'username'","available":false}`), registering as `success=true` in `MCP_AUDIT` because the tool's own handler returned a normal (non-exception) "can't do this" result; and (2) even where arguments didn't matter, "Spring AI synthesis" only ever *pre-executed* tools itself and pasted the merged JSON into the system prompt as text — Spring AI's `ChatModel` never actually selected or invoked a tool via its own protocol, so `FunctionToolCallback`/`ToolCallingChatOptions` (the actual Spring AI tool-calling API) were unused code paths despite the flag's name.

Fixed by wiring the real protocol: `DefaultToolCallingAdapter` (`ai.careerpilot.mcp.springai`) now calls `.inputSchema(...)` with the tool's real `McpToolDefinition.inputSchema()` (serialized via Jackson) alongside the pre-existing `.inputType(Map.class)` — previously only `.inputType(Map.class)` was set, which tells Spring AI how to *deserialize* args but exposes no real parameter schema to the model deciding what to pass. `CapabilityAwareChatService.chat()` now tries a new `synthesizeWithRealToolCalling(...)` path first when `spring.ai.tool.calling.enabled=true` and both the `ChatModel` and `ToolCallingAdapter` beans exist: it builds one real `ToolCallback` per selected tool via `toolCallingAdapter.adapt(tool, context)` — using the request's actual `McpExecutionContext`, not a system-scoped placeholder — passes them through `OpenAiChatOptions.builder().toolCallbacks(...).build()`, and calls `chatModel.call(prompt)` once, letting Spring AI's own internal loop decide whether/which tool to call, with what LLM-chosen arguments, invoke it, and feed the result back for a final answer. The pre-Phase-10.3.1 pre-execute-then-paste-as-text behavior still exists, renamed to `legacyPreExecuteAndRespond(...)` — it's the fallback whenever real tool calling isn't available (flag off, either bean missing) or throws, preserving the same never-fail-the-request discipline as every other engine in this codebase. `CapabilityConfig` injects the pre-existing Phase 10.2 `mcpToolCallingAdapter` bean (`McpConfig`, gated by its own independent `mcp.enabled`) as an `ObjectProvider<ToolCallingAdapter>` — optional, since `capability.engine.enabled` and `mcp.enabled` are independent flags.

**Live-verified the fix actually closes the argument-passing gap** (not just unit-tested): a Copilot request "Analyse my GitHub profile, username torvalds" produced `MCP_AUDIT tool=analyze_github_profile server=github ... success=true` with the LLM having genuinely extracted `username=torvalds` from free text via the now-exposed schema — previously this exact request always failed with the missing-argument error, silently, on every prior test. One separately-tracked, non-blocking observation: the NVIDIA-hosted `deepseek-ai/deepseek-v4-flash` model behind the Spring AI foundation client (see Phase 9.1's `SpringAiConfig`) sometimes echoes its own tool-call syntax as literal text in the *final* answer after a successful tool round-trip, rather than synthesizing a natural-language summary — a model output-quality quirk of that specific model's function-calling maturity, not a wiring defect; the `MCP_AUDIT` trail is the reliable signal, not the rendered text.

Verified via `mvn test` (2022/2022, zero regressions — 2020 prior + 2 new, covering real-tool-calling success and real-tool-calling-throws-falls-back-to-legacy).

### Phase 11.1 — Enterprise Intent Engine: a richer classification layer, still not wired to the Copilot
`ai/careerpilot/intent/` is the first increment of the six-part Phase 11 master plan (Phases 11.2–11.6 — Capability Planner, Multi-Capability Execution, Enterprise Memory Evolution, Proactive Career Intelligence, Autonomous Career Agent — are explicitly **not yet built**; the phase spec itself mandates incremental delivery with validation between each). Per the Phase 11 target architecture (`Copilot → Intent Engine → Capability Planner → Capability Engine → ...`), Intent Engine is a new layer sitting *above* the existing Phase 10.3 Capability Engine, not a replacement for it — `ai.careerpilot.capability` is untouched.

Pipeline: `IntentResolver` (`KeywordIntentResolver` — scores each registered `IntentDefinition` by keyword-substring matches, deliberately the ML-swap seam: a future embedding/LLM classifier implements the same interface) → `IntentClassifier` (`DefaultIntentClassifier` — ranks by score, ties broken by `IntentDefinition.priority()`, e.g. the more specific `GITHUB_ANALYSIS` beats `CAREER_STRATEGY` on an equal-score tie) → `IntentEngine` (`DefaultIntentEngine` — accepts the top candidate only above `intent.engine.min-confidence` (default 0.4), else an explicit reasoned fallback; never throws). `IntentType` is a **separate, richer taxonomy from `CapabilityType`** — 7 values including `EXECUTIVE_COACH`, which has no Phase 10.3 capability equivalent yet (anticipating a future capability the spec's own examples require). `IntentHistory` (`InMemoryIntentHistory`, bounded 50-entry-per-user ring buffer) and `IntentMetrics` (`InMemoryIntentMetrics`) exist for a future Capability Planner to consult — nothing reads them yet.

Single flag, unlike Phase 10.3's four-flag layering: `intent.engine.enabled` (default `false`, `IntentConfig` the only bean source — matches the phase spec's own single-flag requirement exactly). **Not wired into `CopilotService` or anything else** — this is deliberate scope discipline, not an oversight: Phase 11.2's Capability Planner is what will map a classified `IntentType` down to `CapabilityType`(s) and route into the existing Phase 10.3/10.4 pipeline; connecting Intent Engine directly to the Copilot now would bypass that not-yet-built planner.

Verified via `mvn test` (1885/1885, zero regressions — 1853 prior + 32 new) plus an `ApplicationContextRunner` end-to-end test (`IntentConfigTest`) that wires the real bean graph and classifies an actual message, and a dedicated test exercising every one of the phase spec's own worked examples ("I keep getting rejected" → Resume Analysis, "Can I crack Amazon?" → Interview Preparation, etc.) through the real resolver+classifier.

### Phase 11.2 — Capability Planner: bridges Intent Engine and Capability Engine, still not executing anything
`ai/careerpilot/planner/` answers the Phase 11.1 package javadoc's own promise: the first code that maps a classified `IntentType` down to one or more `CapabilityType`s (Phase 10.3, byte-for-byte unchanged). Per the Phase 11 target architecture, this is planning-only — Phase 11.3 (Multi-Capability Execution, not yet built) is what will actually execute a `CapabilityPlan`; `CapabilityPlanner` is not called by the Copilot, `CapabilityAwareChatService`, or anything else yet.

`DefaultCapabilityPlanner`'s `IntentType → List<CapabilityStep>` mapping is a static `Map` today (six of the seven Phase 11.1 intents map 1:1 onto an identically-shaped Phase 10.3 capability); `EXECUTIVE_COACH` — which still has no dedicated capability — is the one worked multi-capability example, mapping to `{CAREER_STRATEGY (HIGH), JOB_RECOMMENDATION (MEDIUM)}` with an explicit `CapabilityDependencies` edge (job recommendations should be informed by an already-computed career strategy). `DefaultPlanOptimizer` resolves steps + dependencies into a stage-by-stage `ExecutionOrder` via Kahn's-algorithm topological sort (each stage a list of capabilities safe to run in parallel — the shape a future Phase 11.3 `ParallelCapabilityExecutor` would consume) with priority-based ordering within a stage; a dependency cycle (never produced by today's static mapping, but a future dynamic one could) degrades to one combined stage rather than looping or throwing, matching the same never-fail discipline as every prior Phase 10/11 engine.

Single flag, gated the same way as Phase 11.1: `capability.planner.enabled` (default `false`, lives under the pre-existing top-level `capability:` YAML block alongside Phase 10.3's `capability.engine.enabled` — not a duplicate key). `CapabilityPlannerMetrics` (plan latency, plan size, cycle-detection count) is intentionally separate from Phase 10.3's `CapabilityMetrics` — planning and execution are different concerns measured at different layers.

Verified via `mvn test` (1901/1901, zero regressions — 1885 prior + 16 new), including an `ApplicationContextRunner` end-to-end test wiring the real bean graph and producing an actual multi-stage plan, and dedicated topological-sort tests (independent steps → one parallel stage, a real dependency → two ordered stages, an out-of-plan dependency ignored rather than blocking, a forced cycle → graceful one-stage degrade).

### Phase 11.3 — Multi-Capability Execution: actually runs a plan, still not called by anything live
`ai/careerpilot/planner/execution/` is the layer that turns a Phase 11.2 `CapabilityPlan` (planning output only) into a real, executed `MultiCapabilityResult` — multiple capabilities (resume, GitHub, memory, jobs, career strategy) genuinely running in one request. Still not wired into the Copilot or any controller — `ExecutionCoordinator` is the intended future call site for whichever phase eventually connects Intent Engine → Capability Planner → this layer → Spring AI synthesis.

`DefaultCapabilityExecutor` executes ONE capability by reusing the existing Phase 10.3 `CapabilityRegistry`/`ToolSelectionEngine` to resolve its MCP tools and the existing Phase 10.2 `McpExecutor` to run them — no duplicated tool-resolution logic, and never a tool handler called directly (same security contract as every prior phase). A step is retried (whole-step, not per-tool) up to `multi.capability.max-retries` (default 1) additional times before being recorded as a partial failure. `DefaultParallelCapabilityExecutor` runs one stage's capabilities concurrently via `CompletableFuture` — safe because Phase 11.2's `PlanOptimizer` already guarantees no dependency within a stage, mirroring the exact parallel shape Phase 10.3's `CapabilityAwareChatService.executeTools` established one layer down (over MCP tools instead of whole capabilities). `DefaultExecutionCoordinator` walks `ExecutionGraph.from(plan)` stage by stage — sequential between stages (a later stage may depend on an earlier one's results), parallel within — and a failed capability in one stage never stops later stages from attempting to run. `DefaultResultMerger` produces a genuinely structured `MergedExecutionContext` (a `Map<CapabilityType, Object>` of successful results plus a rendered text block noting failures) rather than concatenating raw strings, per the phase spec's explicit requirement.

Single flag, same pattern as 11.1/11.2: `multi.capability.enabled` (default `false`). `CapabilityRegistry`/`ToolSelectionEngine`/`McpExecutor` are all injected as `ObjectProvider`s (their own independent flags — `capability.engine.enabled`/`mcp.enabled`) — `DefaultCapabilityExecutor` degrades to an explicit failed `ExecutionResult` rather than throwing if either underlying layer is off.

Verified via `mvn test` (1925/1925, zero regressions — 1901 prior + 24 new), including a timing-based test proving three simulated 100ms tool calls complete in well under the ~300ms sequential baseline (genuine concurrency, not just API shape), a real retry-then-succeed test, a partial-failure test confirming later stages still execute after an earlier stage's failure, and a full `ApplicationContextRunner` flag-gating test.

### Phase 11.4 — Enterprise Memory Evolution: a new classification layer, additive alongside every existing memory subsystem
`ai/careerpilot/memory/enterprise/` adds the 8-category memory taxonomy from the phase spec (WORKING/LONG_TERM/CAREER/DECISION/CONVERSATION/SKILL/PREFERENCE/LEARNING) as a **new layer that does not replace anything**: `ai.careerpilot.memory.CareerMemoryService` (Phase 7.15.1, still the backing store for the Phase 10.2 Memory MCP server), `ai.careerpilot.memory.conversation` (conversation-derived decision extraction), and `ai.careerpilot.service.ConversationMemory` (Copilot chat history) are all untouched — this package is a parallel, broader classification system, not wired to read from or write into any of them.

`DefaultMemoryClassifier` (keyword rules, the same ML-swap-seam discipline as `ai.careerpilot.intent.KeywordIntentResolver`) assigns both a `MemoryType` and a `MemoryImportance` (score + CRITICAL/HIGH/MEDIUM/LOW band, same shape as `IntentConfidence`) to freshly-remembered content, landing anything unclassified in `WORKING` — the deliberately transient default. `DefaultMemoryConsolidator` is the working-memory → long-term lifecycle the spec asked for: a `WORKING` entry accessed at least `promotion-access-threshold` times gets promoted (re-classified, or generic `LONG_TERM` if still ambiguous) regardless of age; one that ages past `working-ttl-hours` without enough access is evicted outright; anything neither aged nor frequently accessed is left alone. `DefaultMemoryRetriever` marks every entry it returns as accessed, which is what actually feeds the consolidator's access-count rule — the two are deliberately coupled.

Entirely in-memory (`InMemoryMemoryStore`, an unbounded-until-capacity per-user map) — **no new Flyway migration**, matching the phase's "ZERO database breaking changes" requirement exactly; a future phase wanting durability would replace that one class only. `DefaultMemoryManager` enforces `max-entries-per-type` per user, evicting the single lowest-importance (oldest tie-break) entry of that type before a new one would exceed the cap — a bounded structure, not unbounded growth.

Single flag, same pattern as every prior Phase 11 sub-phase: `enterprise.memory.enabled` (default `false`, `EnterpriseMemoryConfig` the only bean source). Not wired into the Copilot, any controller, or any of the existing memory subsystems — `MemoryManager`/`MemoryRetriever`/`MemorySearch`/`MemoryConsolidator` are ready-to-wire but currently only reachable from tests.

Verified via `mvn test` (1962/1962, zero regressions — 1925 prior + 37 new), including a capacity-eviction test (lowest-importance entry evicted first when a type hits its cap), and dedicated consolidation tests for all four branches (frequent-access promotion, unclassifiable-content-falls-back-to-LONG_TERM, aged-and-unused eviction, fresh-and-unused left untouched).

### Phase 11.5 — Proactive Career Intelligence: read-only insight detection over existing data, still not scheduled or wired
`ai/careerpilot/career/monitor/` detects the 7 proactive-insight categories the phase spec names — new job matches, resume outdated, missing certifications, salary below market, promotion readiness, interview reminders, learning suggestions — as thin read-only wrappers around data that already existed before this phase, the same discipline as every Phase 10.2 MCP tool: `JobRecommendationRepository` (job matches), `ResumeRepository.createdAt` (resume staleness), `CareerStrategy.skillGapsJson`/`promotionReadinessJson` (learning/certification/promotion signals — presence-only, this package never parses that JSON's internal shape), `Offer.baseSalary` vs. `Offer.marketP50` (salary below market), `Interview.scheduledAt` (interview reminders). No new query beyond existing finder methods, no new table, no fabricated signal.

`CareerOpportunityDetector` covers job matches specifically; `CareerEventEngine` covers the other six — each check independently try/caught inside `DefaultCareerEventEngine`/`DefaultCareerMonitor` so one missing/absent data source (no resume, no career strategy row, no offer) simply produces no alert for that category rather than an error. `CareerTimeline` (in-memory, bounded per-user ring buffer, same shape as Phase 11.1's `InMemoryIntentHistory`) is what stops the same alert firing every run — `DefaultCareerMonitor` suppresses anything surfaced within `alert-cooldown-days` (default 7) before handing the rest to `CareerRecommendationEngine` for severity-ranked, capped prioritization.

Single flag, same pattern as every prior Phase 11 sub-phase: `career.monitor.enabled` (default `false`, merged into the pre-existing top-level `career:` YAML block rather than a duplicate root key — that block already holds `career.orchestrator.*`/`career.relevance.*`/etc. from earlier phases). Not wired into any scheduler or controller — compare to the already-shipped, already-wired `ai.careerpilot.dailydiscovery` package, which this does not replace or connect to.

One real bug caught by its own test suite: the resume-outdated and interview-reminder alerts originally built their `evidence` map with `Map.of(...)`, which throws `NullPointerException` on a null value — and entity ids are null for any not-yet-persisted row (every unit test, and potentially a real not-yet-flushed entity). Fixed with a null-tolerant `HashMap`-based helper.

Verified via `mvn test` (1994/1994, zero regressions — 1962 prior + 32 new).

### Phase 11.6 — Autonomous Career Agent: closes the Phase 11 series, task dispatch deliberately deferred
`ai/careerpilot/career/agent/` is the sixth and final sub-phase of the Phase 11 master plan. It closes the observe → plan → reflect loop: `AutonomousCareerAgent.runOnce(userId)` checks `TaskScheduler` for run eligibility (in-process cadence tracking, default 24h — not Spring's `@Scheduled`, nothing auto-triggers this), observes via Phase 11.5's `CareerMonitor` (`AgentObservation.from(CareerInsights)` — wraps its `recommendations()` directly, or an empty observation if that layer's own independent `career.monitor.enabled` flag is off or it throws), plans via `DefaultAgentPlanner` (a static `CareerAlertType → AgentTaskType` map, the same style as Phase 11.2's intent-to-capability mapping), dispatches each planned task, reflects, and remembers via `AgentMemory` (bounded per-user ring buffer, same shape as every other Phase 11 history component).

**Task dispatch is deliberately deferred, not real.** Every one of the 8 autonomous task categories the phase spec names already has a real, existing engine somewhere in this codebase — daily job discovery (`JobDiscoveryScheduler`/`DailyJobDiscoveryScheduler`), ATS resume optimization (Phase 2D.2), Phase 3A application tracking, interview planning (`InterviewService`/`StarStoryEngine`), career/learning roadmap generation, skill gap detection (`SkillGapIntelligenceService`), salary trend monitoring (`OfferAnalysisService`). Per the Phase 11 mission's explicit "DO NOT replace any existing subsystem," `DeferredAgentTaskExecutor` — the only `AgentTaskExecutor` shipped in this phase — always returns `TaskOutcome.DEFERRED` rather than calling any of them. The full loop is genuinely exercised end-to-end against real Phase 11.5 signals; only the final "actually do it" step is a documented placeholder, the same honesty discipline as `Context7ApiClient`'s "best-effort, not live-verified" caveat.

Single flag, gated the same way as every prior Phase 11 sub-phase: `career.agent.enabled` (default `false`, merged into the pre-existing top-level `career:` YAML block as a `agent:` sibling to `career.monitor.*`). Verified via `mvn test` (2020/2020, zero regressions — 1994 prior + 26 new). One flaky-test bug found and fixed during this phase: a `Duration.ZERO`-interval eligibility test raced against clock resolution (last-run and "now" landing in the same instant); fixed with a real `Thread.sleep` gap, not a production code change.

**Phase 11 is now complete**: Intent Engine (11.1) → Capability Planner (11.2) → Multi-Capability Execution (11.3) → Enterprise Memory Evolution (11.4) → Proactive Career Intelligence (11.5) → Autonomous Career Agent (11.6). Every sub-phase shipped dark-by-default, additive, and standalone-tested; none replaced an existing subsystem. Unlike Phase 10 (where 10.4 was the deliberate "connect it to production" phase), no Phase 11 sub-phase wires into the Copilot, a scheduler, or any controller — that remains open, deliberately, for a future phase.

### International Job Discovery Engine, Phase 1 — country-tier relocation program, dark by default
`ai.careerpilot.jobdiscovery.international` adds the first slice of a config-driven relocation-jobs program on top of the *existing* Domestic/International infrastructure (`JobProvider`, `JobScopeStrategy`, `JobMatchingService`/`JobScoring`) rather than rebuilding any of it — this phase is deliberately thin: seniority/title eligibility, curated country intelligence, a separate weighted ranking, and read-only endpoints/dashboard. A much larger spec (≈20 job sources, OpenSearch, Kafka events, a LangGraph/MCP surface, weekly reports, hexagonal rewrite) was scoped down after review: most of it either already exists in some form, is infeasible without scraping/ToS violations, or is genuine future-phase work — see "Out of scope" below.

**Config-driven country tiers** (`V69__international_country_tiers.sql`) — `supported_countries` (country_code, display_name, tier TIER_1/2/3, active), seeded for Germany/Netherlands (Tier 1), Ireland/Canada/Australia (Tier 2), Luxembourg (Tier 3). `SupportedCountryService` is a second, independent gate from the existing `InternationalScopeStrategy` (which answers "which countries can *this candidate* see," from their profile) — this one answers "is this country part of the Phase-1 program at all." Future countries (USA, Singapore, Japan, etc.) are a data-only row insert, never a code change. Every method on `SupportedCountryService` returns the empty/false case when `career.international.tiering.enabled` is off (default), matching this codebase's "master switch = byte-identical no-op" convention — including the read-only `/api/jobs/international/countries`/`/intelligence` endpoints.

**Seniority + title eligibility** — `SeniorityLevelClassifier` (reuses the existing `JobTaxonomy.seniorityLevel`, no new title-parsing logic) accepts SENIOR/LEAD/PRINCIPAL and rejects an explicit intern/junior/graduate/trainee/contract/part-time list; `InternationalRoleTaxonomy` holds the program's fixed 27-title allow-list (whole-word-or-role-family match, same style as `RoleExclusionFilter`). `InternationalEligibilityFilter` combines both behind two independent flags (`career.international.seniority-filter.enabled` master, `career.international.title-allowlist.enabled` the more aggressive sub-gate) and is wired as one more no-op-when-off `.filter()` stage into `JobMatchingService.refreshForUser`'s existing chain and `JobService.discovered`'s existing scope-aware post-filter pattern — zero change to either when the flag is off.

**Country Intelligence** (`V70__country_intelligence.sql`) — `country_intelligence`: nine curated 0–100 scores per country (visa probability, relocation difficulty, language requirement, cost of living, expected savings, job stability, tech market, principal-engineer growth, AI market) plus a `source_note` provenance column. **Explicitly static/curated, not live-computed** — there's no real data source for e.g. live visa-approval probability; values are placeholder-but-defensible and should be reviewed against real published indices before being relied on for a real decision.

**International ranking** (`V71__international_job_ranking.sql`) — `InternationalJobScoring` implements the program's exact weighted formula (40% skill / 15% visa probability / 10% salary / 10% career growth / 10% company stability / 5% remote flexibility / 5% principal-engineer growth / 5% AI tech stack), deliberately separate from `JobScoring.scoreV2`'s own weights (40/25/20/10/3/1/1) and written to a **new parallel table** rather than new columns on `job_recommendations` — two independently-weighted formulas for two different purposes (relocation viability vs. general job fit) stay structurally independent. `JobScoring` gained two new `public` (previously private/inline) helpers, `skillScoreOnly(...)` and `salaryScore(...)`, extracted with zero behavior change to `scoreV2` itself (verified: the full pre-existing `JobScoring`/`JobMatchingService` test suite stayed green after the extraction) — `InternationalJobScoring` reuses these rather than duplicating the logic. `InternationalJobRankingService` mirrors `JobMatchingService.refreshForUser`'s shape and rides the *same* refresh trigger points (`JobRecommendationService.rebuild()` and the page-0 implicit refresh in `recommend()`), try/catch isolated so a ranking failure never blocks the existing recommendation refresh. **Depends on two flags, not one**: `career.international.ranking.enabled` gates the write path itself, but `SupportedCountryService#byDisplayName` (used to resolve each candidate country into a Phase-1 row) also requires `career.international.tiering.enabled` — both must be on before this service writes anything, the same layered pattern as Phase 2D's `<stage>.enabled` + `<stage>.trigger.enabled`.

**Providers** — `AdzunaProvider` gained `ie` (Ireland) to its country-name/currency maps and its default country list (`gb,us,in,ie,au`); Luxembourg has no Adzuna coverage and ships thin in Phase 1 (documented gap, no fabricated endpoint). Three new dark-stub providers — `LinkedInProvider`/`IndeedProvider`/`GlassdoorProvider` — are exact structural copies of the existing `TaleoProvider` convention: `isConfigured()` is permanently `false` (none of the three has a free/ToS-compliant public search API — scraping any of them violates their ToS), with a diagnostics-only `isFlagEnabled()` mirroring the flag without ever affecting `isConfigured()`.

**New read-only API** — `InternationalJobController` (`/api/jobs/international/{countries,intelligence/{code},ranked,dashboard}`), entirely additive; `GET /api/jobs/discovered` and `GET /api/jobs/recommended` are untouched byte-for-byte. `/ranked` composes (never replaces) the existing job shape with the new ranking + country-intelligence data and returns an empty page rather than erroring when the ranking flag is off or the user has no rows yet. `/dashboard` (`InternationalDashboardService`) is plain in-memory aggregation over the current user's own `international_job_ranking` rows plus their jobs/applications — not a new analytics pipeline.

**Frontend** — `PreferencesDialog.tsx` gained a tier-grouped country picker (click-to-add into the existing free-text `preferredCountries` field) sourced from `/countries`; `JobBadges.tsx` gained `CountryTierBadge`/`SeniorityBadge`; `ExplainDialog.tsx`'s existing "why am I a match" panel now additionally renders a compact country-intelligence block when ranking data exists for that job's country (conditional, no change to the domestic-path rendering). New page `InternationalDashboard.tsx` (route `/jobs/international/dashboard`, linked from the International tab header) reuses the exact Recharts + CSS-variable-token styling already established in `Dashboard.tsx` — no new charting library, no new design tokens.

**Flags** (all new, all default `false`): `career.international.tiering.enabled`, `career.international.seniority-filter.enabled`, `career.international.title-allowlist.enabled`, `career.international.ranking.enabled`, `career.discovery.linkedin.enabled`/`indeed.enabled`/`glassdoor.enabled` (the last three diagnostics-only).

**Out of scope for Phase 1** (deferred to future, separately-requested phases): real LinkedIn/Indeed/Glassdoor integration (never planned — ToS-prohibited, stubs stay dark permanently); a generic Personio/Recruitee crawler; OpenSearch-based faceted search/heatmaps (pgvector + Postgres suffice at Phase 1 scale); new Kafka event types for discovery milestones; a LangGraph/MCP-exposed agent or tool surface for the international engine; weekly email/notification reports (would reuse `DailyCareerSummaryGenerator`'s existing pattern rather than a new pipeline); admin CRUD UI for `supported_countries`/`country_intelligence` (read-only + migration-seeded in Phase 1); a candidate-side "relocation support required" preference (Phase 1 relies solely on the existing job-side `relocation_support` boolean); expansion beyond the 6 seeded countries.

Verified via `mvn test` (2043/2043, zero regressions — 2022 prior + 21 new) and `npx tsc --noEmit` + `npx vitest run` (frontend, zero errors). Live-verified end-to-end: `docker compose build backend` initially silently failed on the recurring `docker-credential-desktop` PATH bug (same fix as documented elsewhere in this file — remove `credsStore` from `~/.docker/config.json`) and produced a stale image missing the new migrations without the compose command reporting a nonzero exit — always verify a freshly-built image actually contains new migration files (`docker run --rm --entrypoint sh <image> -c "unzip -l /app/app.jar | grep db/migration"`) before trusting a "successful" build. Once rebuilt correctly, Flyway applied V69–V71 cleanly on the live Neon database; with all flags at default `false`, `/api/jobs/international/countries` returns `[]` and `/dashboard`/`/ranked` return empty/zero — confirmed byte-identical to off; with `career.international.tiering.enabled=true`, `/countries` returned the 6 seeded countries with correct tiers and `/intelligence/de` returned real seeded scores, `/intelligence/xx` correctly 404'd.

### Mission Engine, Phase 1 — the long-term "what a user is trying to become," stable by design
`ai.careerpilot.mission` (+ `CareerMission`/`CareerGoal`/`UserCareerPreference` in `domain`, `V72__career_mission.sql`) is a small, deliberately un-clever CRUD layer: a user's long-term career mission ("Become Principal Java AI Architect in Europe within 24 months") plus its milestones (`CareerGoal`) and soft preference signals (`UserCareerPreference`). No caching, no events, no state machine — `MissionStatus` (ACTIVE/PAUSED/COMPLETED) is a plain field update via `MissionService.update`. Countries/industries/skills are JSONB string lists (via the existing `JsonLists` helper, reused rather than reimplemented), never enums — "countries are data, not code."

**`UserCareerPreference` is deliberately NOT a duplicate of `candidate_preferences`** (V5/V9/V10 migrations, backing `CandidatePreferences` — already owns location/salary/visa/remote-mode preferences, consumed by job matching). This new table holds only what that one doesn't: risk tolerance, preferred company stage, work-culture priority, mentorship preference, relocation willingness. No REST surface for `CareerGoal`/`UserCareerPreference` in Phase 1 — just the data model, per the phase's stated principle that future AI agents will consume Mission data (none do yet).

Ownership is scoped by `userId` (manual isolation, same convention as everywhere else in this codebase); a mission belonging to another user 404s identically to a non-existent one (`MissionNotFoundException extends NoSuchElementException`) — a security-conscious choice, not a limitation. `PUT /api/missions/{id}` is a full REST replace (omitted fields become null/empty on update — verified live), not a partial PATCH.

API: `POST/GET/PUT/DELETE /api/missions[/{id}]`, plus `GET /api/missions` (list) as a small non-spec addition for basic usability. Verified via `mvn test` (2061/2061 — 2043 prior + 18 new) and live end-to-end against Neon (full create→read→list→update→delete→404-after-delete cycle).

### Country Intelligence Engine, Phase 2 — extends Phase 1's country data, does not fork it
A near-duplicate of International Job Discovery Engine Phase 1's `country_intelligence` table was explicitly avoided here: rather than a new `country_profile` entity, `V73__country_intelligence_profile_fields.sql` **adds 5 columns to the existing `country_intelligence` table** (`visa_information`, `salary_information`, `technology_demand` JSONB, `remote_policy`, `priority_score`), seeded with real descriptive content for the same 6 Phase-1 countries. One source of truth for per-country data, not two tables that can drift out of sync — see the `CountryIntelligence` entity's own javadoc for the explicit rationale.

**`CountryMatchingCapability`** (`ai.careerpilot.jobdiscovery.international`) is the phase's one genuinely new piece: deterministic (no LLM, same discipline as `InternationalJobScoring`) Mission-to-country fit scoring. `rankForMission(CareerMission)` scores every active supported country: a base score (visa probability + job stability + tech market, blended 70/30 with principal-engineer-growth when the mission's `targetLevel` reads as senior/staff/principal/architect/lead), a tech-overlap bonus (mission's current+to-acquire skills vs. the country's `technology_demand` list, via the shared `JobTaxonomy` skill-family matching — up to +15), and a preferred-country bonus (+20 if the country is in the mission's `targetCountries`), clamped to 100 — plus a human-readable explanation string built from the same components. Never fabricates a country outside `supported_countries`; degrades to a neutral 50 with an explicit "no curated intelligence" explanation for a supported country with no intelligence row, rather than throwing.

New `CountryController` (`GET /api/countries`, `GET /api/countries/{code}`, `GET /api/countries/{code}/career-fit?missionId=`) is a separate URL namespace from Phase 1's `/api/jobs/international/*` (this phase's country data serves the Mission system, not only job discovery) but the SAME underlying `SupportedCountryService`/`CountryIntelligenceService` — inherits the same `career.international.tiering.enabled` gate transitively, no new flag introduced. `career-fit` defaults to the user's most recent ACTIVE mission when `missionId` is omitted, 404ing with a clear message if the user has none (an expected state for a new user, not a server error).

Verified via `mvn test` (2072/2072 — 2061 prior + 11 new) and live end-to-end against Neon: created a mission targeting Germany/Netherlands with Java/Spring Boot/Cloud skills, `GET /api/countries/de/career-fit` scored 100 (target-country + 3-skill overlap), `GET /api/countries/ie/career-fit` (non-target, partial overlap) scored 84 — confirming the weighting behaves as designed.

**Known architecture overlap flagged for Phase 4+, not yet reconciled**: the user's broader vision beyond Strategy Engine (Mission Orchestrator, Workflow Registry, Capability Layer, Daily Career Coach, Autonomous Career Agent) describes, near-component-for-component, infrastructure that **already exists** in this codebase under different names — `AiGatewayService` (the described "AI Gateway"), `ai.careerpilot.mcp` (the described "MCP"), `ai.springai` (the described "Spring AI layer"), `ai.careerpilot.capability` Phase 10.3 (the described "Capability Layer"), the LangGraph graph in `agent-service/app/graph.py` (the described "LangGraph Workflows" — its 8 nodes already closely match the phase spec's named example workflows), `dailydiscovery`/`DailyCareerSummaryGenerator` (the described "Daily Career Coach"), and `ai.careerpilot.career.agent` Phase 11.6 (the described "Autonomous Career Agent," though task dispatch is still deferred). Strategy Engine (Phase 3, below) got exactly this reconciliation treatment before being built; Phase 4+ (Mission Orchestrator etc.) will need the same pass first.

### Strategy Engine, Phase 3 — converts a Mission into an actionable, trackable plan
`ai.careerpilot.strategy` (+ `StrategyPlan` in `domain`, `V74__strategy_plan.sql`) turns a `CareerMission` into a concrete, completable action list. **Deliberately does not touch `career_strategy`** (Phase 6.6's single-row-per-user computed AI/probability snapshot — narrative text blobs like `recommendedTrajectory`/`roadmap3Month`, not discrete completable items; a fundamentally different shape, confirmed by reading the entity before building this phase). Also deliberately does **not** introduce a `strategy_action` table: `CareerGoal` (Mission Engine, Phase 1) already has exactly the shape an action needs — title, completable `MissionStatus` — so Phase 3 reuses it, adding a nullable `strategy_plan_id` FK column. And no separate `strategy_history` table either: `StrategyEvaluationService.generate` always inserts a **new** `StrategyPlan` row rather than updating one in place, so the table is its own append-only history — `findByMissionIdOrderByGeneratedAtDesc` reads it directly.

`StrategyEvaluationService` is rule-based and deterministic (no LLM) — the phase's own spec calls this out explicitly as the intended Phase 1 approach, LLM-generated (Spring AI) strategy stated as a future extension point, same "rule-based now, AI later" discipline as `CountryMatchingCapability`. Generation logic: one "Improve `<skill>` knowledge" action per mission `skillsToAcquire` entry, one "Apply for `<targetRole>` positions" action, and a "Practice system design" action added only when `targetLevel` reads as senior/staff/principal/architect/lead — live-verified to reproduce the phase spec's own worked example (Kubernetes, apply for architect positions, practice system design) near-verbatim. `timeframeDays` derives from the mission's `timelineMonths` (× 30, capped at 24 months) or defaults to 90.

API: `POST /api/strategy/generate` (body `{missionId}`, always creates a new plan), `GET /api/strategy/{missionId}` (latest plan + its actions), `PUT /api/strategy/action/{id}/complete`. Ownership is enforced via the parent mission's `userId` (same 404-not-403 convention as `MissionNotFoundException`). Verified via `mvn test` (2083/2083 — 2072 prior + 11 new) and live end-to-end against Neon: generated a plan from the Germany/Netherlands mission created in Phase 2's test, got the exact 4 actions described above, read them back via `GET`, and completed one via `PUT`.

### Workflow Registry, Phase 4 — a declarative catalog, deliberately not an execution engine
`ai.careerpilot.workflowregistry` (+ `WorkflowDefinition`/`WorkflowExecution` in `domain`, `V75__workflow_registry.sql`) is a DB-backed catalog of reusable workflow *types* (`JOB_DISCOVERY_V1`, `RESUME_OPTIMIZATION_V1`, `INTERVIEW_PREPARATION_V1`, `SKILL_ANALYSIS_V1`, `CAREER_STRATEGY_V1` — all 5 seeded by the migration) — genuinely new, since nothing in this codebase already exposes workflow types as DB-stored, registerable metadata (the closest existing thing, the LangGraph graph in `agent-service/app/graph.py`, is a hardcoded Python pipeline, not a queryable registry).

**`execute` deliberately always produces a `DEFERRED` `WorkflowExecution` row today** — every workflow type in the catalog already has a real engine somewhere in this codebase (the LangGraph pipeline via `WorkflowService` for the standard flow), and per this file's own existing rule ("do not expose the agent service to the frontend — funnel it through `WorkflowService`"), this registry does not bypass that by invoking the agent-service directly. Same honesty discipline as `DeferredAgentTaskExecutor` (Phase 11.6) — a documented placeholder, not a fabricated integration. A future phase can make `execute` real by dispatching to the appropriate existing service per `workflowType`.

**Unlike every later addition to this stack (Workflow Planner, Mission Execution Engine, LangGraph Workflow Runtime — all below), `WorkflowRegistryController`/`WorkflowRegistryService`/`WorkflowExecutionService` are plain `@Service`/`@RestController` beans with no feature flag** — the catalog-lookup and register/execute endpoints are live and reachable in production today, not dark. This is safe only because `execute()` is neutered to the `DEFERRED` no-op described above; it is not itself gated the way its siblings are, so don't assume a flag exists here when auditing what's "wired" versus "dark" in this file.

**Route collision caught and fixed before shipping**: the phase spec's literal `GET /workflows` path was already owned by the existing `WorkflowController` (LangGraph `WorkflowRun` history, Phase 3A — a different, pre-existing concept) — Spring Boot failed to boot with an "Ambiguous mapping" error on first live-deploy attempt. Fixed by moving the registry's list endpoint to `GET /api/workflow-definitions`; `POST /api/workflow/register` and `POST /api/workflow/{id}/execute` (singular `/workflow/`) never collided.

API: `GET /api/workflow-definitions`, `POST /api/workflow/register`, `POST /api/workflow/{id}/execute`. Verified via `mvn test` (2091/2091 — 2083 prior + 8 new) and live end-to-end against Neon: listed the 5 seeded definitions, executed `JOB_DISCOVERY_V1` and got a `DEFERRED` record with an honest explanatory note.

### Mission Orchestrator, Phase 5 — recommends workflows, never executes them
`MissionOrchestratorService` (`ai.careerpilot.mission`, + `MissionExecution`/`WorkflowDecisionLog` in `domain`, `V76__mission_orchestrator.sql`) reads a Mission's current state — its latest `StrategyPlan`'s actions (Phase 3) and the most recent resume score from `WorkflowRun` — and produces a ranked, explained list of Workflow Registry (Phase 4) recommendations via simple deterministic rules (no LLM, same discipline as `StrategyEvaluationService`/`CountryMatchingCapability`): no plan yet → recommend `CAREER_STRATEGY_V1` only; incomplete "Improve X" actions → `SKILL_ANALYSIS_V1`; resume score below 75 → `RESUME_OPTIMIZATION_V1`; an incomplete "Apply for X" action → `JOB_DISCOVERY_V1`; a completed one → `INTERVIEW_PREPARATION_V1`.

**Recommends, never executes** — matches the "human approval required before autonomous action" principle running through every acting subsystem in this codebase (Phase 2E's `ApprovalService`, Phase 7's `AutoApplyEngine`). `mission_execution` is one row per orchestrator run (append-only, so it's its own history); `workflow_decision_log` holds that run's ranked recommendations.

API: `POST /api/orchestrator/run/{missionId}`, `GET /api/orchestrator/status/{missionId}`. Verified via `mvn test` (2099/2099 — 2091 prior + 8 new) and live end-to-end against Neon: running the orchestrator against the Phase 3 mission (one skill action already completed, others still open) correctly recommended `SKILL_ANALYSIS_V1` + `JOB_DISCOVERY_V1` with accurate reasons, skipping the already-completed action.

**Phase 4/5 live-deploy notes**: Docker Desktop crashed mid-session (all containers exited); restarting it re-triggered the recurring `docker-credential-desktop` PATH bug (fixed the same way as documented elsewhere in this file) and Kafka's stale-broker-registration race (fixed with a plain `docker restart kafka`) — both transient, both already-known issues, not code problems.

### Phase 7A — Mission-Aware Autonomous Career Agent: the agent stays the single execution coordinator
`ai.careerpilot.career.agent` (Phase 11.6's `AutonomousCareerAgent`, extended — not forked) gained mission awareness: `AgentObservation` carries an optional `MissionContext`, `DefaultAgentPlanner` gained a mission-first planning branch (a `WorkflowType → AgentTaskType` map) that takes priority over the pre-existing Phase 11.6 observation-based planning when mission context is present, and `DefaultAutonomousCareerAgent` gained `observeMission()` plus a provisioned-but-unused `ObjectProvider<ai.careerpilot.mission.WorkflowPlanner>` seam (the Phase 6A.1 narrow interface, not Phase 8's — see the naming note in `ai.careerpilot.workflowplanner`'s package-info). All existing constructors are preserved via delegation — zero breaking change to Phase 11.6's shipped shape. Gated by `career.mission.agent.enabled` (default `false`).

**Explicit non-goals, stated by the phase spec itself**: do NOT implement Workflow Planner here, do NOT implement LangGraph workflows, do NOT change production behaviour. The agent remains the single enterprise *execution coordinator* — it decides "what should I execute next" from already-computed mission/strategy state; it never decides WHAT the mission, country, or strategy should be (that stays owned by Mission Engine/Strategy Engine), and — as of this phase — it still doesn't decide *how* a workflow executes or in what order relative to others (that's Phase 8/Pre-Phase 9, below). Verified via `mvn test` (2125/2125 — 2111 prior + 14 new).

### Workflow Planner and Mission Execution Engine — internal capabilities of the Mission Orchestrator, not pipeline stages
Two packages, `ai.careerpilot.workflowplanner` (Phase 8) and `ai.careerpilot.missionexecution` (Pre-Phase-9 Architecture Hardening), together answer the two questions the Mission Orchestrator (Phase 5, above) doesn't: *how* should one workflow execute, and *in what order/policy* should several of them run. They are **owned by the Mission Orchestrator** — internal planning/scheduling capabilities it will call, the same relationship `WorkflowService` has with `AgentServiceClient` — not independent stages in a serial pipeline, and not siblings of Mission Engine/Strategy Engine in the top-level architecture. Ownership here is expressed the normal Java way (the owning service imports and calls the owned interface) rather than by package nesting — see each package's own `package-info.java` for the explicit rationale.

```
Mission Engine
    │
    ▼
Strategy Engine
    │
    ▼
Mission Orchestrator
    │
    ├── Workflow Planner         (HOW one workflow should execute)
    ├── Mission Execution Engine (WHEN / IN WHAT ORDER several execute)
    ├── Workflow Registry        (Phase 4, metadata lookup only)
    └── (future) Approval Manager (not yet built — no class exists today)
    │
    ▼
AI Execution Client              (ai.careerpilot.runtime — WorkflowRuntime/LangGraphWorkflowExecutor)
    │
═══ LANGUAGE BOUNDARY — Java Control Plane ends here, Python AI Execution Plane begins ═══
    │
    ▼
Python AI Execution Plane (agent-service/)
    │
    ▼
Workflow Dispatcher (agent-service/app/dispatcher/ — Phase 10A, generic POST /workflows/{workflowId}/runs;
                      /runs and /skill-gap/runs remain separate, untouched entry points alongside it)
    │
    ▼
LangGraph Runtime — each workflow owns its own StateGraph (app/graph.py's CareerState graph,
                     app/skillgap/graph.py's SkillGapState graph, ...)
    │
    ▼
Workflow Graph → AI Agent Workflows (agent-service/app/agents/*, app/skillgap/agents/*)
    │
    ▼
Capability Layer → Spring AI → MCP → AI Gateway
```

Everything above the language-boundary line is Java; everything below is Python. `ai.careerpilot.runtime` is the only package Java code is allowed to sit in on that boundary — it validates, resolves metadata, and transports a request/response across an HTTP call to `agent-service`; it owns no graph topology, no node execution order, and no LangGraph checkpoint state. See `ai.careerpilot.runtime`'s own `package-info.java` for the full Java/Python ownership table.

**Workflow Planner** (`ai.careerpilot.workflowplanner`, all-new package) converts one `WorkflowPlanRequest` into one `WorkflowPlan` — step breakdown (`WorkflowStep`), `WorkflowExecutionStrategy` (SEQUENTIAL/PARALLEL/CONDITIONAL/HUMAN_APPROVAL/RETRY/SKIP/RESUME_LATER/FUTURE_AI_LOOP), retry/fallback policy, and a deterministic cost/duration/complexity/confidence `WorkflowEstimate` — for a single `WorkflowType` (15 values: Resume, Job Discovery, ATS, Interview, Learning, Salary, Company Intelligence, Offer Evaluation, Visa, Relocation, Mission Progress, Career Strategy, LinkedIn, Networking, Portfolio). It never hardcodes a workflow's existence — `WorkflowSelector` always asks the existing Workflow Registry (Phase 4) via a new non-throwing `latestForType(String)` read added to `WorkflowRegistryService` (one new method, zero change to existing behavior), backed by 10 new seed rows in `V78__workflow_planner_definitions.sql`. Six single-method interfaces (`WorkflowSelector`/`WorkflowStepTemplateProvider`/`WorkflowDependencyResolver`/`WorkflowEstimator`/`WorkflowPlanFactory`/`WorkflowValidator`) each have one `Default*` implementation composed by the `WorkflowPlanner`/`DefaultWorkflowPlanner` facade — no God class. Gated by `workflow.planner.enabled` (default `false`). Verified via `mvn test` (2168/2168 — 2125 prior + 43 new).

**Mission Execution Engine** (`ai.careerpilot.missionexecution`, all-new package) takes several `WorkflowPlan`s at once (via `ExecutionContext`, which also carries mission progress, current per-workflow states, caller-supplied metrics for precondition evaluation, and previous run results) and decides, per workflow: `ExecutionPolicy` (AUTO/MANUAL/BACKGROUND/APPROVAL_REQUIRED/SEQUENTIAL/PARALLEL/SCHEDULED/RETRY/WAIT/BLOCKED/SKIPPED/CANCELLED), `ExecutionPriority` (CRITICAL/HIGH/NORMAL/LOW/OPTIONAL — a new enum, deliberately not a modification of Phase 8's `WorkflowPriority`), a week-number slot (`ExecutionScheduler`, walking a fixed natural sequence — Resume→LinkedIn→Portfolio→Learning→JobDiscovery→ATS→Interview→OfferEvaluation→Visa→Relocation), and blocking via `Precondition`s (e.g. "Resume Score >= 90") plus prerequisite-workflow completion checks (e.g. Interview needs Resume+ATS done). Output is one `MissionExecutionPlan`: `executionOrder`, `executionQueue` (readyNow/waiting/scheduled), `approvalQueue`, `blockedWorkflows`, `retryQueue`, `futureQueue`, `parallelGroups`, plus an aggregate `MissionExecutionEstimate`. **It never executes a workflow — only decides order and policy.** Owns its own bounded per-mission `ExecutionHistory` (`InMemoryExecutionHistory`, 50-entry ring buffer) as an internal collaborator — this is not a peer capability the Orchestrator calls separately. Gated by `execution.engine.enabled` (default `false`). Verified via `mvn test` (2207/2207 — 2168 prior + 39 new).

**Neither package is wired into `MissionOrchestratorService` yet** — both remain dark, self-contained, zero-import capabilities (grep-confirmed: nothing outside each package references its top-level interface). The ownership relationship above describes the intended shape for the future phase that does the wiring — it does not imply the Orchestrator currently calls either one. When that wiring phase happens, `MissionOrchestratorService` takes `ObjectProvider<WorkflowPlanner>`/`ObjectProvider<MissionExecutionEngine>` constructor params, the same optional-collaborator pattern Phase 7A already used for its own `ObjectProvider<ai.careerpilot.mission.WorkflowPlanner>` seam — not a package move, not a new facade class built ahead of a real caller.

### LangGraph Workflow Runtime — Java's AI Execution Client; the language boundary itself
`ai.careerpilot.runtime` (all-new package, **architecturally frozen** as of Phase 9's stabilization pass — see below) is the Java-side **AI Execution Client** in the canonical architecture diagram: the last Java package before the language boundary. Given one already-decided `ExecutionDecision` (from a `MissionExecutionPlan` the Mission Execution Engine already produced), it runs the lifecycle **validate → resolve Workflow Registry definition → build context/state → invoke executor → map result**, and returns a `WorkflowExecutionResult`. It never decides which workflow to run, never inspects `inputs`/`outputs`/`context` payloads (all plain `Map<String, Object>`, passed through opaquely), and never throws past its own boundary — every failure path (validation, not-found, timeout, cancellation, unexpected error) is caught by `DefaultWorkflowRuntime` and returned as a terminal result with a populated `errors` list, never silently discarded.

**Java is the Control Plane; Python is the AI Execution Plane; LangGraph is exclusively a Python concern.** This package owns validation, metadata resolution, transport, and result mapping — it does not and must never own graph topology, node execution order, conditional-edge logic, multi-agent orchestration, or LangGraph checkpoint state (that's `agent-service/app/graph.py`'s `StateGraph`/`CareerState`, entirely in Python). This split was explicitly reviewed and approved; see `ai.careerpilot.runtime`'s `package-info.java` for the full ownership table.

**`WorkflowExecutor` is the clean, swappable abstraction** (`WorkflowExecutor.execute(WorkflowExecutionContext) → WorkflowExecutorOutcome`) — `LangGraphWorkflowExecutor` is the only implementation, delegating to the existing `AgentServiceClient` (a thin, already-generic HTTP wrapper around the Python LangGraph agent-service's `/runs` endpoint). It deliberately does **not** go through `WorkflowService` (the existing 2D/3A caller of `AgentServiceClient`, which assembles its payload from `Resume`/`Job` rows) — that's business logic this runtime is expressly forbidden from owning. The payload it builds is a generic envelope (mission/user/workflow/execution identifiers plus the caller's opaque `inputs`); a future phase that adds real business input assembly as its own capability is what will make the payload match what any given LangGraph node actually expects. `WorkflowRegistryAdapter`/`DefaultWorkflowRegistryAdapter` is the only seam into `ai.careerpilot.workflowregistry`, reusing `WorkflowRegistryService.latestForType(...)` (Phase 8's own lookup) rather than a new query.

**No Approval Manager exists yet**, so `DefaultExecutionRequestValidator` rejects `APPROVAL_REQUIRED` (and `BLOCKED`/`CANCELLED`/`SKIPPED`/`WAIT`) decisions outright rather than silently executing past a control this platform's other acting subsystems (Phase 2E's `ApprovalService`, Phase 7's `AutoApplyEngine`) always enforce. `WorkflowMetrics`/`InMemoryWorkflowMetrics` is the observability extension point — plain `AtomicLong` counters by status and workflow id (same hand-rolled style as `AiMetrics`), explicitly not distributed tracing. `WorkflowLifecycleManager`/`ExecutionTrace`/`ExecutionEvent` handle per-execution timing/event bookkeeping, discarded once mapped into the final result — not a history store (that already exists, unduplicated, as `ai.careerpilot.missionexecution.ExecutionHistory`).

Gated by `runtime.enabled` (default `false`). Like `workflowplanner`/`missionexecution`, it's a top-level sibling package, not nested under `ai.careerpilot.mission` — ownership is expressed by the future caller (the Mission Orchestrator) importing `WorkflowRuntime`, not by package placement. **Not wired into anything yet** — nothing outside this package references `WorkflowRuntime`. Verified via `mvn test` (2250/2250 — 2207 prior + 43 new).

**Phase 9 (AI Execution Plane Integration) is architecturally frozen** as of its stabilization pass: architecture reviewed and approved (Java Control Plane / Python AI Execution Plane boundary confirmed intact — no `GraphNode`/`ConditionalEdge`/`GraphStateMachine`/`GraphExecutor`/`AgentGraph` or any other LangGraph-concept class exists anywhere in this package), documentation tightened so `WorkflowState` cannot be mistaken for LangGraph's `CareerState`, and no code, API, test, or behavior changed during stabilization — only `package-info.java`/class-level javadoc and this section. The platform is ready for Phase 10 (the first real business workflow) to build on this boundary.

### Phase 10 — Skill Gap Intelligence Workflow: the first business workflow, end-to-end through both languages
The first workflow to actually answer a business question — "what skills does the user need to achieve their career mission" — spanning both languages for the first time since Phase 9 froze the boundary. Built entirely on top of the frozen platform (Mission Engine → Strategy Engine → Mission Orchestrator → Workflow Planner → Mission Execution Engine → Workflow Registry) **without modifying any of it**.

**Java side** (`ai.careerpilot.skillgap`, all-new package, gated `skillgap.workflow.enabled`): `SkillGapWorkflowService` is the entire Control-Plane responsibility — validates mission ownership, looks up the `SKILL_GAP_INTELLIGENCE_V1` `workflow_definition` (one new seed row, `V79__skill_gap_analysis.sql`, read via the existing unmodified `WorkflowRegistryService.latestForType`), builds a transport payload from `CareerMission` (target role/level/countries/timeline/current skills — data marshalling, not AI reasoning), invokes Python, and persists the result to the new `skill_gap_analysis` table (one row per run, its own append-only history — same "generate always inserts" convention as `strategy_plan`). `SkillGapController` exposes `POST /api/skill-gap/{missionId}/run`, `GET .../latest`, `GET .../history`.

**Deliberately does NOT reuse `ai.careerpilot.runtime.WorkflowRuntime`/`ai.careerpilot.agent.AgentServiceClient`** (both frozen) — `SkillGapAgentServiceClient` is a new, small, isolated HTTP client calling a new, dedicated Python endpoint (`POST /skill-gap/runs`), rather than routing through the existing shared `/runs` endpoint (the main 8-node career graph), which would have required either misusing that endpoint or modifying a live, shared, already-in-production entry point. See `ai.careerpilot.skillgap`'s package-info for the full rationale — `WorkflowRuntime` remains exactly as Phase 9 left it, unwired and unmodified.

**Naming note**: not the same thing as Phase 7.19.2's `learning.career.goal.SkillGapIntelligenceService` — that's a deterministic, no-LLM frequency count over already-persisted `job_recommendations` matched/missing skills, with no Mission input and no learning roadmap. The two are unrelated and neither calls the other.

**Python side** (`agent-service/app/skillgap/`, all-new package, `app/main.py` gained exactly one import + one `include_router` line): a second, independent `StateGraph` (`SkillGapState`, distinct from `CareerState`) with six nodes — Mission Context (deterministic, no LLM call — the data's already structured) → Resume Intelligence (deterministic fallback when no `resume_text` supplied, else AI-extracted) → Market Intelligence (AI: expected skills per role/country, each pre-classified CRITICAL/IMPORTANT/OPTIONAL) → Skill Gap (deterministic set-difference against the candidate's known skills — no LLM call, free and reproducible) → Learning Roadmap (AI: duration/difficulty/dependencies/business impact per gap) → Mission Readiness (hybrid: `readiness_score`/`confidence`/`mission_progress` computed deterministically from gap counts — never invented — with only the strengths/risks/recommendations narrative going through the AI Gateway). Stateless by design: no `PostgresSaver`/checkpoint table, since this workflow computes-and-returns in one request cycle (no human-approval pause), keeping it resource-light on the 2GB-RAM Oracle Cloud Free Tier VM. All AI calls go through the existing `get_workflow_ai_gateway()` multi-provider failover gateway — no new provider code.

One real bug caught by its own tests: the Mission Context node's id collided with its own output field name (`mission_context`) — LangGraph forbids a node id that matches a state key, the same class of collision the codebase's own `CareerState.salary_insights`/`salary_intelligence` comment already documents. Fixed by naming the node `mission_context_agent` (state field unchanged).

Verified via `mvn test` (2260/2260 — 2250 prior + 10 new) and `pytest` (88/88 — 80 prior + 8 new), including an end-to-end router test that reproduces the phase spec's own worked example (Senior Java Architect, Germany, 8 years, 6 known skills) and gets the exact same `readinessScore: 78` the spec's own example shows.

### Phase 10A — AI Execution Platform generalization: evidence-driven, not speculative
Skill Gap Intelligence (Phase 10) exposed real limitations in the Phase 9 "AI Execution Client": `LangGraphWorkflowExecutor` could only reach the main career graph (`/runs`), and `WorkflowExecutionRequest` required a `WorkflowType` enum value — every new workflow would have needed to modify the frozen `ai.careerpilot.workflowplanner` enum. Phase 10A generalizes the platform against that concrete evidence, **with zero breaking changes** (nothing outside `ai.careerpilot.runtime` called any of this before or after, and Skill Gap itself was not touched). Three ADRs capture the reasoning: `docs/adr/ADR-006-generic-workflow-dispatch.md`, `ADR-007-workflow-registration-strategy.md`, `ADR-008-workflow-execution-contract.md`.

**Python — generic dispatcher** (`agent-service/app/dispatcher/`, new package): `WorkflowDispatchRegistry` (in-process, string-keyed) + `POST /workflows/{workflowId}/runs`, additive alongside the untouched `/runs` and `/skill-gap/runs`. A `WorkflowRegistration` is graph factory + state mapper + output mapper — registering never executes anything. `agent-service/app/skillgap/registration.py` registers the existing skill-gap graph under `SKILL_GAP_INTELLIGENCE_V1`, proving the generic path end-to-end using Skill Gap as a **read-only reference** (its own `SYSTEM`/`SCHEMA`/prompts/state are untouched) — not a migration of Skill Gap onto it. `app/main.py` gained two lines (one router include, one registration call).

**Python — shared AI helper** (`agent-service/app/agent_support.py`, new module): `call_structured_agent(...)` extracts the repeated try/except/log/fallback boilerplate around `gateway.generate_structured_response(...)` that existed in `career_strategy.py` and three of the six skill-gap agents. It never decides what an agent asks for or how to interpret success — each agent keeps its own `SYSTEM`/`SCHEMA`/prompt and its own `on_success` mapping. Applied to `resume_intelligence`/`market_intelligence`/`learning_roadmap`/`mission_readiness` with byte-for-byte preserved log wording and fallback shapes — proven by Skill Gap's own pre-existing test suite passing unchanged after the extraction (behavior-preservation, not a rewrite).

**Java — `AgentServiceClient` gains one additive method**: `startWorkflowRun(String workflowId, Map<String,Object> payload)` → `POST /workflows/{workflowId}/runs`, returning the new `AgentServiceDtos.WorkflowDispatchResponse` (`workflowId`/`executionId`/`correlationId`/`status`/`durationMs`/`output`/`errors` — the generic envelope ADR-008 standardizes on). `startRun`/`resumeRun`/`getRun` and every existing caller (`WorkflowService`) are byte-for-byte unchanged.

**Java — `ai.careerpilot.runtime` regeneralized** (the frozen Phase 9 package — explicitly authorized for this evolution since nothing called it yet, so no caller could break): `WorkflowExecutionRequest.workflowId()` (plain string) is now the canonical identity; `executionDecision()` is optional, present only when a Mission Execution Engine caller wants policy/priority carried through (`WorkflowExecutionRequest.forDecision(...)` preserves that ergonomic call shape). `WorkflowRegistryAdapter.resolve(String)` is now primary, with `resolve(WorkflowType)` kept as a convenience default method. `LangGraphWorkflowExecutor` now calls `startWorkflowRun` using the resolved definition's business key, reaching any registered workflow. `WorkflowExecutionResult.metrics()` gained `missionId` alongside the existing `workflowVersion`/`executionPolicy`(when present)/`correlationId`/`retryCount`, and `DefaultWorkflowRuntime`'s structured log lines now include `workflowId`/`missionId`/`correlationId` throughout the lifecycle.

**What was explicitly NOT touched**: `ai.careerpilot.skillgap` (Skill Gap's own service/client/controller/DTOs), `/runs`, `/skill-gap/runs`, `ai.careerpilot.mission`/`workflowplanner`/`missionexecution`/`workflowregistry`, any REST API, any feature flag, any DB schema (Skill Gap's `V79` migration is untouched — Phase 10A added no new migration).

Verified via `mvn test` (2266/2266 — 2260 prior + 6 new) and `pytest` (102/102 — 88 prior + 11 dispatcher + 3 helper), including an end-to-end test that dispatches Skill Gap through the *generic* endpoint and gets the identical readiness-score math as its dedicated endpoint.

### Phase 10B — Workflow Development Standard: documentation only, zero code changes
Phase 10B is the publication of the official CareerPilot AI Workflow Development Standard — extracting the proven Phase 9/10/10A pattern into a specification every future workflow (Resume Intelligence, Job Discovery Intelligence, ATS Optimisation, Interview Intelligence, Career Strategy, Application Intelligence, Daily Career Coach, Autonomous Career Agent) must follow. **No production code changed in this phase** — it is a pure documentation deliverable, living under `docs/architecture/`, `docs/workflows/`, and `docs/development/`.

**Start here**: `docs/development/WORKFLOW_DEVELOPMENT_GUIDE.md`. The authoritative specification is `docs/architecture/WORKFLOW_STANDARD.md`; copy-pasteable skeletons are `docs/workflows/java-workflow-template.md`/`python-workflow-template.md`; process checklists are `docs/workflows/workflow-definition-checklist.md` (before building), `docs/development/workflow-review-checklist.md` (PR review), and `docs/workflows/production-readiness-checklist.md` (go-live).

**One explicit, load-bearing correction the Standard makes to naively copying the reference implementation**: Skill Gap Intelligence (`ai.careerpilot.skillgap`) predates the Phase 10A generic dispatcher and ships its own dedicated HTTP client (`SkillGapAgentServiceClient`) and dedicated Python endpoint (`POST /skill-gap/runs`) — the correct call at the time, now a frozen historical exception. The Standard requires every *future* workflow to call the existing, generalized `ai.careerpilot.runtime.WorkflowRuntime` directly (no new client) and register into the existing `WorkflowDispatchRegistry` (no new endpoint) — exactly what Phase 10A's generalization was built to enable. Everything else about Skill Gap's shape (entity/repository/DTO/controller/persistence/history, state-model organization, agent structure, test coverage) **is** the standard and should be copied.

### Phase 6A — Mission-Aware Daily Coach: extends the existing Daily Brief, does not fork it
`ai.careerpilot.mission.MissionAwareDailyBriefService` (NEW class, + 12 nullable columns added to the EXISTING `daily_career_summary` table via `V77__daily_summary_mission_aware.sql`) is explicitly **not** a second Daily Coach — `DailyCareerSummaryGenerator` (Phase 5N) remains the only thing that ever writes a `DailyCareerSummary` row; this is a small collaborator it calls, the identical composition pattern already established for `ExecutiveDecisionEngine` (Phase 7.19.5) one field-block above it in the same entity. `DailyJobDiscoveryScheduler`/`DailyJobDiscoveryCoordinator` are untouched — no second scheduler, no second coordinator.

`MissionAwareDailyBriefService.buildFor(userId)` composes exclusively from already-built engines — never a new computation: the user's most-recent ACTIVE `CareerMission` (Mission Engine, Phase 1) → its latest `StrategyPlan` and `CareerGoal` actions (Strategy Engine, Phase 3) for progress % and today's tasks → `MissionOrchestratorService.run()` (Phase 5) for priority workflows → `CountryMatchingCapability.rankForMission()` (Country Intelligence, Phase 2) for current/alternative relocation strategy, top-ranked country vs. runner-up. High-risk areas are derived only from real incomplete "Improve `<skill>`" actions (worded as "`<skill>` gap") — the phase spec's own example risk "low recruiter activity" is deliberately **not** fabricated since no real data source for it exists anywhere in this codebase, matching this file's "never invent a signal" discipline used throughout.

Both the orchestrator call and the country-ranking call are individually try/catch isolated inside the service (`safeOrchestratorDecisions`/`safeCountryRanking`) so a failure in either degrades that one section to empty rather than losing the whole brief; `DailyCareerSummaryGenerator.applyMissionBrief()` wraps the entire call one layer up as defense-in-depth, so a mission-brief failure never blocks the underlying (pre-existing) summary from being persisted.

Single flag: `career.mission.daily.enabled` (default `false`, inline `@Value`, no `application.yml` entry — same convention as its sibling `copilot.*`/`career.discovery.*` flags). With it off, `buildFor` returns `Optional.empty()` unconditionally without touching any repository (verified by a dedicated `verifyNoInteractions` test) — `DailyCareerSummaryGenerator`'s pre-Phase-6A behavior and the `daily_career_summary` row shape are byte-for-byte unchanged. No REST DTO, controller, or endpoint changed — the existing `GET /api/daily-discovery/summary` simply starts returning the 12 extra (now-populated) fields on the same row once the flag is on and the user has an active mission.

**Pre-existing, unrelated bug found (not caused by this phase) during live verification**: `DailyJobDiscoveryCoordinator.runOnce()` calls `correlation.start(WORKFLOW_TYPE, null, null, null)` — always passing a null `userId` into `workflow_correlation.user_id`, which is `NOT NULL`. `POST /api/daily-discovery/run` therefore fails unconditionally before its per-user loop even starts, independent of any Phase 6A flag. It's never been hit in production because `career.discovery.scheduler.enabled` defaults `false`; left unfixed here as out of scope for this phase and tracked separately.

Migration `V77` confirmed applied cleanly to the live Neon database (`Successfully applied 1 migration ... now at version v77`); with the flag off, `GET /api/daily-discovery/summary` returns 404 for a fresh user exactly as before this phase (no regression). Full end-to-end population of the live JSON response was not curl-verified due to the pre-existing coordinator bug above — the mission-aware field mapping is instead pinned by the two dedicated unit test files (`MissionAwareDailyBriefServiceTest`, `DailyCareerSummaryGeneratorTest`) exercising the real (non-mocked) business logic end-to-end at the service layer.

### Phase 12C — Universal Browser Form Automation Engine: the capability that made real applications possible
A Phase 12C acceptance-test attempt was **stopped at its own gate** before running: auditing the acceptance criteria against the code showed the guest-apply flow filled exactly **three fields** — `GreenhouseConnector.extractForm` returns `{#first_name, #last_name, #email}`, `LeverConnector` returns two — and `GuestApplyAutomationService` never called `uploadResume`/`uploadCoverLetter`/`answerQuestions` (a gap `ExecutionCheckpoint`'s own javadoc already documented). Since resume is a **required** field on every real Greenhouse/Lever form, a real submission would either fail the employer's validation or deliver an incomplete application under the candidate's real name. This phase closes that gap; the live acceptance test is deferred until after it.

`execution/browser/form/` is **one vendor-neutral engine, not one uploader per ATS** — no class in the package names Greenhouse, Lever, Ashby or any other vendor. The pipeline is discover → classify → resolve → plan → fill, each stage an independently testable component. **Discovery runs in the browser** (`FormDiscoveryScript`'s three read-only JS snippets) rather than over fetched HTML, because this codebase has no HTML parser and, more importantly, real ATS forms are JS-rendered — parsing served HTML would see an empty `<div id="app">`. Everything downstream is pure Java over `DiscoveredField` records, which is what makes the entire truthfulness path unit-testable without launching a browser.

**`AnswerResolver` is where "never fabricate" is actually enforced.** It generates nothing and calls no AI; every value comes from one of three pre-existing sources, each named in the result's `source`: `FieldMappingService` (Phase 7.16 — `User`/`CandidateProfile`, already audited for data-source honesty), `User` directly for the first/last-name split that mapper doesn't expose, and persisted `ApplicationSubmissionAnswer` rows (answers a human already reviewed on the approval screen). **`QuestionCategory` is the join key** that makes the engine portable without per-employer code: Greenhouse's "What are your salary expectations?" and Ashby's "Expected compensation" both classify to `SALARY` through the *existing* `QuestionDetectionService` and find the same stored answer. Matching is exact → normalised → category, so a verbatim question always beats a category sibling; `OTHER` never matches by category alone. Fields with no data source anywhere in the schema (phone, LinkedIn, GitHub, portfolio) are **enumerated in `CanonicalField`** rather than omitted — naming a gap is how it stays visible — and always resolve unresolved, checked *before* anything else so a loosely-matching stored answer can't leak into them. `AnswerGenerationService`'s literal failure sentinel is explicitly rejected rather than typed into a live form.

Ordering in `FieldClassifier` is the whole design, and the tests are mostly collisions: `"Cover letter"` must beat the generic file rule (or the cover letter lands in the resume slot), `"First name"` must beat `"name"`, `"LinkedIn URL"` must beat the generic URL rule. Short collision-prone tokens (`cv`, `name`) use whole-word regex — a substring check for `cv` matches "Have you received a COVID vaccine". **An unlabelled file input is never assumed to be the resume.** Choice controls are only filled when a real option genuinely matches; matching is exact/case-insensitive/boolean and deliberately **not** substring-based, because `"No"` is a substring of `"Not applicable"` and on a visa-sponsorship question that difference is material — no match means refuse, never pick the closest-looking option.

**Two safety behaviours are the point of the phase.** (1) A required field with no verified value is a *blocking gap* and **aborts the attempt** rather than parking a human approval — approving a screenshot of a form missing its resume invites approving a submission that arrives incomplete. This is enforced at fill time **and again at `finalizeSubmit`**, which re-navigates to a fresh page after the human approval, so without the second check the resume would be attached to the approved screenshot and absent from the application actually submitted. (2) File uploads are **verified by reading the input back** (`hasUploadedFile`); a `setInputFiles` that silently no-ops — a detached element after an AJAX re-render — would otherwise report success with no resume attached.

The engine runs **after** the connector's own known-good selectors, never instead of them, so it can only ever *add* fields the connector never knew about and cannot regress one it already filled correctly. **It never submits** — `fillForm` stops at the last field; the mandatory `FORM_SCREENSHOT` approval gate is untouched. `nextStep()` (multi-step navigation) is implemented and tested but deliberately **not called by any submitting path**: the approval gate screenshots exactly one page, so traversing pages 2-4 would let a human approve page 1 while the rest was filled unseen — a documented follow-up, not something slipped in here. `MultiStepFormNavigator` is asymmetric on purpose: advancing is inferred permissively (a wrong guess costs a wasted click), submitting requires an unambiguous label with no advance candidate present, two submit-like buttons return `UNCLEAR`, and Back is never chosen.

Cover letter is **text-only**: `CoverLetter` stores prose and this codebase has no PDF renderer, so a cover-letter *file* input is reported as an honest gap rather than uploading a `.txt` where an employer expects a document. `PlaywrightAutomationProvider` gained the control primitives (`evaluate`, `selectOptionAt`, `setCheckedAt`, `uploadFileTo`, `hasUploadedFile`, `fillRichText`, `dismissOverlays`) as concrete methods — **not** on the `BrowserAutomationProvider` interface, which stays the narrow contract the pre-existing connector flow depends on. `fillRichText` uses click-then-`pressSequentially` rather than assigning `innerHTML`, because ProseMirror/Quill editors keep their own model and ignore direct DOM writes — an `innerHTML` assignment appears to work and then submits empty.

Flags: `browser.automation.form-engine.enabled` (default `false` — with it off, `attemptFill` is byte-identical to Phase 12B) and `.require-upload-verification` (default `true`). No new table, migration, DTO, endpoint, or API contract change. Metrics on the existing `/api/diagnostics/browser` under `formEngine`; `formUploadFailures` is the signal that matters — it counts uploads the engine *refused to claim*.

### Phase 12C.5 — Browser Validation Harness: proving the automation works without submitting anything
`execution/browser/validation/` opens a real employer application page, discovers and classifies every control, produces an automation plan and a deterministic confidence score, captures a screenshot, and **stops**. It is how selectors get validated against a live ATS at zero risk to any employer and zero risk to the candidate's reputation — the step that has to come before a real submission is ever attempted.

**The never-submits guarantee is structural, not configuration.** `BrowserFormAutomationEngine` — the only class in this codebase that writes to a page — **is not a dependency of `BrowserValidationHarness` at all**. There is no code path from the harness to an upload, an answer, a submit click, or a multi-step advance, so the guarantee holds by construction rather than by discipline. `BrowserValidationHarnessTest` additionally pins it with `verify(browser, never())` on all nine interaction primitives, so a future edit that introduces one fails loudly. Documents are declared as **availability flags, not loaded**: planning only needs to know *whether* a resume exists to decide if a required file input is a blocking gap, so no resume is ever materialised on disk during validation — a file that is never fetched cannot be uploaded by mistake. Every `ValidationReport` carries `submitted:false`/`documentsUploaded:false`/`questionsAnswered:false` so no consumer can mistake it for a submission record.

**`ValidationUrlPolicy` exists because the harness is an SSRF primitive.** It takes a caller-supplied URL and makes the server fetch it with a full browser — with access to the internal Docker network (`redis`/`kafka`/`minio`) and to cloud metadata. Three independent controls: the trigger lives on the **authenticated** `POST /api/execution/validate-page`, never on the public `/api/diagnostics` surface (reading a past result is safe; triggering a fetch is not); a host allow-list of known public ATS hosts plus operator-added ones; and a resolved-address check rejecting loopback/link-local/private/multicast and the `169.254.169.254` metadata endpoint. **The address check runs for allow-listed hosts too** — DNS is attacker-influenced, and an allow-listed name resolving into a private range is the rebinding case that would make the allow-list the vulnerability rather than the control. Name check runs before address check so an unknown host never triggers a DNS lookup from this server at all. A DNS failure is a denial, not a pass.

**`AutomationConfidence` is deterministic** (no LLM, same discipline as `RetryPolicyService`/`VerificationAdjudicator`): 60 points required-field coverage, 25 classification coverage, 15 supported-control ratio. **A missing required value caps the band at LOW regardless of score** — without that, a page with 40 mapped fields and one unfillable required resume scores ~85 and reads HIGH, which is precisely the false confidence this whole series exists to prevent. A page declaring *no* required fields reports its required coverage as "unproven rather than satisfied" instead of silently scoring 60/60, because many ATSes enforce requiredness in JavaScript.

`SelectorCoverage` deliberately keeps three failure counts separate — **unsupported** (engine cannot drive it: engine work), **unknown** (cannot identify it: usually one classifier rule), **missingRequiredValues** (identified and drivable but no verified data: a product gap, not automation work). Collapsing them into one "failed" number is how a one-line classifier fix gets mistaken for an unsupportable ATS. Hidden/disabled/read-only controls count as discovered but never as coverage failures.

`AtsPlatform` is **reporting only** — nothing in the automation path may branch on it, or the vendor-neutrality of `execution/browser/form/` would be undone in one commit. Detection is host-token only (a path containing `greenhouse.io` must not file a company's own portal under Greenhouse). `BrowserValidationMetrics` holds the latest report per platform in a bounded in-memory map (one entry per enum value, no table, no migration) and labels it `"most recent validation only — not an average across postings"`, since averaging a 6-field form with a 40-field one describes neither.

The harness reports what makes a page *hard* to automate before a failure rather than after: SPA framework, iframe and shadow-root counts (discovery queries the top document only, so zero fields plus a non-zero iframe count is a completely different diagnosis from an empty page — the report says so explicitly), cookie banners, JavaScript errors, and failed requests. **CAPTCHA is detected and reported, never solved.** `PlaywrightAutomationProvider.waitForStable` (DOMContentLoaded → network-idle → settle window) is what separates discovering a real form from discovering an empty `<div id="app">`; it never throws, since a page that never reaches network-idle is common and not a failure.

`DiscoveredField` gained `role` and `xpath` (diagnostics only — the engine acts on the CSS selector, since an absolute XPath breaks on any DOM change), added via a compatibility constructor so existing call sites are unchanged. `role` is deliberately **not** added to `identityText()`, to avoid changing classification semantics.

Flags, all default `false`/safe: `browser.validation.{enabled:false,settle-ms:1500,capture-screenshot:true,allow-list-enforced:true,require-https:true,allowed-hosts:}`. Also requires `browser.automation.enabled`. Results extend the existing `GET /api/diagnostics/browser` under `validation`/`validationPolicy` — no new diagnostics endpoint. No table, migration, DTO change, or schema change.

**UI**: `components/execution/BrowserValidationPanel.tsx`, mounted as a fourth **"Browser Validation"** tab on the existing admin-only `pages/OperationsCenter.tsx` — no new route, since that page is already the home for automation observability. It is deliberately *not* gated by `application.operations.enabled` (the harness has its own flag and its own disabled state, so it stays usable when the operations aggregation view is dark). The never-submits guarantee is rendered as a permanently-visible card rather than a tooltip. The field table shows identity and classification only — never a value — and an `UNKNOWN` classification is toned `warning` because each one is a classifier rule waiting to be written.

**First live run (2026-08-05, local Docker, amd64)**: against a real GitLab Greenhouse posting — Chromium `151.0.7922.71` launched inside the container, discovered **24 real controls**, correctly distinguished the two identically-labelled `Attach` file inputs into `RESUME_UPLOAD`/`COVER_LETTER_UPLOAD`, classified visa/screening/LinkedIn/identity fields, detected reCAPTCHA (reported, never solved) and 2 iframes, scored 49/LOW/not-ready, and released its lease cleanly (`poolAcquired=1, poolReleased=1, poolLeasesExpired=0, activeLeases=0`). **This closes the residual risk carried since Phase 12A** — Playwright genuinely drives a distro Chromium rather than a Playwright-pinned build. Two real gaps surfaced: Greenhouse's custom React dropdowns resolve their label as `"Select..."` instead of the actual question (4 controls lost to `UNKNOWN` — a discovery-script label-resolution fix, not an engine change), and launch took ~39s with navigation ~45s on an 8-core dev box, which needs measuring on the 1-vCPU VM before any rollout stage.

### Phase 13A — Validation history and selector drift: the one genuine gap in a mostly-built Phase 13
A Phase 13 audit (13A ATS Validation Campaign, 13B Canary Submission, 13C Outcome Tracking, 13D Learning Loop, 13E Continuous Recommendations) found that **most of Phase 13 already existed** and, per the phase's own stop conditions, was left untouched. Specifically: 13D's learning loop is one of the most mature subsystems in this codebase — `learning/pattern/` holds 20+ analyzers (skill/company/role/salary/location/industry × success/failure), and `ResumeLearningService`/`ResumePerformanceAnalyzer` already compute exactly 13D's worked example ("which resume version performs better", by real interview and offer rates off append-only `LearningEvent` rows). 13C's outcome tracking exists across `ApplicationStatusHistory`/`ApplicationTimeline`/`ApplicationLifecycleAudit`/`Interview`/`Offer`/`LearningEvent`. 13B's rollout controls exist as `BrowserRolloutGate` + the mandatory `FORM_SCREENSHOT` approval + `VerificationAdjudicator` + `ApplicationExecutionAuditEntry`. 13E's recommendation surface exists as `RecommendedActionEngine`/`ExecutiveDecisionEngine`/`CareerMonitor`. None of these were rebuilt.

The genuine gap was **validation history**. Phase 12C.5 built the harness and kept results in a bounded in-memory map (one entry per ATS, lost on restart) — enough to answer "is this ATS automatable right now", structurally unable to answer "how many pages have we tested", "has confidence moved", or "did a selector change silently degrade us". A validation *campaign* is a question about change over time, so without persistence there was no campaign.

`V80__ats_validation_history.sql` adds `ats_validation_run`, **append-only by contract** — no service updates a row, the entity has no `updatedAt`, and `AtsValidationRunRepository` exposes no delete or update method, so the contract is enforced by the absence of a way to violate it. `SelectorCoverage` is stored as discrete columns rather than a JSON blob so trend queries are plain SQL aggregates rather than per-row JSON parsing on a 1-vCPU box. Every finder is bounded (`findTop20/50/100By...`), matching `WorkflowRunRepository.findTop20By...`.

**`SelectorDriftDetector` is the piece that makes silent degradation impossible.** Pure and deterministic (no LLM, no I/O — same discipline as `RetryPolicyService`/`VerificationAdjudicator`/`AutomationConfidence`). Two design decisions carry it: the baseline is **per-posting, not per-ATS** (two Greenhouse postings legitimately differ — one asks 3 questions, another 20 — so a cross-posting comparison would fire on every other run and train an operator to ignore the alert), and it uses the **median of prior runs, not the last run** (a single flaky run would otherwise become the baseline and mask the real regression after it; a dedicated test pins this). Only `COMPLETED` runs form a baseline, because a `FAILED` run scores 0 by construction and would depress the baseline enough to suppress the very alert a real regression should raise. Severity ladder: readiness lost or a newly-unfillable required field ⇒ `CRITICAL`; confidence drop past the threshold, new unidentified/unsupported controls, or a newly-appeared CAPTCHA ⇒ `WARNING`; `CRITICAL` is never downgraded by a later `WARNING`. **Insufficient history reports `NO_BASELINE`, never `NONE`** — "we have not checked" must never render as "all clear".

`ValidationHistoryService` persists the run and produces the campaign dashboard. It reads the baseline **before** inserting, so a run can never be its own baseline (tested). Honesty rules: an untested ATS is **absent** from the report rather than shown as zero; a platform with only failed runs states `"No completed runs"` rather than an invented 0% confidence; a trend is only stated at ≥4 completed runs and is a newer-half-vs-older-half comparison with a ±3 dead band, deliberately **not** a fitted regression line, since a slope reads as precision this data does not have. `distinctPostings` is reported separately from `pagesTested` because validating the same page ten times is one page of real coverage. **PII boundary**: `campaignReport()` is served on the unauthenticated `GET /api/diagnostics/browser` and emits aggregates only — never a URL, never a user id (pinned by a test).

Wired at the call site (`ExecutionController.validatePage`) rather than inside the harness, so neither `BrowserValidationHarness` nor `ValidationReport` changed shape; the drift verdict is merged into the validation response so an operator learns about a regression in the response that caused it, not from a dashboard hours later. A persistence failure never propagates — the report is the deliverable, the row is bookkeeping.

Flags: `browser.validation.history.enabled` (default `false`), `browser.validation.drift.{confidence-drop-threshold:10,minimum-baseline-runs:2}`. **Explicitly not built** (audited as already-existing or as genuinely absent but out of this slice's scope): 13B per-ATS/per-employer rollout dimensions (only per-user exists today), 13C prompt-version tracking and time-to-response/interview/offer latency — the latter is **computable from existing `LearningEvent` timestamps with no schema change**, and is the natural next slice.

### Phase 13B — Production Intelligence Orchestration: an aggregation layer, not another learning engine
`ai.careerpilot.intelligence` composes the intelligence that already exists into one evidence-backed model. **It computes nothing.** Resume rates come from `ResumeLearningService`'s `resume_learning` rows, dimension patterns from the Phase 6 `SuccessPatternEngine` analyzers' `success_pattern` rows, ATS readiness from Phase 13A's `ValidationHistoryService`. No new analyzer, no competing recommendation engine, no recompute triggered from a read path (calling `ResumeLearningService.recompute` from a Copilot turn would turn a question into a write transaction — the snapshot reports `computedAt` staleness instead).

**The division from `CareerContextService` is the load-bearing design decision.** Mission, Career Timeline, Career Memory, Workflow, Applications, Interviews and Company Knowledge are *deliberately absent* from `ProductionOptimizationSnapshot` — Phase 11A's `CareerContextService` already aggregates every one of them and is already wired into the Copilot. Restating them would create two sources that can disagree about the same fact. The two answer different questions and compose at the Copilot rather than inside one another: `CareerContextService` = "what is happening", `ProductionIntelligenceService` = "what the evidence says works". They render as two separate prompt blocks for the same reason — a soft operational statement must not sit in the same section as a hard evidential claim.

**`Evidence` is the mechanism behind "never recommend without evidence".** Every finding carries source, sample size, supporting counts, `lastUpdated`, and a `cite()` string. **Confidence is a band (INSUFFICIENT/LOW/MEDIUM/HIGH) derived solely from sample size — never a percentage**, a deliberate departure from the phase brief's own "Confidence 96%" examples: three applications and one interview is a 33% rate, and any percentage built on it is arithmetic dressed as certainty. That would be the most persuasive fabrication in the system, because a user would act on it. Below `MINIMUM_SAMPLE` (5 observations) nothing is recommended at all — a resume version or a country below the floor is reported with its real counts and an explicit reason, or dropped from a top-list entirely rather than shown weakly (a "top country" whose first row rests on two applications teaches the reader to distrust the list).

`OptimizationRecommendationService` is pure and deterministic (no LLM, no repository access — same discipline as `RecommendedActionEngine`/`RetryPolicyService`/`AutomationConfidence`). It **structurally cannot fabricate**: every input arrived carrying an `Evidence` record and the orchestrator already dropped everything below the floor, so a citation-free recommendation is not something it declines to make but something it cannot construct. Comparative claims ("Germany, 19% ahead of the Netherlands") are only made when the snapshot genuinely holds both entries and the margin is quoted from their two real rates; a lead under 5 points is labelled **"only marginally ahead"** rather than dressed up, and a single entry is stated flatly with no comparison invented. `AtsIntelligence` carries a mandatory caveat that it measures *form-automation* readiness and **not** which ATS produces more interviews — no table in this platform records outcomes keyed by ATS, so that claim cannot be made and must not be implied. Ranking ladder: resume (goes on every application) → country → skill → company → ATS.

Wired into `CopilotService` with the identical centralized pattern as `careerContextBlock()` — populated once per turn, appended to every skill's context, no handler touched. The prompt text instructs the model to quote the figures verbatim and explicitly forbids characterising them as "strong"/"weak" without stating the numbers, extrapolating a trend, or inventing a confidence percentage; an unlisted dimension must return "No verified data available." `render()` returns that same sentence for an empty list rather than falling silent, since silence reads as "nothing to improve" — a different and false claim.

Flags, all default `false`: `production.intelligence.enabled`, `optimization.recommendations.enabled`, `copilot.production.enabled`. One additive typed accessor (`ValidationHistoryService.platformReadiness()`) so the orchestrator reads rather than re-derives or parses a display map. **No new table, migration, DTO, endpoint, or schema change** — the snapshot is transient aggregation, as the phase required. **Explicitly not built** (stated rather than silently skipped): the Production Intelligence *dashboard* and any frontend, Mission/Timeline/Memory/Job-Ranking/Resume-Optimizer consumption of the snapshot. The backend model and its Copilot surface are complete; those integrations are additive next slices, each a call to `getSnapshot(userId)` at their own seam.

### Phase 13C — Production Intelligence Integration: consumption, not another engine
Integration-only. No new recommendation engine, analyzer, scoring engine or Copilot context was created — the phase's central constraint. Two genuinely new pieces, both thin consumers of the Phase 13B snapshot.

**Adaptive job ranking is the fourth booster in an existing chain, not a new scorer.** `JobMatchingService` already applies three bounded adjustments in an established shape — `applyLearningBoost` → `applyCompanyKnowledgeBoost` → `applyCareerMemoryBoost`, each with an `isActive()` gate, a bounded integer boost, a `[0,100]` clamp, and `base` returned as the *same object* when dark. `ProductionIntelligenceBooster`/`applyProductionIntelligenceBoost` is the fourth link in that identical shape; `JobScoring.scoreV2`'s own weights are untouched. Bound is ±10 on a 0–100 score (the specified ±10%), with per-dimension caps (country ±5, company ±5, skill ±4) so no single signal can consume the whole budget.

Three decisions in the booster carry it. **The snapshot is passed in, never fetched inside** — `refreshForUser` scores a pool of hundreds in one stream, so a booster resolving its own snapshot would be four repository reads *per job*; the caller resolves it once per refresh (and not at all when the flag is off, so a stock deployment builds no snapshot). **An attribute the snapshot has never seen contributes zero, not a penalty** — "no evidence about this country" and "this country performs badly" are different statements, and conflating them would quietly suppress every job in an unexplored market, which is exactly the market a candidate most needs surfaced. **Skills use the strongest single match rather than a sum**, or a job listing ten technologies would out-rank one listing the two that matter. Rates saturate at twice the neutral midpoint, so an 80% conversion on a handful of applications cannot dominate a ranking.

**One read surface for three consumers.** `GET /api/intelligence/optimization` (authenticated — this is one person's own outcome history, unlike the aggregate ATS campaign report on the unauthenticated diagnostics endpoint) returns the snapshot and its ranked recommendations from the same read, so the two can never describe different states. The Resume Optimizer's recommended-version panel (Part 2), the Mission guidance strip (Part 3) and the Dashboard cards (Part 7) each render a slice of that one payload rather than getting an endpoint apiece — three endpoints would be three places for the shape to drift. Returns `200` with an explicit empty payload rather than `404` when dark, the same convention `GET /api/career-timeline` established, so a client can tell "disabled" from "no evidence yet".

**Parts 4 and 6 were already complete in Phase 13B and were deliberately not touched**: the Copilot already receives the evidence block via the centralized `optimizationBlock()` seam, and explainability (why / evidence / sample size / confidence band) is already intrinsic to `Evidence` and `Recommendation`. Rebuilding either would have been the duplicate-context the phase forbids.

Flag: `jobs.matching.production-intelligence-boost.enabled` (default `false`) — with it off, ranking is byte-for-byte identical to Phase 13B, verified by the five pre-existing `JobMatching*Test` suites passing unchanged. No new table, migration, DTO change, or breaking API change. **Explicitly not built**: Part 5's timeline events (change detection requires persisting a prior snapshot to diff against, and the phase forbids new tables without necessity — recording "Resume V10 became recommended" honestly needs that prior state, so it is a deliberate deferral rather than an omission), and all frontend for Parts 2/3/7 — the payload they consume is complete and served.

### Phase 10H — Career Timeline: an aggregation-only read layer, zero new persistence
`ai.careerpilot.careertimeline` (`CareerTimelineService`, `CareerTimelineController` at `GET /api/career-timeline`) is the first single, cross-category, chronological feed spanning a user's whole activity — Mission, Application, Resume, Learning, Interview, Memory, Company, and AI Workflow events in one sorted list. It is deliberately **not** a new event store: it creates zero tables and reuses eight already-existing sources verbatim — `CareerMissionRepository`, `ApplicationTimelineRepository`, `ResumeRepository`/`ResumeTailoringRepository`, `LearningEventRepository`, `InterviewRepository`, `CareerMemoryService.timelineFor(...)` (Phase 7.15.1), and `CompanyKnowledgeRepository`/`CompanyTimelineEventRepository` (Phase 7.13/7.17) plus `WorkflowRunRepository.findTop20By...` (the existing LangGraph run list). Two of those repositories gained one additive query method each (`findByUserIdOrderByOccurredAtDesc` on `ApplicationTimelineRepository` and `CompanyTimelineEventRepository`) — no schema change, the backing columns already existed.

**Deliberately excludes an "Analytics" category.** `ApplicationAnalytics`/`CareerIntelligence` are raw numeric snapshot series with no discrete "personal best" or "score improved" event ever computed or persisted anywhere in this codebase (confirmed by architecture review before building this phase) — synthesizing one would be exactly the fabricated-narrative problem this feature exists to avoid, so Analytics is simply absent from the category list rather than invented.

Each of the eight sources is read independently inside its own try/catch (mirroring `ApplicationCardService`'s established defensive-isolation convention) — one source failing degrades that category to empty rather than breaking the whole feed. Mission/Workflow categories legitimately emit a second event (e.g. "Mission completed") only when the entity's `updatedAt` genuinely differs from `createdAt` — never a fabricated status-change event for a row that was never actually updated.

**`GET /api/career-timeline?category=&page=&size=` always returns HTTP 200**, unlike most other feature endpoints in this codebase — the response carries an explicit `enabled` boolean instead of 404-ing when `career.timeline.enabled` is off, so the frontend can distinguish "feature disabled" from "no events yet" rather than collapsing both into the same empty state. Pagination is manual in-memory truncation over the merged, sorted list (this codebase's established convention — see `WorkflowRunRepository.findTop20By...` — not Spring Data `Pageable`/`Page<T>`), fetching one extra row internally to compute `hasMore` without a second query.

Single flag: `career.timeline.enabled` (default `false`, inline `@Value`, no `application.yml` entry, same convention as `career.memory.enabled`). Frontend: `pages/CareerJourney.tsx` at `/career-journey` (nav-linked, "Career Journey"), category filter chips, expandable event cards (icon/title/description/relative-time/category badge/AI-vs-manual badge/expand-for-detail), `useInfiniteQuery` + "Load more" (the same pattern already established in `RecommendedJobs.tsx`, not a new pagination mechanism). No fabricated header stats — "Career age" and "Career score" were considered and deliberately omitted (no account-creation timestamp or single career-score concept exists anywhere in the backend); only genuinely available data is shown (current active mission via the existing `GET /api/missions`, last-activity relative time from the newest real event, events-loaded count).

Verified via `mvn test` (2281/2281 — 2269 prior + 12 new) and `npx tsc --noEmit` + `npm run build` (frontend, zero errors).

### Frontend data flow
[lib/api.ts](frontend/src/lib/api.ts) is a single axios instance with a bearer-token request interceptor (reading from the zustand store in [lib/auth.ts](frontend/src/lib/auth.ts)) and a 401-→-logout response interceptor. Auth state persists to localStorage via zustand's `persist` middleware. Server state uses TanStack Query — refetches are explicit (`queryClient.invalidateQueries`) after mutations; there is no SSE/WebSocket, so the Workflow page only updates on user action.

## Provisioned-but-unused (do not assume these are integrated)

Knowing what is *not* wired prevents wasted debugging:
- `refresh_tokens` table — no `/api/auth/refresh` endpoint exists
- `audit_logs` table — no code writes to it
- `usage_records` table — no code writes to it; cost tracking is not aggregated
- `embedding` vector columns — no embedding generation anywhere (pgvector extension is installed, but no HNSW/IVFFlat indexes)
- Redis — `spring-boot-starter-data-redis` on the classpath, no `@Cacheable` / `RedisTemplate` usage
- `careerpilot.audit.events` topic — declared in config, neither produced nor consumed
- `security.rate-limit.*` values — read by no limiter (no Bucket4j / RedisRateLimiter)
- `@KafkaListener` — zero consumers exist; producer events go nowhere
- `refresh_tokens` table — exists but no refresh endpoint wired
- `AdaptiveRecommendationEngine.getBoost()` (`learning/recommendation/`) — computed and persisted end-to-end, but not called by `JobScoring`/`JobMatchingService`; live job matching does not use outcome-based learning today despite the pipeline existing

When in doubt, grep for the symbol — if it has no callers, it is scaffolding.

## Diagnostics and Monitoring

[DiagnosticsController.java](backend/src/main/java/ai/careerpilot/api/DiagnosticsController.java) exposes two public endpoints (no auth required) for troubleshooting:

- **`GET /api/diagnostics/ai`** — Gateway diagnostics: API keys loaded, configured models, base URLs, provider health (UP/DOWN/NOT_CONFIGURED), provider order, call stats (total calls, fallbacks, failures per provider), default temperature.
- **`GET /api/diagnostics/workflow`** — Workflow engine diagnostics: workflowEngine/jsonSerialization/agentService status, plus provider chain health. Used to validate that all three services and the provider chain are operational after deployment.

These endpoints are **not guarded by auth** (anyone can call them) to enable uptime monitoring without needing credentials.

Most later phases ship their own narrower diagnostics controller rather than extending `DiagnosticsController` — e.g. `ExecutionDiagnosticsController` (execution/recovery/operations), `PipelineDiagnosticsController` (gap-analysis/ATS-explainability/cover-letter/application-package/auto-apply-package). Before adding a new admin/ops surface, check whether it belongs on one of these existing controllers instead of a new one — `frontend/src/pages/OperationsCenter.tsx` (admin-only route) already aggregates execution/retry/recovery data this way and is the pattern to extend, not duplicate, for any future ops dashboard work.

## Conventions

- Java package root is `ai.careerpilot`. Sub-packages are role-based: `api` (controllers + DTOs), `service`, `repo`, `domain` (JPA entities), `security`, `kafka`, `storage`, `ai`, `agent`, `config`.
- Python agents live one-file-per-agent under `agent-service/app/agents/`. Each exports a single `<name>_node(state) -> dict` function; the dict is shallow-merged into `CareerState` by LangGraph.
- New backend endpoints accept `AuthenticatedUser` as a method parameter (see any existing controller) — this is how you get `userId`/`orgId`.
- Frontend pages live under `src/pages/`, one file each. Routes are registered in [App.tsx](frontend/src/App.tsx) inside the `<Private>`-guarded `<Layout>`.
